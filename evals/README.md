# `evals/` · 评测体系与**口径台账**

> 状态：**当前有效** ｜ 最后更新 2026-10-27

## 1. 怎么跑

```powershell
uv run python evals/run.py --help          # 检索 / 生成 / 拒答 / 读图
uv run python evals/agent_paired.py ...    # agent 与 pipeline 配对评测
```

`results/` **不进 git**（一次跑出几十份 JSON，且和当时的库强相关）。可复现的是
`questions/`（题集）＋ `corpus/`（知识库 B 语料）。

## 2. ⚠️ 口径卡：从 2026-10-27 起**强制记录**

**起因（真实教训）**：2026-10-27 想回看历史结果，发现 58 份里**只有 5 份**记了"用的哪支尺子"
（`--scope all` vs `--scope current`），其余**无法还原** —— 同一批题、不同尺子，数字不可比，
而事后只能靠文件名日期去猜。

⟹ 从此每份结果 JSON **必须**自带这几项（顶层或 `config` 里）：

| 字段 | 记什么 | 为什么 |
|---|---|---|
| `corpus` | 语料版本：篇数 / 块数（如 `B库 36篇/237块`） | 加料前后数字会自然位移，不记就说不清"涨在哪" |
| `retrieval_scope` | `all` 还是 `current` | **尺子不同，分数不可比** |
| `questions` | 题集文件名与题数 | 题库一改，历史数字立刻不可比 |
| `llm_model` / `embedding_model` / `rerank_model` | 模型名 | 换模型会静默改变结果 |
| `rerank_enabled` / `top_n` | 检索配置 | 同上 |
| `answer_mode_default` | 快速还是 agent | 两条路的分数本来就不是一回事 |

**报数时必须带版本**，例：`精排 0.983（B库 36篇/237块 · scope=current）`。

✅ **2026-10-27 补齐情况**：`retrieval` / `generation` / `refusal` / `image-*` / `agent-paired`
五条 dump 现在**都带** `config.corpus` 与 `retrieval_scope`（`agent-paired` 还带 `repeat`）。
此前只有 `retrieval` 记了尺子、**一份都没记语料版本**。

⚠️ **同日修掉的一个坑**：结果文件名取**开始时刻**，同一层两路并发跑会撞在同一秒
⟹ 后完成的**静默覆盖**前者（当天真丢了一份 `generation` 结果，只能猜它属于哪支尺子、最后删掉）。
现在重名一律加 `-2` 后缀，**绝不覆盖**；而**同层不要并发跑**仍是纪律。

**两条读法（别用错）**：
1. **两支尺子不是"哪个更对"**：`current` 是产品态（只在有资格被引用的文档里召回），
   `all` 是全库召回（复现历史数字）。**差值**才是"内容治理值多少分"。
2. **单跑数字不可信**：同一尺子、同一库、同一份题，生成层单跑能在 10~18/20 之间跳（±7 题）。
   报数一律用 **3 次均值**，并把**抖动范围**一起写出来。

## 4. 冻结规则（加料前必读）

1. **先冻结再改**：动语料之前，把当前这批结果标成"改语料之前"，新结果另起一行；
2. **两支尺子都要跑**（`--scope all` / `--scope current`），差值才是"治理值多少分"；
3. `must_hit` 里有 `evidence` 的条目要**重标**（语料变了，证据位置会漂）；
4. 永远保留旧 JSON —— 数字变了不是 bug，是改动的正常位移，**要能解释清楚是哪一项改动带来的**。

| 题 | 期望文档 | 加料后 top-1 | 为什么 |

📌 **这两条不打算"修"**：它们就是"库里多了一堆主题相邻的真页面"之后的正常代价 ——

⚠️ **`must_hit` 没有重标**：12 篇新文档不改变任何一题的标准答案文档（题集问的都是老主题），
所以这一轮**不需要动 `retrieval.yaml`**；下次若给新页出题，才走 §4 第 3 条。
