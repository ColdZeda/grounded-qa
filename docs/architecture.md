# 1. 全貌：一次提问经过哪些环节

```
用户提问
  │
  ├─① 鉴权        Bearer token → 解出 user + tenant
  │
  ├─② 取会话      租户 + 用户双重限定；取不到 → 404
  │
  ├─③ 存提问      用户消息**立刻落库**（刷新页面不丢）
  │
  ├─④ 两路检索    ┌─ 全文路：pg_trgm word_similarity（擅长精确串/型号/错误码）
  │              └─ 向量路：pgvector 余弦距离（擅长语义相近）
  │                   ↓
  │              RRF 融合（只按名次，不看分数）
  │
  ├─⑤ 精排        rerank 模型把 (query, doc) 成对打分 → 重排
  │
  ├─⑥ 判拒答      ★ 证据不够？→ 直接返回固定文案，**根本不调对话模型**
  │
  ├─⑦ 生成        组装提示词（编号引用）→ 流式生成 → SSE 逐段下发
  │
  └─⑧ 落库        回答 + 引用 + 拒答标记 + 耗时
```

**两个刻意的顺序**：

- **④ 在 ⑤ 之前**：先用便宜的方式把候选缩到 20 条，再花钱精排。反过来是拿钱换时间，不划算。
- **⑥ 在 ⑦ 之前**：拒答是**确定性代码**的判断，不是模型的自由发挥。详见 §5。

# 2. 多租户：隔离是怎么"焊死"的

## 2.1 为什么不能靠"记得写 `WHERE tenant_id = ?`"

多租户系统最经典的翻车方式就一句话：**某个查询忘了加租户条件**。

它危险在于：
- **不会报错** —— 接口 200，数据也"对"，只是看到了别人的
- **code review 挡不住** —— 人会忘、新人更会忘、急着上线时最容易忘
- **测试常常测不出来** —— 见下面 2.3

所以这里换了个思路：**不靠自觉，靠结构**。

## 2.2 三道防线

**第一道：表必须带 `tenant_id`（编译期级别的约束）**

`app/db/base.py` 的 `TenantMixin`：继承它 = 自动获得 `tenant_id` 外键 + 索引。

更进一步，有一条**元测试**（`tests/test_tenant_isolation.py`）：

```python
# 所有业务表都必须有 tenant_id，例外只有 tenants 自己
assert missing == []
```

将来谁加了一张新表却忘了继承 Mixin，**测试当场变红**。

**第二道：查询必须经过仓储层**

`app/db/repository.py` 的 `TenantScopedRepository` 把 `tenant_id` 条件**焊进查询构造**：

```python
# ❌ 反面教材：只按主键查，不带任何租户条件
conversation = await session.get(Conversation, conversation_id)

# ✅ 正确：条件在 repo 内部就注入了，你没有"忘记加"这个选项
repo = TenantScopedRepository(session, tenant_id=user.tenant_id, model=Conversation)
conversation = await repo.get(conversation_id)   # 跨租户必然返回 None
```

如果传进去的模型没有 `tenant_id` 列，**直接抛异常**（`MissingTenantColumnError`）——宁可启动就炸，也别带着漏洞跑。

**第三道：写入侧不给"自己选租户"的机会**

```python
repo.build(tenant_id=...)   # ← 直接 ValueError
```

写接口如果能"自己指定归属"，那隔离就退化成了输入校验 —— 早晚出事。

## 2.3 越权测试：为什么"成员 A 读成员 B"是个假测试

大多数项目会这么写越权测试：

> 普通成员 A 去读成员 B 的会话 → 期望 404 ✅

**这个测试是假的。** 因为就算**租户条件完全没写**，代码里的 `user_id` 过滤也会挡住 A —— 测试照样绿，漏洞照样在。

所以这里的测试设计是：**让攻击者是另一个租户的管理员**。

```python
async def test_admin_of_another_tenant_gets_404_not_someone_elses_data(...):
    # 租户 B 的管理员，拿租户 A 的会话 id 去查 → 必须 404
```

管理员本来就能看本租户**所有人**的数据，所以"只看自己的"这条规则**帮不上忙** —— **只剩租户过滤能挡住他**。漏写租户条件 → 这条必红。

## 2.4 隔离是**两层**的

| 层 | 规则 |
|---|---|
| 租户之间 | 谁都别想跨过去（包括管理员） |
| 租户内部按用户 | 普通成员只看得到自己的会话；**管理员能看本租户所有人的** |

> **"管理员"是「租户内的管理员」，不是超级管理员。**
> 跨租户的运营动作**没有 API**，只能手工做 —— 这不是遗漏，是**故意不给入口**：
> 多租户里最危险的 bug 就是"某个 admin 接口忘了限定租户"，不给它入口就少一类漏洞。

## 2.5 越权为什么返回 **404** 而不是 403

| 返回 | 泄露的信息 |
|---|---|
| `403` | "**这条数据存在**，只是不给你看" → 攻击者可以**枚举**出有效 id |
| `404` | 什么都不透露 ✅ |

只有一种情况给 403：**已经登录了，但角色权限不够**（比如普通成员调管理端）—— 这时"存在性"不是秘密。

# 3. 鉴权：登录这件事的六个细节

## 3.1 为什么用 bcrypt 而不是 argon2

argon2 理论上更强，但它依赖 C 扩展 `argon2-cffi-bindings`；**Python 3.13 上不保证有预编译 wheel**，没有就得现场编译 —— CI 变慢、容器构建可能直接失败。

bcrypt 提供 **abi3 wheel**（cp39+ 通用），3.13 上直接装。

> **取舍原则**：在这个项目里，**"装得上、可复现" 优先于 "理论强度更高"**。
> 一个装不上的更强算法，实际安全性是 0。

## 3.2 bcrypt 的 72 字节上限：**拒绝**，不静默截断

bcrypt 只取密码的前 72 字节，**超出部分被悄悄丢掉**。后果：

```
"a"×72 + "X"  和  "a"×72 + "Y"  被当成同一个密码
```

用户以为自己设了更长的密码，其实后半截根本没参与。所以这里**直接报错**，而不是"悄悄帮你截断"。

## 3.3 bcrypt 必须丢进线程池

bcrypt 是 **CPU 密集**的（这正是它抗暴力破解的原因，cost=12 大约 100~250ms）。

如果在 `async def` 路由里**直接调它**，它会把**整个事件循环**卡住 —— 表现为"有人在登录，所有其他请求一起变慢"。所以：

```python
password_ok = await run_in_threadpool(verify_password, form.password, hashed)
```

## 3.4 用户不存在时，也要跑一次哈希（**时间抹平**）

如果"用户不存在"直接返回，而"密码错"要跑 100ms 的 bcrypt，那么**响应时间本身就泄露了"这个邮箱注册过没有"**。

攻击者可以先枚举出有效邮箱，再针对性爆破。做法：用户不存在时也拿一个**假的哈希**跑一次校验。

## 3.5 "密码错"和"用户不存在"必须返回**完全相同**的响应

不只是都返 401 —— **状态码、响应体、响应头**都要一样。测试里直接断言：

```python
assert wrong_password.json() == unknown_email.json()
```

## 3.6 JWT 里带 `tid`，但每个请求**仍然回库核对**

token 里存了 `tid`（租户 id），但 `get_current_user` 每次都会：

1. 按 `sub` 回库查用户
2. 查用户 `is_active` **和** 租户 `is_active`（运营侧的一键止血）
3. **核对 `token.tid == user.tenant_id`**

第 3 步平时是冗余的 —— **冗余的那一份就是用来发现不一致的**：万一某天要做"用户换租户"，旧 token 里还带着旧租户 id，不核对就会出现"人已经不在这个租户了，token 还能读它的数据"。

## 3.7 生产环境不许用开发默认密钥启动

`config.py` 里有个 `model_validator`：`APP_ENV != dev` 时，如果 `JWT_SECRET` 还是默认值、或长度 < 32 字节，**直接拒绝启动**。

> 这类校验必须"启动就炸"。等跑到某个请求才发现，意味着**它已经上线了** ——
> 而公网上一个 `dev-only-...` 的密钥等于任何人都能伪造管理员身份。
>
> ⚠️ **代价要说清楚**：如果部署时忘了把 `APP_ENV` 改成 `prod`，这道闸**不会**拦你。
> 它防的是"知道要上生产但忘了换密钥"，不是"忘了设 APP_ENV"。

## 3.8 一个刻意的简化：邮箱**全局唯一**

含义是「一个邮箱只属于一个租户」—— 跟多数 SaaS 一样（一个账号 → 一个工作区）。

- **好处**：登录只需邮箱，不用先选租户（少一步交互、少一个越权面）
- **代价**：同一个人属于两家公司要开两个邮箱
- **将来要改的话**：去掉 `email` 的全局唯一约束 + 登录接口加 `tenant_slug`

# 4. 检索：为什么要两条路，以及 RRF

## 4.1 两条路的**失败模式不同**

| | 擅长 | 不擅长 |
|---|---|---|
| **向量检索** | 语义相近（"怎么重置密码" → "密码找回流程"） | **精确串**：型号、错误码、专有名词 |
| **全文检索** | 精确串（"报错 E1024"、"X200 保修期"） | 换个说法就找不到 |

而客服场景里**恰好大量是后者**（用户直接复制错误码来问）。所以两条路不是"保险起见"，而是**互补**。

## 4.2 RRF：只用**名次**，不用分数

公式：`score(d) = Σ 1 / (k + rank_i(d))`，`rank` 从 1 开始。

**为什么不能直接加权求和？** 因为两种分数**量纲根本不同**：

- 向量：余弦相似度，0~1，反映语义距离
- 全文：`word_similarity`，0~1，反映字符串重合

两个都叫"0~1"，但一个是"意思像不像"，一个是"字面像不像"。给它们各配一个权重相加，**权重就是拍脑袋**。

RRF 的价值在于：**它把两者变成同一个尺度**（都是"排第几"），于是不需要任何权重。

| 细节 | 为什么 |
|---|---|
| `k = 60` | 它来自原论文。作用是**压平头部**：`k` 很小时（如 1），第 1 名和第 2 名差一倍（1/1 vs 1/2），融合几乎退化成"看第一路"。`k=60` 让前几名差距变小，**多路的一致性**才真正起作用 |
| 只被一路命中的文档**照样得分** | "向量路第 1 名"本身就是强信号，不该因为全文路没召回它就归零 |

## 4.3 `word_similarity` 而不是 `similarity`

两者都是 `pg_trgm` 的，但语义不同：

- `similarity(a, b)`：**整体**相似度。拿 10 个字的提问去比 800 字的 chunk，整体相似度必然很低（分母是长文本）→ 阈值怎么调都召回不出来
- `word_similarity(query, text)`：**"query 有多像 text 里的某一小段"** ← 这正是"短问句 vs 长文档"要的东西

## 4.4 ⚠️ 一个差点让全文检索**完全失效**的坑

`pg_trgm` 按数据库的 **ctype** 决定"什么字符算词"。实测：

| `datctype` | `show_trgm('退款政策')` | `word_similarity` |
|---|---|---|
| `C` | **`{}` 空集** | **0**（永远） |
| `C.UTF-8` | 5 个三元组 | **0.4** ✅ |

**`C` 下中文不算字母 → 一个三元组都切不出来。**

它危险的地方不是"质量差一点"，而是：

> **全文那一路永远召回不出任何东西，而系统不报错、状态码 200** ——
> 看起来就像"知识库里确实没有"。不做实测根本发现不了。

**已处置**：① dev + prod 建库参数都用 `--lc-collate=C.UTF-8 --lc-ctype=C.UTF-8`（**两边必须一致**，否则会出现"本地好好的、部署上去中文一条搜不到"）；② 加了**启动自检**（`app/db/checks.py`），切不出三元组就大声告警。

## 4.5 全文路的阈值刻意设得很低（0.05）

这一步**只做粗筛**，真正的排序与取舍交给 RRF + rerank。

把粗筛阈值调高 = **在检索早期就把可能正确的答案丢掉**，后面再也救不回来。

## 4.6 一个**已知的不完美**：全文路吃不到索引

查询用的是 `word_similarity() >= 阈值` 的**函数形式**，而 `pg_trgm` 的 GIN 索引只加速**算子形式**（`%`、`%>`、`ILIKE`）。

所以：**索引吃不到 → 每次全表算一遍。**

- **为什么还这么做**：算子形式依赖**会话级**阈值 `pg_trgm.word_similarity_threshold`，连接是池化的，会话状态容易串味；函数 + 显式阈值是**确定性**的、可测的
- **为什么现在可以接受**：`cpu 2 核 / 知识库规模小`，几千条 chunk 全表算是毫秒级
- **什么时候必须改**：知识库上万条以后。改法写在 `migrations/versions/…_enable_pg_trgm_….py` 的注释里（**两件事必须一起做**：加 GIN 索引 + 改查询为算子形式，并用 `set_config(..., is_local=true)` 设阈值）

> 📌 **所以这里**没有**建那个 GIN 索引** —— 建了也用不上，白白增加每次写入 chunk 的开销。
> "知道它不 scale、也知道怎么改，但**现在不做**" 和 "不知道有这回事" 是两码事。

# 5. 精排与拒答：幻觉治理的核心

## 5.1 embedding 和 rerank **不能互相替代**

| | 结构 | 何时算 | 能干什么 |
|---|---|---|---|
| **embedding** | **双塔**：query 和 doc **分别**编码，彼此不见面 | **离线**预计算 doc 向量 | 快速从海量文档里"捞"出候选 |
| **rerank** | **交叉编码**：把 (query, doc) **拼在一起**过一遍模型 | **在线**，每个候选算一次 | 精细判断"这两条到底有多相关" |

因为双塔里 query 和 doc **从没见过面**，它给不出比向量检索更细的排序。

> **所以"用 embedding 模型当 rerank"是无效的**（同模型更没意义：排序完全一样）。
> 但**同一把 Key / 同一家供应商**是完全可以的 —— 那是账号，不是模型。

## 5.2 ★ 拒答必须在**调模型之前**由确定性代码决定

这是整份文档里最重要的一条。

**天真做法**："在提示词里告诉模型 —— 如果资料不足就说不知道。"

**为什么不行**：
1. 模型天然倾向于给出一个**听起来合理**的答案（它的训练目标就是"接着往下写"）
2. 于是"拒答率"变成了**模型心情的副产品** —— 统计不出来、也没法优化
3. 拒答时还要付一次 token 钱
4. 那句"我不知道"还可能被模型**润色**成一段看似有依据的话

**我们的做法**：证据不够 → **直接返回固定文案，一次模型都不调**。

好处：
- 拒答率成了一个**真实、可优化、可回归测试**的指标
- 拒答不花钱
- 拒答文案永远不会被"润色"

测试里有一条锁死这个行为：`assert chat.calls == []`。

## 5.3 ★ 置信度阈值**绝不能**挂在 RRF 分数上

RRF 是**名次**的函数。库里只有一条毫不相关的内容时，它**照样排第一、照样拿到 `1/(60+1) ≈ 0.016`**。

拿它比阈值 = **永远不拒答**（因为任何命中都会有个非零分数）。

所以按情况分三条路（`pipeline.py` 的 `_should_refuse`）：

| 情况 | 结论 | 依据 |
|---|---|---|
| 一条都没检索到 | **拒答** | 没有任何证据，答什么都是编 |
| 有 rerank 分数 | 按 `ANSWER_MIN_SCORE` 判 | 交叉编码的分数是**校准过的相关性**，可以定阈值 |
| 没有 rerank 分数 | **不拒答** | 只有 trgm 相似度时，那个数字**不是相关性语义**，拿它比阈值等于瞎判 |

第三条看着"不够安全"，但**用无意义的数字假装判断过**才是真的危险：它会给你一个虚假的安全感。

## 5.4 模型/依赖挂了要**降级**，不要跟着挂

| 挂掉的组件 | 降级行为 |
|---|---|
| embedding | 退化成**纯全文检索**（召回差一些，但还能答） |
| rerank | 退化成 **RRF 顺序**（排序差一些，但还能答） |
| 对话模型 | 流里发 `error` 事件；**已经拿到的半截回答照样落库**（见 §8.3） |

> **可用性 > 功能齐全。** 一个"精排服务抖动就整个问答 500"的系统，不如一个"降级但一直能答"的系统。

## 5.5 拒答与引用为什么必须**落库**

`messages` 表上有两列：`refused`（布尔）和 `citations`（JSONB）。

- **不落 `refused`**：拒答率统计不出来 → 幻觉治理**没有仪表盘**
- **不落 `citations`**：前端点不开溯源、评测没法断言"这条回答引对了没有"

这两列是**深度锚落在数据模型上的样子**，所以第 1 项（数据模型）时就要有，不能等"生成模块做完再加"。

# 6. 生成：提示词与引用溯源

## 6.1 提示词写在**代码里**，不落数据库

它是**行为规范**，应该走 code review + 版本控制。

如果放数据库，就会出现"某天有人在后台改了一句话，全站回答风格就变了"——而且**没有任何记录**。

（按租户定制提示词是另一个功能，将来再说。）

## 6.2 ★ 上下文编号必须与 `citations` 顺序**严格一致**

提示词里是：

```
【参考资料】
[1] 签收后 7 天内可无理由退货……
[2] 运费由买家承担……
```

模型回答里写 `[2]`，前端要能把它映射回**第二段原文**。

> **编号错位是"引用溯源"最隐蔽的失败方式**：
> 界面看起来有引用、也能点开，点进去却是**另一段文字**。
> 这比"没有引用"更糟 —— 它给了用户一个**假的核对能力**。

## 6.3 单条 chunk 会截断

chunk 本身已经切过，但极端情况（表格、代码块）可能很长。不截断会把 prompt 撑爆。

> 而**爆掉的表现是"模型截断/答非所问"，不是报错** —— 很难查。所以宁可主动截断并标注。

## 6.4 多轮历史只带最近几条

- 不带 → 追问（"那它的价格呢？"）完全无法回答
- 带太多 → token 成本线性上涨，且**离题的旧上下文会把模型带偏**

## 6.5 引用卡片上的分数要标**口径**

`citations[i].score_kind` 取值：`rerank` / `vector_cosine` / `fulltext_trgm`。

> 界面上写一个笼统的"相关度 0.62"会让人以为它们可比 ——
> 实际上 **0.62 的 rerank 分和 0.62 的余弦相似度完全是两回事**。

## 6.6 引用摘要只截断，**不做"智能摘要"**

引用卡片的用途是**让人能核对原文**。任何再加工都可能引入与原文不符的表述 —— 那就本末倒置了。

# 7. 数据模型：几个"现在就要定"的列

## 7.1 UUID 主键（而不是自增整数）

| 原因 | 说明 |
|---|---|
| 不泄露规模 | `/users/3` 一眼看出"我们只有 3 个用户" |
| 分库/合并不冲突 | 自增 ID 在跨库合并时必然撞车 |

**代价**：索引比整数大、随机写入对 B-tree 不如顺序写友好。当前规模下无所谓。

## 7.2 枚举用 **VARCHAR + CHECK**，不用 PG 原生 ENUM

原生 ENUM 加一个取值要 `ALTER TYPE ... ADD VALUE`，而这条语句**不能在事务里跑**（老 PG），Alembic 迁移默认又在事务里 —— 加个状态值就得写手工迁移。

VARCHAR + CHECK 改起来只是 drop/add 一个约束，代价小得多。

> ⚠️ **一个真实的坑**：SQLAlchemy 1.4 起 `Enum.create_constraint` **默认是 False** ——
> `native_enum=False` 单独用只会得到一个**裸 VARCHAR**，数据库层面**没有任何校验**。
> 名字里的 "VARCHAR + CHECK" 要成立，必须显式用 `enum_check()`（见 `app/db/base.py`）。
>
> 又：`create_constraint=True` 会让 Alembic autogenerate **生成两条重复的 CHECK**，所以还是显式写更清楚。

## 7.3 命名约定（`NAMING_CONVENTION`）一次定死

PostgreSQL 默认给约束起名（`users_email_key` 之类），但**名字依赖版本与建表顺序**。

Alembic 的 autogenerate 靠**约束名**比对差异 —— 名字不稳定，迁移就会误判"有变化"，生成一堆空迁移，甚至写错 DROP。

**一旦定死，永不修改。**

## 7.4 `citations` 用 JSONB，不另开一张表

引用是**消息的一部分**，从不单独查询，也不跨消息聚合 → 拆表只增加 JOIN 成本。

**什么时候该改**：要统计"哪些文档最常被引用"时。那时再迁移也不迟。

## 7.5 `chunk.embedding` 可空 —— 因为入库分两阶段

入库流程是 `解析 → 存文本 → 算向量 → 回填`。

如果把向量列设成 `NOT NULL`，就**逼着"文本+向量一次性写入"** —— 那样解析和向量化就没法分阶段重试了（向量化失败 = 整条记录回滚，重来一遍解析）。

## 7.6 `(tenant_id, content_hash)` 复合唯一

- 同一个文件被**同一个租户**传两次 → 挡住（不重复入库）
- 同一个文件被**不同租户**各传一次 → **允许**（各有各的知识库，不该互相挡）

`content_hash` 用 **sha256**，不用 md5（md5 已被证明可构造碰撞，不该出现在新代码里）。

## 7.7 关系属性一律 `lazy="raise"`

async 环境下"顺手访问关系属性"会触发**隐式 IO**，报错是 `MissingGreenlet` —— 极难懂。

设成 `raise` 让它在**写代码时**就炸，逼你显式 `selectinload`。

## 7.8 `expire_on_commit=False`

SQLAlchemy 默认 commit 后把所有属性标记为过期，下次访问**触发新查询** —— 在 async 里这会变成 `MissingGreenlet`，而且是在"明明刚提交完"的地方炸。

## 7.9 时间戳交给**数据库**（`server_default=func.now()`）

应用容器和数据库可能有时间偏差，多副本时更乱。统一由数据库打时间戳，**同一个库里的所有时间可比**。

# 8. 接口与流式：SSE 的坑

## 8.1 为什么用 SSE 而不是 WebSocket

| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务器→客户端） | 双向 |
| 协议 | 普通 HTTP | 需要升级握手 |
| 过 nginx | 就是 HTTP，配置简单 | 要额外配 upgrade 头 |

问答场景**只需要服务器往客户端推**（用户的问题用一个普通 POST 发出去就够了）。用 WebSocket 是杀鸡用牛刀，还引入一堆基础设施复杂度。

## 8.2 ★ 流开始之后，**错误改不了状态码**

HTTP 状态码在响应头里，**流一开始就发出去了**。之后出错只能：

> **在流里发一个 `error` 事件**，而不是把状态码改成 500。

所以错误分两类，处理方式完全不同：

| 何时出错 | 怎么处理 |
|---|---|
| **流开始前**（越权、参数不合法） | 正常 `HTTPException` → 404 / 422 |
| **流开始后**（模型 API 挂了） | 发 `error` 事件 |

## 8.3 落库放在 `finally`

客户端中途断开（关页面、切网络）会让生成器抛 `GeneratorExit`。如果落库写在最后一行，**那条回答就永远丢了** —— 而用户明明已经看到了半截。

## 8.4 `X-Accel-Buffering: no`

nginx 默认会**缓冲**上游响应。

不加这个头，SSE 会被攒成一坨再一次性发出去 —— **"流式"看起来完全没生效**。

> 更讨厌的是：**本地直连（不经过 nginx）时是好的**，只有部署后才出问题 → 很容易误判成前端 bug。

## 8.5 SSE 的 `data` 必须是**单行 JSON**

SSE 协议里**换行是字段分隔符**。回答里只要有换行，不转义就会把一帧拆成两帧，前端收到半截 JSON 直接解析失败。

`json.dumps` 默认把换行转成 `\n`，正好解决这件事。

## 8.6 用户消息**立刻落库**，助手消息**流完再落**

用户消息立刻存 → 即使用户马上刷新页面，提问记录也在。
助手消息要等流结束，因为那时才知道：引用了什么、是否拒答、耗时多少。

## 8.7 会话列表按 `updated_at` 排序，所以要**显式碰一下会话**

助手消息落库**不会**自动更新 `conversations.updated_at`（那是另一张表）。

不碰它的话，"刚聊过的会话"不会浮到列表最上面 —— 用起来非常别扭。

（用 UPDATE 语句而不是改 ORM 属性：属性赋同一个值 SQLAlchemy 会认为"没变"，于是不发 UPDATE，`onupdate` 也就不会触发。）

# 9. 工程约定：那些看起来多余的决定

## 9.1 连接池按 2C2G 调小

`pool_size=5, max_overflow=5`。池子开太大**不会让应用更快**，只会在数据库那头堆出更多空闲连接吃内存。

`pool_pre_ping=True`：连接被中间设备悄悄掐断时，池里的死连接会导致"第一次请求必失败"。

## 9.2 模型客户端**不用厂商 SDK**，只用 httpx

目的是让"换供应商"退化成**改 `.env`**，而不是改代码。

代价是每个接口的请求体要自己拼 —— 但只有三个（对话 / embedding / rerank），且都很短。

> 三个客户端的**形状不一样**：对话和 embedding 是 OpenAI 兼容，rerank **不是**标准的一部分（这里按阿里云百炼的 DashScope 形状）。
> **硬凑一个"统一接口"只会把差异藏起来**，等换供应商时更痛。

## 9.3 模型客户端**构造时注入**

两个理由：一是不用厂商 SDK；二是**测试必须能塞假实现** —— 否则跑一次测试就要真花钱（`tests/test_chat_api.py` 里的 `FakeChat` / `FakeEmbedder`）。

## 9.4 测试里**绝不真调模型 API**

烧钱 + 结果不稳定 + 评测失真。一律 mock / 回放 / 缓存。

## 9.5 每个测试**自建数据库引擎**，且用 `NullPool`

pytest-asyncio **每个测试函数一个新事件循环**，而 asyncpg 连接**绑定事件循环**。

共享一个进程级连接池 → 从第二个测试开始就会撞上：

```
Task got Future attached to a different loop
```

**这个报错完全看不出和"测试隔离"有关**，极易误判成业务代码 bug。

## 9.6 集成测试连不上库就 **SKIP**，不是 FAIL

没起 compose 的人不该看到一片红。但**绝不静默**：`pytest -q -rs` 会把跳过原因列出来。

## 9.7 `alembic.ini` 必须**纯 ASCII**

Alembic 用 `encoding="locale"` 读这个文件（`alembic/util/compat.py`）。中文 Windows 的 locale 是 **GBK** → 文件里的 UTF-8 中文注释**直接把它读崩**，**在连数据库之前**就失败。

> ⚠️ Linux（C.UTF-8）上同样内容完全正常 ⇒ **只在开发机复现，服务器上永远看不到**。

## 9.8 autogenerate **管不了**的两件事（每次都要人工补）

1. 向量列会引用 `pgvector.sqlalchemy.vector.VECTOR` 但**不导入** → 跑起来 `NameError`
2. **不会**生成 `CREATE EXTENSION vector` → 建 `chunks` 表直接失败

## 9.9 镜像里必须带 `migrations/` 和 `alembic.ini`

否则容器里跑不了 `alembic upgrade head` —— 部署脚本会在"执行迁移"这一步莫名其妙地失败。

## 9.10 dev 与 prod 的**建库参数必须一致**

这次就是栽在这上面（§4.4）：如果只在 dev 修了 ctype，就会出现"本地全文检索好好的、部署上去中文一条搜不到"——**最难查的一类差异**。

## 9.11 全机统一 UTF-8（`PYTHONUTF8=1`）

**现象**：在 PowerShell 里跑 python 脚本，中文输出变成 `���Ĳ���` 这种乱码。

**原因**：两边编码对不上 —— **Python 的 stdout 是 `gbk`**（中文 Windows 的 locale 是 cp936），
而 **PowerShell 的 `[Console]::OutputEncoding` 是 `utf-8`**。于是 GBK 字节被当 UTF-8 解读。

**为什么不在脚本里改 `print`**：

> 这是**环境**不一致，不是某个脚本的 bug。
> 每个脚本各改一遍 = 永远改不完，而且**新写的脚本还会再踩**。

**做法**：设用户级环境变量 `PYTHONUTF8=1`，让 Python **统一按 UTF-8** 输出。

```powershell
[Environment]::SetEnvironmentVariable('PYTHONUTF8','1','User')
```

**顺带的收益**：Python 的 UTF-8 模式会把 `open()` 的默认编码一并改成 UTF-8 ——
于是**消掉一整类**"用 GBK 读 UTF-8 文件"的坑。

> 本项目的 `alembic.ini` 就踩过**同源**的问题（见 §9.7）：Alembic 用 `encoding="locale"` 读它，
> 中文 Windows 上是 GBK，文件里的 UTF-8 中文注释直接把它读崩。
> 两个问题的根是同一件事：**这台机器上"默认编码"不是一个统一的值。**

**代价**：它会改变本机**所有** Python 项目的默认行为。
通常只会变好，但"改了机器上的全局设置"这件事应当**知情并同意** —— 这次是用户明确同意的。

> ⚠️ **一个容易白折腾半小时的点**：环境变量是**进程启动时的快照**。
> 设完之后，**已经跑着的终端 / 编辑器 / Agent 进程看不到它** ——
> 必须**新开进程**（新终端、重启 DSH）才生效。
> 在旧进程里跑，你会以为"我明明设了怎么还是乱码"。

## 9.12 SSE 在浏览器端**不能用 `EventSource`**

前端要消费 `POST /conversations/{id}/messages` 的事件流。直觉是"SSE 嘛，用 `EventSource`" —— **用不了**：

| | `EventSource` | 我们的接口 |
|---|---|---|
| 方法 | **只能 GET** | `POST` |
| 参数 | 只能进 URL | JSON body |

把提问塞进 query string 有三个问题：

1. **长度**：URL 在各层都有上限（nginx 默认 8 KB），而提问允许 2000 字
2. **会进日志**：nginx 的 `access_log` 默认记完整 URL → 用户的提问会**明文落到日志里**
3. **语义不对**：这是个**写操作**（会落库、会调模型花钱），用 GET 表达它违反 HTTP 语义

**做法**：`fetch` 拿到 `Response.body`（一个 `ReadableStream<Uint8Array>`），**自己按 SSE 规范切帧**。
代码在 `web\src\api\sse.ts` —— **零依赖、不碰 DOM**，所以能脱离浏览器单独验。

自己切帧有三个必须处理的坑：

| 坑 | 表现 | 处理 |
|---|---|---|
| **帧会被网络切开** | 一次 `read()` 可能只有半帧，也可能一次拿到三帧 | 攒缓冲区 → 切出完整帧 → 剩下的留着 |
| **多字节字符也会被切开** | 一个汉字 3 字节，切在中间就解成替换字符 `U+FFFD`（那个"问号方块"） | `TextDecoder` 必须带 `{ stream: true }` |
| **换行是字段分隔符，不是内容** | 按 `\n` 分帧会把一帧拆成两帧 | 用**空行**分帧；多个 `data:` 行用 `\n` 连接 |

**验证方式**（这件事**没法靠手点页面验** —— 帧被切开是偶发的）：
把一段真实的 SSE 字节流**按每一个可能的位置切开**（370 种），以及**逐字节喂**，
断言还原出的帧完全一致、且**没有出现替换字符 `U+FFFD`**。全部通过。

> ⚠️ 这个脚本是**一次性的**（在仓库外），**没有进 CI** —— 见 §10.3。

## 9.13 ★ 流式消息必须 `reactive()` 包一层（Vue 3 的响应式陷阱）

**现象**：把流式回答的占位消息 push 进 `ref<UiMessage[]>([])`，
然后攥着**那个对象的引用**往里追加文字 —— **界面一个字都不动**，控制台也不报错。

**原因**：`ref([])` 的深层响应式**不是**"push 进去就自动生效"，而是**读取时**才把元素换成 Proxy：

```
messages.value.push(raw)      // 数组里存的是**原始对象**
messages.value[i]             // 读的时候才 toReactive(raw) → 得到 Proxy
raw.content += text           // ⚠️ 改的是原始对象 → 绕过 Proxy → 不触发更新
```

**解法**：push 之前先 `reactive()`，这样手里的引用**本身就是** Proxy：

```ts
const pending = reactive<UiMessage>({ /* ... */ })
messages.value.push(pending)
pending.content += text        // ✅ 触发更新
```

**为什么值得单独写一条**：这个 bug 的特征是**"没有报错"**。
往"数据没更新"的方向排查，会一路查到 API、查到 SSE、查到后端 —— 而问题在最前面那 10 行。

## 9.14 中文输入法下，Enter 不是 Enter

**现象**：用拼音输入法打字，**候选词还没选完就被发出去了**。

**原因**：输入法激活期间按 Enter 是"**确认候选词**"，不是"提交"。浏览器照样派发 `keydown`。

**解法**：判 `event.isComposing`（组合输入中），再兜一个旧标记 `keyCode === 229`：

```ts
if (event.isComposing || event.keyCode === 229) return
if (event.key === 'Enter' && !event.shiftKey) { event.preventDefault(); send() }
```

**为什么值得单独写一条**：它**只在中文输入法下复现**。
用英文敲一百遍 `hello` 都不会出现 —— 很容易在演示现场第一次被人发现。

## 9.15 token 存 `localStorage`：一个**有代价**的选择

| 方案 | 刷新后 | XSS 能拿走？ | 需要后端配合 |
|---|---|---|---|
| **`localStorage`（现在选的）** | ✅ 还在 | ⚠️ **能**（JS 可读） | 不用 |
| 内存变量（`ref`） | ❌ 掉登录 | ✅ 拿不到 | 不用 |
| `httpOnly` Cookie | ✅ 还在 | ✅ 拿不到 | **要**（改鉴权方式 ＋ 防 CSRF） |

**为什么现在选 `localStorage`**：这是个**以演示为主**的前端，"刷新就掉登录"在演示时非常难看；
而且本前端的回答渲染**全篇不用 `v-html`**，XSS 面很小。

> ⚠️ **这句话是认真的，不是免责声明**：真上生产要换成 `httpOnly` Cookie。
> 它是一条**已知的、有条件的**技术债，不是"我们没想过"。

**顺带一个细节**：登录响应里的 `expires_in` 也存下来（算成**过期时刻**）。
token 过期后所有请求都会 401，靠"先撞一次 401 再跳登录"的体验是"点一下 → 卡一下 → 被踢出去"。
**本地就能判断的事，不要交给一次网络往返。**

## 9.16 前端**刻意不引入**的六样东西

| 不引入 | 为什么 |
|---|---|
| **Pinia** | 全应用只有"当前用户"一份全局状态。模块级 `ref` 天然单例、天然可 tree-shake；引 Pinia 要多学 store 定义 / `storeToRefs` / 插件 / devtools 接线 |
| **axios** | 只需要三件事（拼前缀、带 token、统一处理 401），`fetch` ＋ 40 行就够。axios 会带来拦截器 / 取消 / 转换器一整套概念 |
| **UI 组件库**（Element Plus 等） | 3 个页面、5 个组件。组件库还要学主题变量 / 按需引入 / 样式覆盖三层规则，而且**体积和版本升级都是负债**（这些静态资源要发给浏览器） |
| **CORS 中间件** | 开发走 `vite` proxy、生产走 nginx 反代 —— **两种情况都同源**。同源就不需要 CORS，也就少一类配置错误（和一类"允许来源写太宽"的风险） |
| **从 OpenAPI 生成 TS 类型** | 6 个端点，手抄 40 行比引入 codegen 链条便宜。**代价是真实的**：后端改字段前端不报错，只会在运行时变成 `undefined`（所以字段名是一个一个对着 `app/schemas/*.py` 抄的，不凭印象写） |
| **前端测试框架**（vitest 等） | 见下面的说明 —— **这条是当前的缺口** |

> ⚠️ **最后一条要说清楚**：SSE 解析器用一次性脚本验过了（§9.12），但**没有进 CI**。
> 也就是说，**将来改动 `sse.ts` 时没有任何东西会拦住你**。
> 补 vitest 的时机：**下一次要动 `sse.ts` 的时候** —— 那时先补测试再改。

## 9.17 会话**懒创建**：拿提问当标题

**问题**：如果"新建会话"按钮**立刻**在服务端建一条，会有两个后果：
用户点进去又退出来就留下一堆**空会话**；而且标题只能是"新会话" ——
列表页变成一排一模一样的字，**等于没有列表**。

**不选的解法**：给后端加 `PATCH /conversations/{id}` 改标题。
为了一个**展示效果**去扩后端接口 ＋ 补测试，不划算。

**做法**：`/conversations/new` 这条路由**不建会话**。用户**发出第一条提问**时才创建，
`title` 直接取提问的前 30 字：

```
点「新建会话」 → /conversations/new（本地空状态，服务端无记录）
      ↓ 用户输入并发送
创建会话（title = 提问）→ router.replace 到 /conversations/<真实 id> → 开始流式
```

**代价**（两处，都要记着）：

1. 多一条路由，且 `ChatView` 的 `id` 变成**可选**
2. 那次 `router.replace` 会让 `watch(() => props.id)` 触发一次 `load()` ——
   而此刻回答**正在流式接收**，重新拉消息会把**还没落库**的助手消息抹掉
   （后端要到流结束才落库，见 §8.6）。所以需要一个 `skipNextLoad` 标志跳过**那一次**

> 📌 **为什么这样是安全的**：vue-router 在两个路由记录指向**同一个组件**时会**复用实例**
> （不是重新挂载），所以流式状态不会丢。
> **2026-10-15 实测确认**：在 `/conversations/new` 提问后 URL 换成真实 id，消息与拒答横幅都在。

## 9.18 知识库入库（最小版）：几个不显然的取舍

**它为什么必须先做**：语料为空时**页面问什么都只能拒答** ——
引用溯源、逐字流式这些最该展示的东西**全是隐形的**。所以"最小入库"不是可选项，
它是让前面那些工作**能被看见**的前提。

**刻意不做的**（都属于 v1.0 第 3 项的 Web / 异步部分）：上传 UI · Redis 队列 ·
mini worker（`handle_job` 仍是 TODO）· PDF/docx 解析 · 增量更新。
就是一个离线脚本：读目录 → 清洗 → 切分 →（可选）嵌入 → 写库。`scripts\kb\ingest.py`。

### ① 每块前面带上**标题路径**

切分时把 `Dependencies > First Steps > Create a dependency` 写成每个 chunk 的前缀。

**为什么值**：光看 `Let's first focus on the dependency.` 根本不知道在讲什么。
加上路径之后，① 向量和关键词都变得**有指向**；② **引用摘要自己就说明了出处** ——
用户看到来源卡片时不必再点进去确认。代价是前缀占掉几十个字符（从 `chunk_size` 里扣）。

### ② 摘要必须"洗"成纯文本 —— 因为前端**不渲染 markdown**

`chunks.content` 被两处消费：喂给模型；以及 `make_snippet()` 截断后**直接显示在引用卡片上**。
而前端**全篇不用 `v-html`**（§9.15 里那条 XSS 论证正依赖这一点）。
所以 mkdocs 的 `**加粗**`、`{ #anchor }`、`{* ../../docs_src/... *}` 会**原样出现在用户面前**。

清洗**只对代码块之外的行**做：代码里的 `#` 是注释、`[]` 是下标，一律重写会把示例改坏。
唯一的内例外是**终端上色标签**（`<span style="color: green;">INFO</span>`）——
那不是代码，是文档站点渲染配色的痕迹，**连代码块一起清**。
（实测：不处理的话 240 块里有 **137** 个残留标签。）

### ③ 切点要对齐**两级**边界：先段落，后词

最初只对齐换行。结果切出 `me package that this module ...` 这种**从单词中间开始**的块 ——
原因是 **FastAPI 文档一个自然段就是一行**，常常超过 100 字，窗口里根本没有换行可对齐。

改成两级找切点：**先找换行（段落边界），找不到再找空格（词边界）**。
⚠️ 窗口的**起点和终点都要这样对齐**：只对齐终点的话，重叠窗口的起点照样落在半个词上。

### ④ `embedding` 可空 ⇒ "先落文本、后补向量"是一条**正经路径**

`chunks.embedding` 本来就是可空的（`knowledge.py`：入库分两阶段）。所以脚本提供 `--no-embed`：
**没有 embedding key 时照样能把语料和全文检索路跑通** ——
pg_trgm 在数据库里，**不需要任何 key**。

⚠️ 代价必须说清楚：补向量**只能 `--replace` 重跑**。不加的话文档会被判成"已入库过"直接跳过，
**向量永远补不上，而且不报错** —— 所以脚本在结束时会把这句话再打印一遍。

顺带：`--dry-run` 只打印切分结果、不连库不调模型。**调切分参数时先跑它**（否则每试一次都在花钱）。

### ⑤ 一个差点踩的坑：删文档不能用 ORM 级联

`Document.chunks` 是 `lazy="raise"`（§7.7）。`session.delete(document)` 会先去加载那个集合
→ **直接抛 `LazyLoadError`**。必须用 Core 的 `delete(Document).where(...)`，
让数据库的 `ON DELETE CASCADE` 干活。

> 📌 这条值得单独记：**两个各自正确的决定叠在一起变成了坑** ——
> `lazy="raise"` 是对的（§7.7），级联删除也是对的，
> 但它们的组合要求写代码的人**恰好知道**这件事。

### ⑥ 这一步的代价（如实记）

1. **它不是第 3 项。** 上传 UI / Redis 队列 / `handle_job`（worker）**一个都没做**。
   它只是"让检索链路有东西可检索"的最低限度。
2. **清洗与切分逻辑暂时住在 `scripts\kb\ingest.py`，按架构它们属于 `app\rag\`。**
   ⚠️ **迟早要搬。** 第 3 项做 worker 时**必须 `import` 它，不许复制一份** ——
   复制的那一刻，两条链路的切分规则就开始各自漂移了。
3. **`--no-embed` 是一把脚枪。** 它留下没有向量的 chunk，而补向量只能 `--replace` 重跑；
   忘了加就会**静默跳过**（文档被判"已入库过"），**向量永远补不上且不报错**。
   现在的防线只是"脚本在结束时把这句话打印一遍" —— **靠人记得看输出，不是好设计**。
   （更安全的做法是加一个 `--embed-only` 补齐模式，见 §10.3。）
4. **它验的是「机制」，不是「场景」。**
   ⚠️ **2026-10-15 更新**：中文端到端**已经验过了，是通的** ——
   但**通的原因必须说清楚**：靠的是**向量路跨语言**（实测中英余弦 **0.7885**），
   **不是全文路**（pg_trgm 在中文 query 撞英文 chunk 时切不出三元组）。
   所以这个"通"是**有条件的**：**embedding 一旦挂掉、降级成纯全文检索，中文就会塌。**
   → **中文语料（知识库 B）仍然必需**，只是理由从"能不能跑通"变成了"**全文路要能真正参与**"。

## 9.19 「详细程度」开关：同一份数据，两种呈现

**问题**：拒答时前端会列出检索到的来源，但后端落库的 `Answer.citations` 是**空数组**
（`schemas/chat.py` 的注释写着"拒答没有依据可引"）。
于是**同一句话，看直播和看回放长得不一样** —— 刷新之后来源消失。

**这不是 bug，是一条没对齐的边界。** SSE 那层想的是"让用户看到我找到了什么"，
落库那层想的是"拒答没有**引用**"。两句话都对，但**没人问过一句"那刷新之后呢"**。

**定案（2026-10-15）：把「存不存」和「显不显示」拆成两层。**

| 层 | 决定 |
|---|---|
| **数据层** | **永远存全** —— 拒答也落 `citations` ＋ `confidence` |
| **界面层** | **一个可切换的档位**（不是三套代码） |

| 档位 | 给谁 | 来源 | 分数（`精排分 0.466`） |
|---|---|---|---|
| **详细** | 开发 / 评测 / **面试官** | ✅ 显示 | ✅ 显示 |
| **简洁** | 终端用户 | ✅ 显示，但**换人话** | ❌ 隐藏 |

**为什么数据层必须"永远存全"**：

- **badcase 复盘都是事后做的。** 只改前端显示的话，**刷新后信息就断了**，"观察"无从谈起 ——
  开发期最需要的恰恰是"刷新后还在"。
- 拒答时那几条来源的含义是「**用户问 X，我召回了这些，但都不够好**」——
  这**正是优化检索的入口**。丢掉它，等于**每次拒答都在说"我不知道"，
  却不留下任何"我为什么不知道"的证据**。
- `confidence` 同理：不落库就永远答不出"它是在 0.33 拒的还是 0.59 拒的" → **阈值调优只能靠猜**。

**为什么界面层要分档，而不是一刀切**：

- ⚠️ **面试官不是"客户"** —— 他恰恰是**最想看内部信息**的人。
  "拒答时列出来源"对他是**加分项**：它证明你有 **badcase 归因**的意识。
- 对**终端用户**，要藏的其实**不是"来源"，而是"分数"**：
  「这条答案来自《退款政策》第 3 条」是**建立信任**的东西；
  「精排分 0.466」才是实现细节。

**代价**：多一个开关要维护；而且"同一份数据两种呈现"意味着**两种呈现都得有人验**。
（当前默认 **详细** —— 这是求职作品集，那是卖点。）

## 9.20 又一个 Vue 陷阱：`v-if` 里的**裸标识符**会被当常量折叠掉

**现象**：写了 `v-if="isDetailed"`（`isDetailed` 是个 `computed`），
**点切换按钮，界面纹丝不动，控制台也不报错。**

**定性**：去抓**编译产物** —— 模块里**只剩一句 `import`**，
既没有 `_unref(isDetailed)` 也没有 `_ctx.isDetailed`，**整个 `v-if` 消失了**。

**原因**：`@vue/compiler-sfc` 在**裸标识符当整个条件**时会做**常量折叠**。

> ⚠️ 同一个 `detailLevel` 写在**表达式**里（`detailLevel === 'x'`）就完全正常 ——
> 所以这个坑**只在"裸标识符当整个条件"时出现**，极难往编译器上联想。
> 2026-10-15 实测踩中：切换档位时"按钮高亮了、`localStorage` 也写对了，
> 但分数照旧显示"。

**解法**：**写成函数调用** `isDetailed()` —— 调用表达式不会被当成常量。

**为什么值得单独记**：它的症状和 §9.13（`reactive()` 陷阱）**一模一样** ——
"**数据变了界面不动，而且不报错**"。但根因一个在**运行时**、一个在**编译期**。
遇到这类症状，**先去看编译产物**，比在响应式上反复猜快得多。

| **没有向量索引（HNSW / IVFFlat）** | 当前 chunk 规模顺序扫描够快；建索引要调 `maintenance_work_mem`，且索引本身占内存 | chunk 数量上万时 |
| **embedding 维度写死在迁移里（1024）** | 维度是**元数据锁**，本来就该冻结（改维度 ＝ 必须全量重嵌入） | 换 embedding 模型时（必须全量重嵌入） |
| **前端没有 CI 测试** | 只用手一次性脚本验了 SSE 解析器（§9.12），没引 vitest —— 在这个规模下，引测试框架的成本还没盖过收益 | **下一次要动 `sse.ts` 的时候**（那时先补测试再改，别裸改） |
| **切分 / 清洗逻辑住在 `scripts\kb\ingest.py`** | 按架构它属于 `app\rag\`，但那边还没建；**"脚本先跑通"比"先摆对位置"重要** | **做 worker 时**：**先搬进 `app\rag\` 再 `import`**，**不许复制一份** —— 复制的那一刻，两条链路的切分规则就开始各自漂移 |
| **`--no-embed` 会留下没有向量的 chunk** | 补向量只能 `--replace` 重跑；忘了加就**静默跳过**（文档被判"已入库过"），**向量永远补不上且不报错**。现在的防线只是"脚本结束时打印一句提醒" | 拿到 key 后立刻 `--replace`；或加一个比 `--replace` 安全的 **`--embed-only`** 补齐模式 |
| **`citations` 字段混装两种含义** | 成功回答时它是"**引用**"；拒答时（§9.19 决定落库后）它是"**检索候选，但没有被引用**"。**字段名会撒谎** | 要做干净就得拆开（加 `retrieved` 字段，或给每条标 `used: bool`）。**当前不值得**，但要知道它是个将就 |
