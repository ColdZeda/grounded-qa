# 1. 全貌：一次提问经过哪些环节

```
用户提问
  │
  ├─① 鉴权        Bearer token → 解出 user + tenant
  │
  ├─② 取会话      租户 + 用户双重限定；取不到 → 404
  │
  ├─③ 存提问      用户消息**立刻落库**（刷新页面不丢）
  │
  ├─④ 两路检索    ┌─ 全文路：pg_trgm word_similarity（擅长精确串/型号/错误码）
  │              └─ 向量路：pgvector 余弦距离（擅长语义相近）
  │                   ↓
  │              RRF 融合（只按名次，不看分数）
  │
  ├─⑤ 精排        rerank 模型把 (query, doc) 成对打分 → 重排
  │
  ├─⑥ 判拒答      ★ 证据不够？→ 直接返回固定文案，**根本不调对话模型**
  │
  ├─⑦ 生成        组装提示词（编号引用）→ 流式生成 → SSE 逐段下发
  │
  └─⑧ 落库        回答 + 引用 + 拒答标记 + 耗时
```

**两个刻意的顺序**：

- **④ 在 ⑤ 之前**：先用便宜的方式把候选缩到 20 条，再花钱精排。反过来是拿钱换时间，不划算。
- **⑥ 在 ⑦ 之前**：拒答是**确定性代码**的判断，不是模型的自由发挥。详见 §5。

# 2. 多租户：隔离是怎么"焊死"的

## 2.1 为什么不能靠"记得写 `WHERE tenant_id = ?`"

多租户系统最经典的翻车方式就一句话：**某个查询忘了加租户条件**。

它危险在于：
- **不会报错** —— 接口 200，数据也"对"，只是看到了别人的
- **code review 挡不住** —— 人会忘、新人更会忘、急着上线时最容易忘
- **测试常常测不出来** —— 见下面 2.3

所以这里换了个思路：**不靠自觉，靠结构**。

## 2.2 三道防线

**第一道：表必须带 `tenant_id`（编译期级别的约束）**

`app/db/base.py` 的 `TenantMixin`：继承它 = 自动获得 `tenant_id` 外键 + 索引。

更进一步，有一条**元测试**（`tests/test_tenant_isolation.py`）：

```python
# 所有业务表都必须有 tenant_id，例外只有 tenants 自己
assert missing == []
```

将来谁加了一张新表却忘了继承 Mixin，**测试当场变红**。

**第二道：查询必须经过仓储层**

`app/db/repository.py` 的 `TenantScopedRepository` 把 `tenant_id` 条件**焊进查询构造**：

```python
# ❌ 反面教材：只按主键查，不带任何租户条件
conversation = await session.get(Conversation, conversation_id)

# ✅ 正确：条件在 repo 内部就注入了，你没有"忘记加"这个选项
repo = TenantScopedRepository(session, tenant_id=user.tenant_id, model=Conversation)
conversation = await repo.get(conversation_id)   # 跨租户必然返回 None
```

如果传进去的模型没有 `tenant_id` 列，**直接抛异常**（`MissingTenantColumnError`）——宁可启动就炸，也别带着漏洞跑。

**第三道：写入侧不给"自己选租户"的机会**

```python
repo.build(tenant_id=...)   # ← 直接 ValueError
```

写接口如果能"自己指定归属"，那隔离就退化成了输入校验 —— 早晚出事。

## 2.3 越权测试：为什么"成员 A 读成员 B"是个假测试

大多数项目会这么写越权测试：

> 普通成员 A 去读成员 B 的会话 → 期望 404 ✅

**这个测试是假的。** 因为就算**租户条件完全没写**，代码里的 `user_id` 过滤也会挡住 A —— 测试照样绿，漏洞照样在。

所以这里的测试设计是：**让攻击者是另一个租户的管理员**。

```python
async def test_admin_of_another_tenant_gets_404_not_someone_elses_data(...):
    # 租户 B 的管理员，拿租户 A 的会话 id 去查 → 必须 404
```

管理员本来就能看本租户**所有人**的数据，所以"只看自己的"这条规则**帮不上忙** —— **只剩租户过滤能挡住他**。漏写租户条件 → 这条必红。

## 2.4 隔离是**两层**的

| 层 | 规则 |
|---|---|
| 租户之间 | 谁都别想跨过去（包括管理员） |
| 租户内部按用户 | 普通成员只看得到自己的会话；**管理员能看本租户所有人的** |

> **"管理员"是「租户内的管理员」，不是超级管理员。**
> 跨租户的运营动作**没有 API**，只能手工做 —— 这不是遗漏，是**故意不给入口**：
> 多租户里最危险的 bug 就是"某个 admin 接口忘了限定租户"，不给它入口就少一类漏洞。

## 2.5 越权为什么返回 **404** 而不是 403

| 返回 | 泄露的信息 |
|---|---|
| `403` | "**这条数据存在**，只是不给你看" → 攻击者可以**枚举**出有效 id |
| `404` | 什么都不透露 ✅ |

只有一种情况给 403：**已经登录了，但角色权限不够**（比如普通成员调管理端）—— 这时"存在性"不是秘密。

# 3. 鉴权：登录这件事的细节

> ⚠️ **标题原先写的是"六个细节"，而实际有 `§3.1`–`§3.8` 八条**（2026-10-16 发现）。
> 修法是**把数字删掉**，不是改成"八个" —— `AGENTS §4` 早就记过这个教训：
> **写进标题的条数要在几处手工同步，必然漂移**。改了"八"，下次加 `§3.9` 又会漂。

## 3.1 为什么用 bcrypt 而不是 argon2

argon2 理论上更强，但它依赖 C 扩展 `argon2-cffi-bindings`；**Python 3.13 上不保证有预编译 wheel**，没有就得现场编译 —— CI 变慢、容器构建可能直接失败。

bcrypt 提供 **abi3 wheel**（cp39+ 通用），3.13 上直接装。

> **取舍原则**：在这个项目里，**"装得上、可复现" 优先于 "理论强度更高"**。
> 一个装不上的更强算法，实际安全性是 0。

## 3.2 bcrypt 的 72 字节上限：**拒绝**，不静默截断

bcrypt 只取密码的前 72 字节，**超出部分被悄悄丢掉**。后果：

```
"a"×72 + "X"  和  "a"×72 + "Y"  被当成同一个密码
```

用户以为自己设了更长的密码，其实后半截根本没参与。所以这里**直接报错**，而不是"悄悄帮你截断"。

## 3.3 bcrypt 必须丢进线程池

bcrypt 是 **CPU 密集**的（这正是它抗暴力破解的原因，cost=12 大约 100~250ms）。

如果在 `async def` 路由里**直接调它**，它会把**整个事件循环**卡住 —— 表现为"有人在登录，所有其他请求一起变慢"。所以：

```python
password_ok = await run_in_threadpool(verify_password, form.password, hashed)
```

## 3.4 用户不存在时，也要跑一次哈希（**时间抹平**）

如果"用户不存在"直接返回，而"密码错"要跑 100ms 的 bcrypt，那么**响应时间本身就泄露了"这个邮箱注册过没有"**。

攻击者可以先枚举出有效邮箱，再针对性爆破。做法：用户不存在时也拿一个**假的哈希**跑一次校验。

## 3.5 "密码错"和"用户不存在"必须返回**完全相同**的响应

不只是都返 401 —— **状态码、响应体、响应头**都要一样。测试里直接断言：

```python
assert wrong_password.json() == unknown_email.json()
```

## 3.6 JWT 里带 `tid`，但每个请求**仍然回库核对**

token 里存了 `tid`（租户 id），但 `get_current_user` 每次都会：

1. 按 `sub` 回库查用户
2. 查用户 `is_active` **和** 租户 `is_active`（运营侧的一键止血）
3. **核对 `token.tid == user.tenant_id`**

第 3 步平时是冗余的 —— **冗余的那一份就是用来发现不一致的**：万一某天要做"用户换租户"，旧 token 里还带着旧租户 id，不核对就会出现"人已经不在这个租户了，token 还能读它的数据"。

## 3.7 生产环境不许用开发默认密钥启动

`config.py` 里有个 `model_validator`：`APP_ENV != dev` 时，如果 `JWT_SECRET` 还是默认值、或长度 < 32 字节，**直接拒绝启动**。

> 这类校验必须"启动就炸"。等跑到某个请求才发现，意味着**它已经上线了** ——
> 而公网上一个 `dev-only-...` 的密钥等于任何人都能伪造管理员身份。
>
> ⚠️ **代价要说清楚**：如果部署时忘了把 `APP_ENV` 改成 `prod`，这道闸**不会**拦你。
> 它防的是"知道要上生产但忘了换密钥"，不是"忘了设 APP_ENV"。

## 3.8 一个刻意的简化：邮箱**全局唯一**

含义是「一个邮箱只属于一个租户」—— 跟多数 SaaS 一样（一个账号 → 一个工作区）。

- **好处**：登录只需邮箱，不用先选租户（少一步交互、少一个越权面）
- **代价**：同一个人属于两家公司要开两个邮箱
- **将来要改的话**：去掉 `email` 的全局唯一约束 + 登录接口加 `tenant_slug`

# 4. 检索：为什么要两条路，以及 RRF

## 4.1 两条路的**失败模式不同**

| | 擅长 | 不擅长 |
|---|---|---|
| **向量检索** | 语义相近（"怎么重置密码" → "密码找回流程"） | **精确串**：型号、错误码、专有名词 |
| **全文检索** | 精确串（"报错 E1024"、"X200 保修期"） | 换个说法就找不到 |

而客服场景里**恰好大量是后者**（用户直接复制错误码来问）。所以两条路不是"保险起见"，而是**互补**。

## 4.2 RRF：只用**名次**，不用分数

公式：`score(d) = Σ 1 / (k + rank_i(d))`，`rank` 从 1 开始。

**为什么不能直接加权求和？** 因为两种分数**量纲根本不同**：

- 向量：余弦相似度，0~1，反映语义距离
- 全文：`word_similarity`，0~1，反映字符串重合

两个都叫"0~1"，但一个是"意思像不像"，一个是"字面像不像"。给它们各配一个权重相加，**权重就是拍脑袋**。

RRF 的价值在于：**它把两者变成同一个尺度**（都是"排第几"），于是不需要任何权重。

| 细节 | 为什么 |
|---|---|
| `k = 60` | 它来自原论文。作用是**压平头部**：`k` 很小时（如 1），第 1 名和第 2 名差一倍（1/1 vs 1/2），融合几乎退化成"看第一路"。`k=60` 让前几名差距变小，**多路的一致性**才真正起作用 |
| 只被一路命中的文档**照样得分** | "向量路第 1 名"本身就是强信号，不该因为全文路没召回它就归零 |

## 4.3 `word_similarity` 而不是 `similarity`

两者都是 `pg_trgm` 的，但语义不同：

- `similarity(a, b)`：**整体**相似度。拿 10 个字的提问去比 800 字的 chunk，整体相似度必然很低（分母是长文本）→ 阈值怎么调都召回不出来
- `word_similarity(query, text)`：**"query 有多像 text 里的某一小段"** ← 这正是"短问句 vs 长文档"要的东西

## 4.4 ⚠️ 一个差点让全文检索**完全失效**的坑

`pg_trgm` 按数据库的 **ctype** 决定"什么字符算词"。实测：

| `datctype` | `show_trgm('退款政策')` | `word_similarity` |
|---|---|---|
| `C` | **`{}` 空集** | **0**（永远） |
| `C.UTF-8` | 5 个三元组 | **0.4** ✅ |

**`C` 下中文不算字母 → 一个三元组都切不出来。**

它危险的地方不是"质量差一点"，而是：

> **全文那一路永远召回不出任何东西，而系统不报错、状态码 200** ——
> 看起来就像"知识库里确实没有"。不做实测根本发现不了。

**已处置**：① dev + prod 建库参数都用 `--lc-collate=C.UTF-8 --lc-ctype=C.UTF-8`（**两边必须一致**，否则会出现"本地好好的、部署上去中文一条搜不到"）；② 加了**启动自检**（`app/db/checks.py`），切不出三元组就大声告警。

## 4.5 全文路的阈值刻意设得很低（0.05）

这一步**只做粗筛**，真正的排序与取舍交给 RRF + rerank。

把粗筛阈值调高 = **在检索早期就把可能正确的答案丢掉**，后面再也救不回来。

## 4.6 一个**已知的不完美**：全文路吃不到索引

查询用的是 `word_similarity() >= 阈值` 的**函数形式**，而 `pg_trgm` 的 GIN 索引只加速**算子形式**（`%`、`%>`、`ILIKE`）。

所以：**索引吃不到 → 每次全表算一遍。**

- **为什么还这么做**：算子形式依赖**会话级**阈值 `pg_trgm.word_similarity_threshold`，连接是池化的，会话状态容易串味；函数 + 显式阈值是**确定性**的、可测的
- **为什么现在可以接受**：`cpu 2 核 / 知识库规模小`，几千条 chunk 全表算是毫秒级
- **什么时候必须改**：知识库上万条以后。改法写在 `migrations/versions/…_enable_pg_trgm_….py` 的注释里（**两件事必须一起做**：加 GIN 索引 + 改查询为算子形式，并用 `set_config(..., is_local=true)` 设阈值）

> 📌 **所以这里**没有**建那个 GIN 索引** —— 建了也用不上，白白增加每次写入 chunk 的开销。
> "知道它不 scale、也知道怎么改，但**现在不做**" 和 "不知道有这回事" 是两码事。

## 4.7 ★ 「混合检索到底有没有用」—— **只有中文语料能回答**（2026-10-16）

**要被回答的问题**（面试必问的一句）：

> "你为什么要用混合检索？比**纯向量**好多少？"

**天真做法**：拿知识库 A（FastAPI 官方文档，**英文**）跑一组消融 ——
纯向量 / 纯全文 / 混合，三组比一比，出个数字。

**这么做的结果是：三组几乎一样，什么都测不出来。**
原因藏在 §4.4 那张表的**另一面**：

| | 知识库 A（**英文**语料） | 知识库 B（**中文**语料） |
|---|---|---|
| **中文**提问 → 全文路 | `pg_trgm` 切出来的是**中文** trigram，而 chunk 里全是英文 → **字符串层面重合为零 → 一条都召回不出来** | 中文 trigram 撞中文 chunk → **正常工作**（`word_similarity` 实测 **0.4**） |
| 于是消融测到的是 | 只有**向量路**在干活 → "混合" ≈ "纯向量" | **两条路都在干活** → 混合 vs 纯向量**才有差值可测** |

> ⚠️ **这跟 §4.4 的坑不是一回事，别混淆**：
> · §4.4 是 **ctype 配错**，中文**切不出**三元组 —— 那是 **bug，已修**；
> · 这里是 ctype **正确**、中文**也切得出** —— 但**查询与文档不同语言**，
>   在字符串层面就重合不了。**修不了，也不需要修。**
>
> 它说明的只是：**哪种语料能回答哪个问题。**

**结论与代价**：

- 「混合检索比纯向量好多少」**在 A 库上无法回答** ——
  不是"数据不好看"，而是**实验设计上就测不到**。
  硬要拿它当成绩，会得出"混合检索没什么用"的**错误结论**
  （真相是：**全文路根本没参与**）。
- 所以 **v4 起把「检索消融」定成 B 库的专属实验**（`plan\PROJECT-PLAN.md` §7.3）。
  ⚠️ 代价：要给检索层**新增两个开关**（`fulltext_enabled` / `vector_enabled`）——
  今天是**硬连**的，`config.py` 里只有 `rerank_enabled`。
- 📌 **它值得做的关键原因**：消融**只跑检索层、不调生成模型 ⟹ 零 token 成本**。
  同一条题集换个开关跑三遍而已。
- ✅ **顺带一条已于 2026-10-17 收口的事**（原先是"将就"）：阈值现已**分两套**（rerank / 余弦），实测与选值见 §9.25；这里留一句结论：`answer_min_score` 只有**一套**时，
  却既要跟 rerank 分数比、又要在 rerank 不可用时跟**向量余弦**比 ——
  两者分布不同。见 **§10.3**。

# 5. 精排与拒答：幻觉治理的核心

## 5.1 embedding 和 rerank **不能互相替代**

| | 结构 | 何时算 | 能干什么 |
|---|---|---|---|
| **embedding** | **双塔**：query 和 doc **分别**编码，彼此不见面 | **离线**预计算 doc 向量 | 快速从海量文档里"捞"出候选 |
| **rerank** | **交叉编码**：把 (query, doc) **拼在一起**过一遍模型 | **在线**，每个候选算一次 | 精细判断"这两条到底有多相关" |

因为双塔里 query 和 doc **从没见过面**，它给不出比向量检索更细的排序。

> **所以"用 embedding 模型当 rerank"是无效的**（同模型更没意义：排序完全一样）。
> 但**同一把 Key / 同一家供应商**是完全可以的 —— 那是账号，不是模型。

## 5.2 ★ 拒答必须在**调模型之前**由确定性代码决定

这是整份文档里最重要的一条。

**天真做法**："在提示词里告诉模型 —— 如果资料不足就说不知道。"

**为什么不行**：
1. 模型天然倾向于给出一个**听起来合理**的答案（它的训练目标就是"接着往下写"）
2. 于是"拒答率"变成了**模型心情的副产品** —— 统计不出来、也没法优化
3. 拒答时还要付一次 token 钱
4. 那句"我不知道"还可能被模型**润色**成一段看似有依据的话

**我们的做法**：证据不够 → **直接返回固定文案，一次模型都不调**。

好处：
- 拒答率成了一个**真实、可优化、可回归测试**的指标
- 拒答不花钱
- 拒答文案永远不会被"润色"

测试里有一条锁死这个行为：`assert chat.calls == []`。

## 5.3 ★ 置信度阈值**绝不能**挂在 RRF 分数上

RRF 是**名次**的函数。库里只有一条毫不相关的内容时，它**照样排第一、照样拿到 `1/(60+1) ≈ 0.016`**。

拿它比阈值 = **永远不拒答**（因为任何命中都会有个非零分数）。

所以按情况分**四条**路（`pipeline.py` 的 `_should_refuse`）：

| 情况 | 结论 | 依据 |
|---|---|---|
| 一条都没检索到 | **拒答** | 没有任何证据，答什么都是编 |
| 有 **rerank** 分数 | 按 `ANSWER_MIN_SCORE` 判 | 交叉编码的分数是**校准过的相关性**，可以定阈值 |
| 只有**向量余弦**（没开 rerank ／ rerank 调用失败） | **按 `ANSWER_MIN_COSINE`（0.45）判** | 余弦至少有"相似"的语义，比 trgm 强。<br>✅ **2026-10-17 起用独立的阈值**（原先是拿 rerank 的 0.60 去比余弦，实测会误拒 19/25 —— 见 §9.25）。<br>⚠️ 但余弦本身分离度很差，所以这仍是**降级** —— 那个阈值是照 **rerank 分数**标的，两者分布不同（见 §10.3） |
| 只有 **trgm** 相似度（没 embedding 也没 rerank） | **不拒答** | trgm 那个数字**不是相关性语义**，拿它比阈值等于瞎判 |

> ⚠️ **2026-10-16 更正**：这张表原先只有三行，把后两种情况合并成"没有 rerank 分数 → 不拒答"——
> **那是错的**。`confidence is None` 才是不拒答；而 `vector_cosine` 分支**给得出 `confidence`**，
> 于是同一个阈值会被拿去比余弦。合并那一行会让读者以为"rerank 一挂就不判了"，
> 而真实行为是"**照样判，只是拿错了尺子**"—— 后者才是需要知道的事。

**最后一条**看着"不够安全"，但**用无意义的数字假装判断过**才是真的危险：它会给你一个虚假的安全感。

## 5.4 模型/依赖挂了要**降级**，不要跟着挂

| 挂掉的组件 | 降级行为 |
|---|---|
| embedding | 退化成**纯全文检索**（召回差一些，但还能答） |
| rerank | 退化成 **RRF 顺序**（排序差一些，但还能答） |
| 对话模型 | 流里发 `error` 事件；**已经拿到的半截回答照样落库**（见 §8.3） |

> **可用性 > 功能齐全。** 一个"精排服务抖动就整个问答 500"的系统，不如一个"降级但一直能答"的系统。

## 5.5 拒答与引用为什么必须**落库**

`messages` 表上有两列：`refused`（布尔）和 `citations`（JSONB）。

- **不落 `refused`**：拒答率统计不出来 → 幻觉治理**没有仪表盘**
- **不落 `citations`**：前端点不开溯源、评测没法断言"这条回答引对了没有"

这两列是**深度锚落在数据模型上的样子**，所以第 1 项（数据模型）时就要有，不能等"生成模块做完再加"。

# 6. 生成：提示词与引用溯源

## 6.1 提示词写在**代码里**，不落数据库

它是**行为规范**，应该走 code review + 版本控制。

如果放数据库，就会出现"某天有人在后台改了一句话，全站回答风格就变了"——而且**没有任何记录**。

（按租户定制提示词是另一个功能，将来再说。）

## 6.2 ★ 上下文编号必须与 `citations` 顺序**严格一致**

提示词里是：

```
【参考资料】
[1] 签收后 7 天内可无理由退货……
[2] 运费由买家承担……
```

模型回答里写 `[2]`，前端要能把它映射回**第二段原文**。

> **编号错位是"引用溯源"最隐蔽的失败方式**：
> 界面看起来有引用、也能点开，点进去却是**另一段文字**。
> 这比"没有引用"更糟 —— 它给了用户一个**假的核对能力**。

## 6.3 单条 chunk 会截断

chunk 本身已经切过，但极端情况（表格、代码块）可能很长。不截断会把 prompt 撑爆。

> 而**爆掉的表现是"模型截断/答非所问"，不是报错** —— 很难查。所以宁可主动截断并标注。

## 6.4 多轮历史只带最近几条

- 不带 → 追问（"那它的价格呢？"）完全无法回答
- 带太多 → token 成本线性上涨，且**离题的旧上下文会把模型带偏**

## 6.5 引用卡片上的分数要标**口径**

`citations[i].score_kind` 取值：`rerank` / `vector_cosine` / `fulltext_trgm`。

> 界面上写一个笼统的"相关度 0.62"会让人以为它们可比 ——
> 实际上 **0.62 的 rerank 分和 0.62 的余弦相似度完全是两回事**。

## 6.6 引用摘要只截断，**不做"智能摘要"**

引用卡片的用途是**让人能核对原文**。任何再加工都可能引入与原文不符的表述 —— 那就本末倒置了。

# 7. 数据模型：几个"现在就要定"的列

## 7.1 UUID 主键（而不是自增整数）

| 原因 | 说明 |
|---|---|
| 不泄露规模 | `/users/3` 一眼看出"我们只有 3 个用户" |
| 分库/合并不冲突 | 自增 ID 在跨库合并时必然撞车 |

**代价**：索引比整数大、随机写入对 B-tree 不如顺序写友好。当前规模下无所谓。

## 7.2 枚举用 **VARCHAR + CHECK**，不用 PG 原生 ENUM

原生 ENUM 加一个取值要 `ALTER TYPE ... ADD VALUE`，而这条语句**不能在事务里跑**（老 PG），Alembic 迁移默认又在事务里 —— 加个状态值就得写手工迁移。

VARCHAR + CHECK 改起来只是 drop/add 一个约束，代价小得多。

> ⚠️ **一个真实的坑**：SQLAlchemy 1.4 起 `Enum.create_constraint` **默认是 False** ——
> `native_enum=False` 单独用只会得到一个**裸 VARCHAR**，数据库层面**没有任何校验**。
> 名字里的 "VARCHAR + CHECK" 要成立，必须显式用 `enum_check()`（见 `app/db/base.py`）。
>
> 又：`create_constraint=True` 会让 Alembic autogenerate **生成两条重复的 CHECK**，所以还是显式写更清楚。

## 7.3 命名约定（`NAMING_CONVENTION`）一次定死

PostgreSQL 默认给约束起名（`users_email_key` 之类），但**名字依赖版本与建表顺序**。

Alembic 的 autogenerate 靠**约束名**比对差异 —— 名字不稳定，迁移就会误判"有变化"，生成一堆空迁移，甚至写错 DROP。

**一旦定死，永不修改。**

## 7.4 `citations` 用 JSONB，不另开一张表

引用是**消息的一部分**，从不单独查询，也不跨消息聚合 → 拆表只增加 JOIN 成本。

**什么时候该改**：要统计"哪些文档最常被引用"时。那时再迁移也不迟。

## 7.5 `chunk.embedding` 可空 —— 因为入库分两阶段

入库流程是 `解析 → 存文本 → 算向量 → 回填`。

如果把向量列设成 `NOT NULL`，就**逼着"文本+向量一次性写入"** —— 那样解析和向量化就没法分阶段重试了（向量化失败 = 整条记录回滚，重来一遍解析）。

## 7.6 `(tenant_id, content_hash)` 复合唯一

- 同一个文件被**同一个租户**传两次 → 挡住（不重复入库）
- 同一个文件被**不同租户**各传一次 → **允许**（各有各的知识库，不该互相挡）

`content_hash` 用 **sha256**，不用 md5（md5 已被证明可构造碰撞，不该出现在新代码里）。

## 7.7 关系属性一律 `lazy="raise"`

async 环境下"顺手访问关系属性"会触发**隐式 IO**，报错是 `MissingGreenlet` —— 极难懂。

设成 `raise` 让它在**写代码时**就炸，逼你显式 `selectinload`。

## 7.8 `expire_on_commit=False`

SQLAlchemy 默认 commit 后把所有属性标记为过期，下次访问**触发新查询** —— 在 async 里这会变成 `MissingGreenlet`，而且是在"明明刚提交完"的地方炸。

## 7.9 时间戳交给**数据库**（`server_default=func.now()`）

应用容器和数据库可能有时间偏差，多副本时更乱。统一由数据库打时间戳，**同一个库里的所有时间可比**。

# 8. 接口与流式：SSE 的坑

## 8.1 为什么用 SSE 而不是 WebSocket

| | SSE | WebSocket |
|---|---|---|
| 方向 | 单向（服务器→客户端） | 双向 |
| 协议 | 普通 HTTP | 需要升级握手 |
| 过 nginx | 就是 HTTP，配置简单 | 要额外配 upgrade 头 |

问答场景**只需要服务器往客户端推**（用户的问题用一个普通 POST 发出去就够了）。用 WebSocket 是杀鸡用牛刀，还引入一堆基础设施复杂度。

## 8.2 ★ 流开始之后，**错误改不了状态码**

HTTP 状态码在响应头里，**流一开始就发出去了**。之后出错只能：

> **在流里发一个 `error` 事件**，而不是把状态码改成 500。

所以错误分两类，处理方式完全不同：

| 何时出错 | 怎么处理 |
|---|---|
| **流开始前**（越权、参数不合法） | 正常 `HTTPException` → 404 / 422 |
| **流开始后**（模型 API 挂了） | 发 `error` 事件 |

## 8.3 落库放在 `finally`

客户端中途断开（关页面、切网络）会让生成器抛 `GeneratorExit`。如果落库写在最后一行，**那条回答就永远丢了** —— 而用户明明已经看到了半截。

## 8.4 `X-Accel-Buffering: no`

nginx 默认会**缓冲**上游响应。

不加这个头，SSE 会被攒成一坨再一次性发出去 —— **"流式"看起来完全没生效**。

> 更讨厌的是：**本地直连（不经过 nginx）时是好的**，只有部署后才出问题 → 很容易误判成前端 bug。

## 8.5 SSE 的 `data` 必须是**单行 JSON**

SSE 协议里**换行是字段分隔符**。回答里只要有换行，不转义就会把一帧拆成两帧，前端收到半截 JSON 直接解析失败。

`json.dumps` 默认把换行转成 `\n`，正好解决这件事。

## 8.6 用户消息**立刻落库**，助手消息**流完再落**

用户消息立刻存 → 即使用户马上刷新页面，提问记录也在。
助手消息要等流结束，因为那时才知道：引用了什么、是否拒答、耗时多少。

## 8.7 会话列表按 `updated_at` 排序，所以要**显式碰一下会话**

助手消息落库**不会**自动更新 `conversations.updated_at`（那是另一张表）。

不碰它的话，"刚聊过的会话"不会浮到列表最上面 —— 用起来非常别扭。

（用 UPDATE 语句而不是改 ORM 属性：属性赋同一个值 SQLAlchemy 会认为"没变"，于是不发 UPDATE，`onupdate` 也就不会触发。）

## 9.1 连接池按 2C2G 调小

`pool_size=5, max_overflow=5`。池子开太大**不会让应用更快**，只会在数据库那头堆出更多空闲连接吃内存。

`pool_pre_ping=True`：连接被中间设备悄悄掐断时，池里的死连接会导致"第一次请求必失败"。

## 9.2 模型客户端**不用厂商 SDK**，只用 httpx

目的是让"换供应商"退化成**改 `.env`**，而不是改代码。

代价是每个接口的请求体要自己拼 —— 但只有三个（对话 / embedding / rerank），且都很短。

> 三个客户端的**形状不一样**：对话和 embedding 是 OpenAI 兼容，rerank **不是**标准的一部分（这里按阿里云百炼的 DashScope 形状）。
> **硬凑一个"统一接口"只会把差异藏起来**，等换供应商时更痛。

## 9.3 模型客户端**构造时注入**

两个理由：一是不用厂商 SDK；二是**测试必须能塞假实现** —— 否则跑一次测试就要真花钱（`tests/test_chat_api.py` 里的 `FakeChat` / `FakeEmbedder`）。

## 9.4 测试里**绝不真调模型 API**

烧钱 + 结果不稳定 + 评测失真。一律 mock / 回放 / 缓存。

## 9.5 每个测试**自建数据库引擎**，且用 `NullPool`

pytest-asyncio **每个测试函数一个新事件循环**，而 asyncpg 连接**绑定事件循环**。

共享一个进程级连接池 → 从第二个测试开始就会撞上：

```
Task got Future attached to a different loop
```

**这个报错完全看不出和"测试隔离"有关**，极易误判成业务代码 bug。

## 9.6 集成测试连不上库就 **SKIP**，不是 FAIL

没起 compose 的人不该看到一片红。但**绝不静默**：`pytest -q -rs` 会把跳过原因列出来。

## 9.7 `alembic.ini` 必须**纯 ASCII**

Alembic 用 `encoding="locale"` 读这个文件（`alembic/util/compat.py`）。中文 Windows 的 locale 是 **GBK** → 文件里的 UTF-8 中文注释**直接把它读崩**，**在连数据库之前**就失败。

> ⚠️ Linux（C.UTF-8）上同样内容完全正常 ⇒ **只在开发机复现，服务器上永远看不到**。

## 9.8 autogenerate **管不了**的两件事（每次都要人工补）

1. 向量列会引用 `pgvector.sqlalchemy.vector.VECTOR` 但**不导入** → 跑起来 `NameError`
2. **不会**生成 `CREATE EXTENSION vector` → 建 `chunks` 表直接失败

## 9.9 镜像里必须带 `migrations/` 和 `alembic.ini`

否则容器里跑不了 `alembic upgrade head` —— 部署脚本会在"执行迁移"这一步莫名其妙地失败。

## 9.10 dev 与 prod 的**建库参数必须一致**

这次就是栽在这上面（§4.4）：如果只在 dev 修了 ctype，就会出现"本地全文检索好好的、部署上去中文一条搜不到"——**最难查的一类差异**。

## 9.11 全机统一 UTF-8（`PYTHONUTF8=1`）

**现象**：在 PowerShell 里跑 python 脚本，中文输出变成 `���Ĳ���` 这种乱码。

**原因**：两边编码对不上 —— **Python 的 stdout 是 `gbk`**（中文 Windows 的 locale 是 cp936），
而 **PowerShell 的 `[Console]::OutputEncoding` 是 `utf-8`**。于是 GBK 字节被当 UTF-8 解读。

**为什么不在脚本里改 `print`**：

> 这是**环境**不一致，不是某个脚本的 bug。
> 每个脚本各改一遍 = 永远改不完，而且**新写的脚本还会再踩**。

**做法**：设用户级环境变量 `PYTHONUTF8=1`，让 Python **统一按 UTF-8** 输出。

```powershell
[Environment]::SetEnvironmentVariable('PYTHONUTF8','1','User')
```

**顺带的收益**：Python 的 UTF-8 模式会把 `open()` 的默认编码一并改成 UTF-8 ——
于是**消掉一整类**"用 GBK 读 UTF-8 文件"的坑。

> 本项目的 `alembic.ini` 就踩过**同源**的问题（见 §9.7）：Alembic 用 `encoding="locale"` 读它，
> 中文 Windows 上是 GBK，文件里的 UTF-8 中文注释直接把它读崩。
> 两个问题的根是同一件事：**这台机器上"默认编码"不是一个统一的值。**

**代价**：它会改变本机**所有** Python 项目的默认行为。
通常只会变好，但"改了机器上的全局设置"这件事应当**知情并同意** —— 这次是用户明确同意的。

> ⚠️ **一个容易白折腾半小时的点**：环境变量是**进程启动时的快照**。
> 设完之后，**已经跑着的终端 / 编辑器 / Agent 进程看不到它** ——
> 必须**新开进程**（新终端、重启 DSH）才生效。
> 在旧进程里跑，你会以为"我明明设了怎么还是乱码"。

## 9.12 SSE 在浏览器端**不能用 `EventSource`**

前端要消费 `POST /conversations/{id}/messages` 的事件流。直觉是"SSE 嘛，用 `EventSource`" —— **用不了**：

| | `EventSource` | 我们的接口 |
|---|---|---|
| 方法 | **只能 GET** | `POST` |
| 参数 | 只能进 URL | JSON body |

把提问塞进 query string 有三个问题：

1. **长度**：URL 在各层都有上限（nginx 默认 8 KB），而提问允许 2000 字
2. **会进日志**：nginx 的 `access_log` 默认记完整 URL → 用户的提问会**明文落到日志里**
3. **语义不对**：这是个**写操作**（会落库、会调模型花钱），用 GET 表达它违反 HTTP 语义

**做法**：`fetch` 拿到 `Response.body`（一个 `ReadableStream<Uint8Array>`），**自己按 SSE 规范切帧**。
代码在 `web\src\api\sse.ts` —— **零依赖、不碰 DOM**，所以能脱离浏览器单独验。

自己切帧有三个必须处理的坑：

| 坑 | 表现 | 处理 |
|---|---|---|
| **帧会被网络切开** | 一次 `read()` 可能只有半帧，也可能一次拿到三帧 | 攒缓冲区 → 切出完整帧 → 剩下的留着 |
| **多字节字符也会被切开** | 一个汉字 3 字节，切在中间就解成替换字符 `U+FFFD`（那个"问号方块"） | `TextDecoder` 必须带 `{ stream: true }` |
| **换行是字段分隔符，不是内容** | 按 `\n` 分帧会把一帧拆成两帧 | 用**空行**分帧；多个 `data:` 行用 `\n` 连接 |

**验证方式**（这件事**没法靠手点页面验** —— 帧被切开是偶发的）：
把一段真实的 SSE 字节流**按每一个可能的位置切开**（370 种），以及**逐字节喂**，
断言还原出的帧完全一致、且**没有出现替换字符 `U+FFFD`**。全部通过。

> ⚠️ 这个脚本是**一次性的**（在仓库外），**没有进 CI** —— 见 §10.3。

## 9.13 ★ 流式消息必须 `reactive()` 包一层（Vue 3 的响应式陷阱）

**现象**：把流式回答的占位消息 push 进 `ref<UiMessage[]>([])`，
然后攥着**那个对象的引用**往里追加文字 —— **界面一个字都不动**，控制台也不报错。

**原因**：`ref([])` 的深层响应式**不是**"push 进去就自动生效"，而是**读取时**才把元素换成 Proxy：

```
messages.value.push(raw)      // 数组里存的是**原始对象**
messages.value[i]             // 读的时候才 toReactive(raw) → 得到 Proxy
raw.content += text           // ⚠️ 改的是原始对象 → 绕过 Proxy → 不触发更新
```

**解法**：push 之前先 `reactive()`，这样手里的引用**本身就是** Proxy：

```ts
const pending = reactive<UiMessage>({ /* ... */ })
messages.value.push(pending)
pending.content += text        // ✅ 触发更新
```

**为什么值得单独写一条**：这个 bug 的特征是**"没有报错"**。
往"数据没更新"的方向排查，会一路查到 API、查到 SSE、查到后端 —— 而问题在最前面那 10 行。

## 9.14 中文输入法下，Enter 不是 Enter

**现象**：用拼音输入法打字，**候选词还没选完就被发出去了**。

**原因**：输入法激活期间按 Enter 是"**确认候选词**"，不是"提交"。浏览器照样派发 `keydown`。

**解法**：判 `event.isComposing`（组合输入中），再兜一个旧标记 `keyCode === 229`：

```ts
if (event.isComposing || event.keyCode === 229) return
if (event.key === 'Enter' && !event.shiftKey) { event.preventDefault(); send() }
```

**为什么值得单独写一条**：它**只在中文输入法下复现**。
用英文敲一百遍 `hello` 都不会出现 —— 很容易在演示现场第一次被人发现。

## 9.15 token 存 `localStorage`：一个**有代价**的选择

| 方案 | 刷新后 | XSS 能拿走？ | 需要后端配合 |
|---|---|---|---|
| **`localStorage`（现在选的）** | ✅ 还在 | ⚠️ **能**（JS 可读） | 不用 |
| 内存变量（`ref`） | ❌ 掉登录 | ✅ 拿不到 | 不用 |
| `httpOnly` Cookie | ✅ 还在 | ✅ 拿不到 | **要**（改鉴权方式 ＋ 防 CSRF） |

**为什么现在选 `localStorage`**：这是个**以演示为主**的前端，"刷新就掉登录"在演示时非常难看；
而且本前端的回答渲染**全篇不用 `v-html`**，XSS 面很小。

> ⚠️ **这句话是认真的，不是免责声明**：真上生产要换成 `httpOnly` Cookie。
> 它是一条**已知的、有条件的**技术债，不是"我们没想过"。

**顺带一个细节**：登录响应里的 `expires_in` 也存下来（算成**过期时刻**）。
token 过期后所有请求都会 401，靠"先撞一次 401 再跳登录"的体验是"点一下 → 卡一下 → 被踢出去"。
**本地就能判断的事，不要交给一次网络往返。**

## 9.16 前端**刻意不引入**的六样东西

| 不引入 | 为什么 |
|---|---|
| **Pinia** | 全应用只有"当前用户"一份全局状态。模块级 `ref` 天然单例、天然可 tree-shake；引 Pinia 要多学 store 定义 / `storeToRefs` / 插件 / devtools 接线 |
| **axios** | 只需要三件事（拼前缀、带 token、统一处理 401），`fetch` ＋ 40 行就够。axios 会带来拦截器 / 取消 / 转换器一整套概念 |
| **UI 组件库**（Element Plus 等） | 3 个页面、5 个组件。组件库还要学主题变量 / 按需引入 / 样式覆盖三层规则，而且**体积和版本升级都是负债**（这些静态资源要发给浏览器） |
| **CORS 中间件** | 开发走 `vite` proxy、生产走 nginx 反代 —— **两种情况都同源**。同源就不需要 CORS，也就少一类配置错误（和一类"允许来源写太宽"的风险） |
| **从 OpenAPI 生成 TS 类型** | 6 个端点，手抄 40 行比引入 codegen 链条便宜。**代价是真实的**：后端改字段前端不报错，只会在运行时变成 `undefined`（所以字段名是一个一个对着 `app/schemas/*.py` 抄的，不凭印象写） |
| **前端测试框架**（vitest 等） | 见下面的说明 —— **这条是当前的缺口** |

> ⚠️ **最后一条要说清楚**：SSE 解析器用一次性脚本验过了（§9.12），但**没有进 CI**。
> 也就是说，**将来改动 `sse.ts` 时没有任何东西会拦住你**。
> 补 vitest 的时机：**下一次要动 `sse.ts` 的时候** —— 那时先补测试再改。

## 9.17 会话**懒创建**：拿提问当标题

**问题**：如果"新建会话"按钮**立刻**在服务端建一条，会有两个后果：
用户点进去又退出来就留下一堆**空会话**；而且标题只能是"新会话" ——
列表页变成一排一模一样的字，**等于没有列表**。

**不选的解法**：给后端加 `PATCH /conversations/{id}` 改标题。
为了一个**展示效果**去扩后端接口 ＋ 补测试，不划算。

**做法**：`/conversations/new` 这条路由**不建会话**。用户**发出第一条提问**时才创建，
`title` 直接取提问的前 30 字：

```
点「新建会话」 → /conversations/new（本地空状态，服务端无记录）
      ↓ 用户输入并发送
创建会话（title = 提问）→ router.replace 到 /conversations/<真实 id> → 开始流式
```

**代价**（两处，都要记着）：

1. 多一条路由，且 `ChatView` 的 `id` 变成**可选**
2. 那次 `router.replace` 会让 `watch(() => props.id)` 触发一次 `load()` ——
   而此刻回答**正在流式接收**，重新拉消息会把**还没落库**的助手消息抹掉
   （后端要到流结束才落库，见 §8.6）。所以需要一个 `skipNextLoad` 标志跳过**那一次**

> 📌 **为什么这样是安全的**：vue-router 在两个路由记录指向**同一个组件**时会**复用实例**
> （不是重新挂载），所以流式状态不会丢。
> **2026-10-15 实测确认**：在 `/conversations/new` 提问后 URL 换成真实 id，消息与拒答横幅都在。

## 9.18 知识库入库（最小版）：几个不显然的取舍

**它为什么必须先做**：语料为空时**页面问什么都只能拒答** ——
引用溯源、逐字流式这些最该展示的东西**全是隐形的**。所以"最小入库"不是可选项，
它是让前面那些工作**能被看见**的前提。

**刻意不做的**（都属于 v1.0 第 3 项的 Web / 异步部分）：上传 UI · Redis 队列 ·
mini worker · PDF/docx 解析 · 增量更新。
> ✅ **2026-10-17 已补齐前三样**（上传 UI ／ 队列 ／ `handle_job`），见 **§9.26**；
> **PDF/docx 与增量更新仍然不做**（理由在 §10.3）。
就是一个离线脚本：读目录 → 清洗 → 切分 →（可选）嵌入 → 写库。`scripts\kb\ingest.py`。

### ① 每块前面带上**标题路径**

切分时把 `Dependencies > First Steps > Create a dependency` 写成每个 chunk 的前缀。

**为什么值**：光看 `Let's first focus on the dependency.` 根本不知道在讲什么。
加上路径之后，① 向量和关键词都变得**有指向**；② **引用摘要自己就说明了出处** ——
用户看到来源卡片时不必再点进去确认。代价是前缀占掉几十个字符（从 `chunk_size` 里扣）。

### ② 摘要必须"洗"成纯文本 —— 因为前端**不渲染 markdown**

`chunks.content` 被两处消费：喂给模型；以及 `make_snippet()` 截断后**直接显示在引用卡片上**。
而前端**全篇不用 `v-html`**（§9.15 里那条 XSS 论证正依赖这一点）。
所以 mkdocs 的 `**加粗**`、`{ #anchor }`、`{* ../../docs_src/... *}` 会**原样出现在用户面前**。

清洗**只对代码块之外的行**做：代码里的 `#` 是注释、`[]` 是下标，一律重写会把示例改坏。
唯一的内例外是**终端上色标签**（`<span style="color: green;">INFO</span>`）——
那不是代码，是文档站点渲染配色的痕迹，**连代码块一起清**。
（实测：不处理的话 240 块里有 **137** 个残留标签。）

### ③ 切点要对齐**两级**边界：先段落，后词

最初只对齐换行。结果切出 `me package that this module ...` 这种**从单词中间开始**的块 ——
原因是 **FastAPI 文档一个自然段就是一行**，常常超过 100 字，窗口里根本没有换行可对齐。

改成两级找切点：**先找换行（段落边界），找不到再找空格（词边界）**。
⚠️ 窗口的**起点和终点都要这样对齐**：只对齐终点的话，重叠窗口的起点照样落在半个词上。

### ④ `embedding` 可空 ⇒ "先落文本、后补向量"是一条**正经路径**

`chunks.embedding` 本来就是可空的（`knowledge.py`：入库分两阶段）。所以脚本提供 `--no-embed`：
**没有 embedding key 时照样能把语料和全文检索路跑通** ——
pg_trgm 在数据库里，**不需要任何 key**。

⚠️ 代价必须说清楚：补向量**只能 `--replace` 重跑**。不加的话文档会被判成"已入库过"直接跳过，
**向量永远补不上，而且不报错** —— 所以脚本在结束时会把这句话再打印一遍。

顺带：`--dry-run` 只打印切分结果、不连库不调模型。**调切分参数时先跑它**（否则每试一次都在花钱）。

### ⑤ 一个差点踩的坑：删文档不能用 ORM 级联

`Document.chunks` 是 `lazy="raise"`（§7.7）。`session.delete(document)` 会先去加载那个集合
→ **直接抛 `LazyLoadError`**。必须用 Core 的 `delete(Document).where(...)`，
让数据库的 `ON DELETE CASCADE` 干活。

> 📌 这条值得单独记：**两个各自正确的决定叠在一起变成了坑** ——
> `lazy="raise"` 是对的（§7.7），级联删除也是对的，
> 但它们的组合要求写代码的人**恰好知道**这件事。

### ⑥ 这一步的代价（如实记）

1. **它不是第 3 项。** 上传 UI / Redis 队列 / `handle_job`（worker）**一个都没做**。
   它只是"让检索链路有东西可检索"的最低限度。
2. **清洗与切分逻辑暂时住在 `scripts\kb\ingest.py`，按架构它们属于 `app\rag\`。**
   ⚠️ **迟早要搬。** 第 3 项做 worker 时**必须 `import` 它，不许复制一份** ——
   复制的那一刻，两条链路的切分规则就开始各自漂移了。
3. **`--no-embed` 是一把脚枪。** 它留下没有向量的 chunk，而补向量只能 `--replace` 重跑；
   忘了加就会**静默跳过**（文档被判"已入库过"），**向量永远补不上且不报错**。
   现在的防线只是"脚本在结束时把这句话打印一遍" —— **靠人记得看输出，不是好设计**。
   （更安全的做法是加一个 `--embed-only` 补齐模式，见 §10.3。）
4. **它验的是「机制」，不是「场景」。**
   ⚠️ **2026-10-15 更新**：中文端到端**已经验过了，是通的** ——
   但**通的原因必须说清楚**：靠的是**向量路跨语言**（实测中英余弦 **0.7885**），
   **不是全文路**（pg_trgm 在中文 query 撞英文 chunk 时切不出三元组）。
   所以这个"通"是**有条件的**：**embedding 一旦挂掉、降级成纯全文检索，中文就会塌。**
   → **中文语料（知识库 B）仍然必需**，只是理由从"能不能跑通"变成了"**全文路要能真正参与**"。

## 9.19 「详细程度」开关：同一份数据，两种呈现

**问题**：拒答时前端会列出检索到的来源，但后端落库的 `Answer.citations` 是**空数组**
（`schemas/chat.py` 的注释写着"拒答没有依据可引"）。
于是**同一句话，看直播和看回放长得不一样** —— 刷新之后来源消失。

**这不是 bug，是一条没对齐的边界。** SSE 那层想的是"让用户看到我找到了什么"，
落库那层想的是"拒答没有**引用**"。两句话都对，但**没人问过一句"那刷新之后呢"**。

**定案（2026-10-15）：把「存不存」和「显不显示」拆成两层。**

| 层 | 决定 |
|---|---|
| **数据层** | **永远存全** —— 拒答也落 `citations` ＋ `confidence` |
| **界面层** | **一个可切换的档位**（不是三套代码） |

| 档位 | 给谁 | 来源 | 分数（`精排分 0.466`） |
|---|---|---|---|
| **详细** | 开发 / 评测 / **面试官** | ✅ 显示 | ✅ 显示 |
| **简洁** | 终端用户 | ✅ 显示，但**换人话** | ❌ 隐藏 |

**为什么数据层必须"永远存全"**：

- **badcase 复盘都是事后做的。** 只改前端显示的话，**刷新后信息就断了**，"观察"无从谈起 ——
  开发期最需要的恰恰是"刷新后还在"。
- 拒答时那几条来源的含义是「**用户问 X，我召回了这些，但都不够好**」——
  这**正是优化检索的入口**。丢掉它，等于**每次拒答都在说"我不知道"，
  却不留下任何"我为什么不知道"的证据**。
- `confidence` 同理：不落库就永远答不出"它是在 0.33 拒的还是 0.59 拒的" → **阈值调优只能靠猜**。

**为什么界面层要分档，而不是一刀切**：

- ⚠️ **面试官不是"客户"** —— 他恰恰是**最想看内部信息**的人。
  "拒答时列出来源"对他是**加分项**：它证明你有 **badcase 归因**的意识。
- 对**终端用户**，要藏的其实**不是"来源"，而是"分数"**：
  「这条答案来自《退款政策》第 3 条」是**建立信任**的东西；
  「精排分 0.466」才是实现细节。

**代价**：多一个开关要维护；而且"同一份数据两种呈现"意味着**两种呈现都得有人验**。
（当前默认 **详细** —— 这是求职作品集，那是卖点。）

## 9.20 又一个 Vue 陷阱：`v-if` 里的**裸标识符**会被当常量折叠掉

**现象**：写了 `v-if="isDetailed"`（`isDetailed` 是个 `computed`），
**点切换按钮，界面纹丝不动，控制台也不报错。**

**定性**：去抓**编译产物** —— 模块里**只剩一句 `import`**，
既没有 `_unref(isDetailed)` 也没有 `_ctx.isDetailed`，**整个 `v-if` 消失了**。

**原因**：`@vue/compiler-sfc` 在**裸标识符当整个条件**时会做**常量折叠**。

> ⚠️ 同一个 `detailLevel` 写在**表达式**里（`detailLevel === 'x'`）就完全正常 ——
> 所以这个坑**只在"裸标识符当整个条件"时出现**，极难往编译器上联想。
> 2026-10-15 实测踩中：切换档位时"按钮高亮了、`localStorage` 也写对了，
> 但分数照旧显示"。

**解法**：**写成函数调用** `isDetailed()` —— 调用表达式不会被当成常量。

**为什么值得单独记**：它的症状和 §9.13（`reactive()` 陷阱）**一模一样** ——
"**数据变了界面不动，而且不报错**"。但根因一个在**运行时**、一个在**编译期**。
遇到这类症状，**先去看编译产物**，比在响应式上反复猜快得多。

## 9.21 「服务器只 pull ACR」的真正边界：`image:` 写的是地址，不是标签

### 问题

2026-10-17 首次部署，`compose up -d` 红在：

```
failed to resolve reference "docker.io/pgvector/pgvector:0.8.0-pg16": not found
```

`.env` 填全了、`compose config` 也过了 —— 但那是**另一个关卡**的事
（`config` 只做插值，`up` 才真的去拉镜像、建网络、起容器）。

### 天真做法：在服务器上 `docker tag`

第一反应是"服务器本地已经有 redis 了，那把 pgvector 也弄到本地不就行了" ——
`docker pull`（走某个能用的源）→ `docker tag` 成 `pgvector/pgvector:0.8.0-pg16`。
**对 `up -d` 有效，对 CD 无效。**

因为部署脚本是：

```bash
docker compose pull && docker compose up -d      # ← 注意前半段
```

**`image:` 字段里写的是"去哪里找"，不是"叫什么名字"。**
本地 retag 只改变了"名字到镜像"的映射，**没有改变这个地址** ——
`compose pull` 照样按 `docker.io/...` 去拉，照样 404。
于是：**手工能起来，一发版就红**。这正是最难查的那类差异。

### 解法：连公共基础镜像也搬进 ACR，并且搬的动作自动化

1. `docker-compose.prod.yml` 里 `postgres` / `redis` 的 `image:` 改成
   `${ACR_REGISTRY}/pgvector:0.8.0-pg16` / `${ACR_REGISTRY}/redis:7.4.1-alpine`；
2. `deploy.yml` 的 `build-and-push` 加一步「把公共基础镜像补进 ACR」，
   **幂等**：先从 ACR 拉一次，拉到就跳过（否则每次部署都要传 ~700 MB），
   否则从上游拉 → `tag` → `push`。

**代价**：ACR 里多两个仓库、首次数分钟的传输时间；
**换来的**：`image:` 与拉取源**永远一致**，不存在"本地有、CI 没有"的中间态 ——
**"服务器只 pull ACR"这条硬约束，只有在"所有镜像都在 ACR 里"时才成立。**

### 附带一条：搬镜像的动作不该在开发机上做

第一版是在本机 `docker push` 那个 622 MB 的 `pgvector`，
**跑了 57 分钟没结完**（系统代理开着，实测上行 ≈590 KB/s；而 `docker push` 在非 TTY 下
把进度缓冲住，看起来像"卡死"，其实是慢）。
同理还有一处"看起来正常其实很慢"的：`Out-String` 会把整段进度憋到最后才吐。

⟹ **大镜像一律由 CI runner 搬**（runner 到 ACR 直连，334 MB 的 api 镜像不到两分钟）。
判断"慢"还是"卡"**别靠感觉**：隔十几秒采两次网卡字节数，算速率。

> 📌 `prometheus` / `node-exporter` 暂时留在 Docker Hub 原名 ——
> 它们在 `monitoring` profile 里，v1.0 的部署链**不经过它们**。
> 这是**有意的例外**，不是漏了：**开 v1.1 可观测之前必须一并补进 ACR**。

## 9.22 回滚到底被**哪一步**触发：依赖健康门比健康检查轮询更早

### 设计时的假设

部署链被设计成：

```
up -d → alembic upgrade head → seed → 轮询 /healthz（30 次 × 5s）→ 失败则回滚
```

`/healthz` 被赋予了三重职责：compose 的 `healthcheck`、CI 的部署轮询、**自动回滚的判定依据**。
看起来"轮询超时 → 回滚"就是回滚的入口。

### 2026-10-17 演练测出来的真实路径

故意把 `/healthz` 打成 503 之后：

```
坏 api 容器 → healthcheck 不过 → unhealthy
        ↓
nginx 的 depends_on: api: condition: service_healthy 永远不满足
        ↓
`docker compose up -d` 自己等约 99 秒，返回非零（dependency failed to start）
        ↓
job 红在「拉取新镜像并重启」→ 迁移 / seed / 轮询 / 记录版本 **全部 skipped**
        ↓
「部署失败 → 自动回滚」把 IMAGE_TAG 换回旧 tag，23 秒恢复
```

**`轮询 /healthz` 一次都没执行。** 这与设计假设不同，但**结果更好**：
检测窗口从 150 秒缩到 99 秒。

### 三条要记住的推论

1. **`healthcheck` 有第二个用处：当"启动依赖"的门。**
   `depends_on: condition: service_healthy` 让"上一层的健康"成为"下一层能否启动"的前提。
   这带来一个副作用：**只要 api 坏，nginx 根本不会存在** ——
   失败窗口里用户看到的是**连接被拒**（`ERR_CONNECTION_REFUSED`），不是 503。
   排查时别把"站点 502/503"当成默认预期。
2. **轮询那一步不能删。** 它覆盖的是另一类失败：**容器都达标、nginx 也起来了、8080 上仍答不上**
   （nginx 配置写错 / 端口没绑 / 上游地址错）。那类情况下 `up -d` 是**成功的**，
   只有轮询能发现。
3. **`/healthz` 的语义要守得住**：它只回答"进程该不该被重启"，不查依赖。
   如果哪天有人往它里面加数据库检查，上面这套（含 compose healthcheck 触发的重启）会一起变得不稳定 ——
   这正是它当初刻意不查依赖的原因（`app/main.py` 里写了理由）。

### 演练方法本身也值得记

**不能靠"打坏镜像构建"来验回滚**：构建失败时 `deploy` job 压根不启动（`needs: build-and-push`），
没有 `up -d`、没有失败信号、回滚那一步也不会跑 —— 站点原地不动，**什么也验不到**。

必须让**坏镜像真的上到服务器**。最省事且可逆的做法：`/healthz` 里 `raise HTTPException(503, ...)`，
推上去看它红在哪、看回滚是否把它救回来，然后 `git revert`。
**坏的东西必须一键 revert 就好** —— 这是"敢在生产上演习"的前提。

> 📌 演练的完整时间线、逐步结论和证据链 → `..\ops\server-log.md` ⑱；
> 结论性事实 → `..\ops\server-notes.md` C8.8。

## 9.23 四组消融实测：**RRF 会拖后腿，精排才是救场的那个**

### 为什么先做这一组

"检索有效"这件事最容易被糊弄：跑几个问题看着都能答，就说检索没问题。
**能不能答对，是生成层的事；目标文档有没有被召回，才是检索层的事。**
两件事混在一起打一个总分，**改不动** —— 因为不知道分数掉了该动哪一层。

所以先只测检索层：给定问句，**目标文档有没有进 top-5**。
`evals\run.py --layer retrieval`，知识库 B（森屿家居，35 篇 / 231 块），25 道检索题，
候选 20、RRF `k=60`，四组只换检索策略、其余全一样。

### 结果（2026-10-17，`evals\results\retrieval-*.json`）

| 消融 | 全文门槛 | hit@5 | MRR@10 | 命中 |
|---|---|---|---|---|
| 全文单路（`word_similarity`） | 0.05 | 0.560 | 0.435 | 14/25 |
| 向量单路（pgvector 余弦） | — | 0.920 | 0.717 | 23/25 |
| RRF 融合 | 0.05 | **0.840** | 0.638 | 21/25 |
| RRF 融合 | **0.20** | 0.920 | 0.723 | 23/25 |
| RRF ＋ 精排 | 0.05 | **1.000** | 0.843 | 25/25 |
| RRF ＋ 精排 | 0.20 | **1.000** | **0.847** | 25/25 |

### 三个结论，一个比一个反直觉

**① 中文全文路在短问句上是弱的，不是"锦上添花"，是"需要管住"的那一路。**

`word_similarity` 会在 `1/3 = 0.333` 附近**大量并列**。实测："床架 保修 几年"
的前 5 名分数全是 0.333，而正确文档 `40-保修与维修` 根本不在里面 ——
**并列意味着这一路的"名次"基本是随机的**。

**② 所以 RRF 在默认门槛下比纯向量还差（0.840 vs 0.920）。**

这推翻了"混合检索总是更好"的默认假设。RRF 只看**名次**：
把一路随机名次混进来，等于往一个还算准的排序里**注入噪声**。
—— 融合的前提是**每一路都比随机强**；一路接近随机时，融合是负收益。

**③ 门槛抬到 0.20，RRF 立刻回到 0.920，且 MRR 反超纯向量（0.723 vs 0.717）。**

`fulltext_min_similarity` 原来默认 **0.05** 太松（`0.05` 只比"完全不相关"好一点点），
把 0.333 那一坨平局全放进来了。**过滤掉噪音后，融合才重新变成正收益。**

**④ 精排把所有伤都治好了 —— 两个门槛下都是 hit@5 = 1.000。**

精排是**交叉编码**：它重新看每个 `(query, chunk)` 配对，**完全不管原来的名次**。
所以只要候选集里包含了正确文档，前面的排序再乱也能被它纠正回来。
这也解释了为什么 0.05 那个坏门槛在上线后**没有暴露成事故** —— 精排兜住了。

### 代价与边界（别把这张表当结论用）

- **25 题、单次运行**。0.920 与 0.840 差 2 题，**这个量级在多题上可能翻转**。
  要下"RRF 有害"这种结论，需要扩题量 ＋ 多次运行。
- **只在 B 库（中文、2C2G 上的小库）测过**。A 库是英文，`pg_trgm` 在英文上的表现完全不同 ——
  **不能把这个门槛搬到 A 库用**。
- 精排的 1.000 有个前提：**候选集里得有正确答案**。候选只有 20 条，
  如果语料涨到 1 万块、正确文档压根没进候选，精排就无从救起。
  —— 到那时要动的不是精排，是**召回**（更多路／更好的切分／混合权重）。

### 因此定下的两件事

1. **不提门槛默认值**：`fulltext_min_similarity` 保持 0.05，
   把"0.20 在 B 库更好"记进 `..\plan\CANDIDATES.md` 等 A 库也测过再定
   （改一个默认值容易，改错一个默认值很难被发现 —— 见 §10.3 里"阈值只能挂在可比分数上"那条）。
2. **精排不是可选项，是主链路**：这张表是它存在的量化理由。
   `RERANK_ENABLED=false` 只是降级开关，不是等价配置。

> 📌 复现：`uv run python evals/run.py --layer retrieval`（全跑）
> ／`--only rrf --fulltext-min 0.2`（单组＋门槛）。
> 结果 JSON 进 git —— 面试时能直接指着数字讲，而不是"我记得跑过"。

## 9.24 生成层与拒答层：**判分器自己先翻车了三次**

### 为什么要单独测这两层

检索层只回答"证据有没有被召回"。**召回了不等于答对了。** 一个错答可能出在三处：

```
没召回（检索层） ｜ 召回了但没用对（生成层） ｜ 该说没有却编了（拒答层）
```

混在一起打一个总分，**改不动** —— 分数掉了不知道该动哪一层。

### 拒答层：15/15 行为正确，其中 13/15 **一次生成模型都没调**

断言方式不是"看文案像不像拒答"，而是 **SpyChat 数生成模型被调了几次** ——
因为"模型自己决定不答"也能骗过肉眼判分，而那正是本项目**刻意避免**的设计
（拒答必须由调模型**之前**的确定性代码决定，见 §5.2）。

剩下 2 题调了模型，是因为它们**本来就该答** —— 见下面那条更重要的发现。

### ⚠️ 发现一：「库里没有这件事」和「库里有『没有』这件事」不是一回事

原来 `ref-01`「加拿大的退货政策是几天？」标的是"必须拒答"。实测系统回答：

> 加拿大目前不提供服务，因此没有已生效的退货政策[3]。加拿大站的 21 天等数值仍属于
> 未生效的草案计划值，不能对外引用[1][3]。现行有效的退货期限只覆盖美国、德国、日本、
> 新加坡、马来西亚等已开通地区，不能据此推断加拿大[4]。

**这是满分答案，不是失败。** 错的是标签：加拿大未开通这件事**库里有依据**
（公司概览的服务地区 ＋ 站外假政策澄清页）⟹ 正确行为是**明确说"没有"**，而不是拒答。

⟹ 拒答层因此分成两类期望：

| | 含义 | 期望 |
|---|---|---|
| `should_refuse: true` | 库里**完全没有这件事**（成本、CEO、分期、延保） | **拒答，且不调模型** |
| `should_refuse: false` ＋ `must_say` | 库里有**"没有"的证据**（未开通地区） | **答"没有"**，拒答反而是次优（用户想知道"能不能办"） |

**这条修正本身是评测抓出来的** —— 没有跑，我会一直以为系统漏拒了两题。

### ⚠️ 发现二：判分器比模型更不可靠（三次翻车，同一个答案从 5/20 修到 14/20）

同一个结果文件 `generation-20261017T110525Z.json`，**换尺子不换回答**：

| 尺子 | 通过 | 翻车原因 |
|---|---|---|
| 逐字子串匹配 | **5/20** | 中文同义替换全判错：「运费**与**关税」vs「运费**和**关税」、「**不要**自行丢弃」vs「**请勿**自行丢弃」 |
| 改字符二元组覆盖 | 13/20 | 跨数字造出假二元组：「总**则 7 天**」捞汉字得 `["总","则","天"]` ⟹ 造出"则天"这种不存在的词 |
| ＋只在连续中文段内取 | 13/20 | 同上修正后略升 |
| ＋**数字为准**、剥引用标记 | **14/20** | `[1]` 里的数字污染匹配：要点「电子件 1 年」其实没答到，却被 `[1]` 判成命中 |

⟹ 于是定了判分规则：

```
要点里有 数字/百分比/拉丁词 ⟹ **以它为准**（政策里最不可替换的证据）
要点全是中文             ⟹ 看二元组覆盖率 ≥ 0.6，并标记为「弱判定」单独计数
判分前                 ⟹ 先剥掉 [1][2] 这类引用标记
```

**为什么不上 LLM 当裁判**：不可复现 ＋ 烧钱 ＋ 会把"模型的偏好"混进"系统的能力"。
代价是判分偏粗，所以**每一条失败都保留原文**（结果 JSON 里有 `text`），随时可以人工复核。

### 结果（B 库 20 题，`evals\run.py --layer generation`）

| 指标 | 值 |
|---|---|
| **全通过**（要点全中 ＋ 引用对 ＋ 无禁语） | **14/20** |
| 失败构成 | 1 题**真错**（答里出现已废止的 `7~10 个工作日`）＋ 5 题**要点部分缺**（多为"少说了一句"，如漏掉"多不退少不补"、"电子件 1 年"） |
| 判分局限 | `must_not_say` 是**字面匹配、不懂否定** —— 如果模型写"不能用 7~10 天"，也会被判成出现禁语。这条已记进 `CANDIDATES.md` |

### 三条经验（比分数重要）

1. **先修尺子，再看分数。** 5/20 和 14/20 是同一批回答。**分数低先怀疑判分器**，否则会去改本来没错的提示词。
2. **`--rescore` 是必需品**：用已存的回答重判，才能把"尺子变了"和"回答变了"分开。
3. **失败样本必须留原文**。只有分数没有原文的评测，等于没有评测 —— 因为你无法证明扣分是对的。

## 9.25 拒答阈值的标定：**rerank 能分开，余弦分不开**

### 要定的是什么

`_should_refuse` 在不同的失败情形下拿到**两种分数**：rerank 分（交叉编码）和向量余弦。
它们**不是同一个量纲**，用一套阈值必然在一种口径上是错的（那就是 PLAN §8.4 D2）。

标定就是把同一批题跑两遍、把两种分数的分布摊开，找**分离点**。

### 数据（B 库 35 篇 / 231 块，2026-10-17）

| 分数 | 可答（25 题） | 不可答（13 题） | 结论 |
|---|---|---|---|
| **rerank** | 0.790 ~ 0.999（中位 0.936） | 0.238 ~ **0.592**（中位 0.435） | ✅ **间隙 0.592~0.790** |
| **向量余弦** | 0.409 ~ 0.688（中位 0.568） | 0.352 ~ **0.578**（中位 0.440） | ⚠️ **重叠区 0.409~0.578** |

余弦阈值扫描：

| 阈值 | 正确拒答（/13） | **误拒可答**（/25） |
|---|---|---|
| 0.45 | 8 | **1** |
| 0.50 | 10 | 5 |
| 0.55 | 10 | 11 |
| 0.58 | 13 | 14 |
| **0.60（旧行为）** | 13 | **19** |

### 两个结论

1. **rerank 的 0.60 是对的** —— 它落在间隙里（拒答 13/13、误拒 0/25）。
   2026-10-15 那次数值标定（0.60）在 B 库上**依然成立**，没有过时。
2. **余弦没有可用阈值** —— 想要"拒得干净"（0.58）就得**误拒 14/25**；想要"少误拒"（0.45）
   就只拒得掉 8/13。选 **0.45**，因为**误拒比漏拒更伤体验**，而且漏拒至少还有引用可核对。

⟹ **`RERANK_ENABLED=false` 是降级，不是等价配置。** 这句话现在有数字支撑，
而不再是一句"理论上会不同"。

### 一个方法论上的教训

第一次量分布时量错了：我在消融里重排了候选，却**忘了把 rerank 分写回对象**，
于是"精排 top-1 分数"其实还是余弦（中位 0.539）——
它和 pipeline 的真实置信度（**0.96**）差了整整一个量级，**据此得出的结论会完全相反**
（"0.60 太高了，一半题会被拒"）。

**怎么发现的**：不是靠读代码，是靠**对不上** ——
生成层 20 题**一道都没被拒**，而按那个"错误分布"应该有一半被拒。
两个数字打架时，先去查**它们是不是同一个东西**。

> 📌 现有回归测试：`tests/test_refusal_thresholds.py`（5 条）——
> 同一个 0.50 按余弦口径不拒、按 rerank 口径拒。**把两个阈值合并回一个，它会立刻红。**

## 9.26 文档上传：为什么拆成「建行 → 排队 → 处理」三段

### 问题：一次上传里混着**毫秒级**的事和**秒级**的事

| 步骤 | 量级 | 会失败吗 |
|---|---|---|
| 校验后缀/大小、算 sha256、落一行 `Document` | 毫秒 | 基本不会 |
| 清洗 + 切分 | 微秒（纯 CPU） | 基本不会 |
| **embedding** | **秒级**（每 10 块一次网络往返） | **会** —— 限流、超时、key 过期 |

把它们全塞进一个 HTTP 请求里，代价是三个一起出现：用户在转圈、nginx 到点超时、
**超时之后重试还会重复入库**（因为第一次其实成功了，只是没等到响应）。

三种拆法，只有一种能用：

| 做法 | 问题 |
|---|---|
| 请求里全做完 | 慢 ＋ 超时 ＋ 失败没法重试 |
| FastAPI 的 `BackgroundTasks` | 进程一重启任务就**丢**；界面也说不出"在排队"还是"在算" |
| **队列 ＋ 独立 worker** | 多一个容器，但"接受"和"做完"彻底解耦 |

第三种是这里的选法。代价是**必须让用户理解"还没做完"** —— 于是有了状态机和轮询。

### 为什么字节走磁盘，消息里只放 `document_id`

一个 1 MB 的文件 base64 之后是 1.3 MB。塞进 Redis 有两个问题：

1. 占内存 —— 这台机器给 Redis 只留了 96 MB；
2. 更要紧的是 **`maxmemory-policy` 会静默淘汰**：消息被挤掉**不报错**，
   表现是"上传成功、永远 pending"。这类故障找起来极贵。

所以字节落在 **api 与 worker 共享的命名卷**（`gq-uploads`），消息里只有一个 UUID。
**卷是传送带，不是存储**：worker 处理完（成功或失败）立刻删。长期数据是切好的块，
在 `chunks` 表里 —— 要重试就重新上传，字节会重新落盘。

### 为什么是**四个**状态，不是两个

```
PENDING → PROCESSING → READY
              └──────→ FAILED（带 error_message）
```

两个状态（"成功/没成功"）省不掉代码，却让界面**没法说话**：
用户只看到"没成功"，不知道是在排队、在算、还是真的坏了，于是只能反复点。
`FAILED` 是**显式状态**而不是"没变成 READY"——失败必须能被列表看见、能看到原因。

`PENDING` 还承担一件事：**它是"文件已经在盘上、任务可能还没被取走"的唯一凭据**。
worker 启动时扫一遍 `PENDING` 重新入队，就能把"Redis 重启丢了队列"这种孤儿救回来；
扫一遍 `PROCESSING` 则改判 `FAILED`（那个 worker 已经被杀了，界面不能永远转圈）。

### 判重的键是 `content_hash`，但**文件名也要判**

两个键治的是两种不同的病，缺一个都会出事：

- **按 `content_hash`** —— 与表的唯一约束 `UNIQUE(tenant_id, content_hash)` **同口径**。
  不同口径的后果很具体：同一个文件改个名字再传，代码看着是"新文档"，
  数据库直接把它顶成 `IntegrityError`，用户收到 **500**。
- **按 `filename`** —— 语料文件**内容改过**的时候，hash 变了，按 hash 看是新文档，
  而**旧的那份还留在库里被检索到**。于是同一件事有两个版本，答案看运气。
  （这正是离线 CLI 需要 `--replace` 的原因。）

⚠️ **失败过的记录不挡路。** 否则用户改了文件重传、或者纯粹想重试，
都会被一句"已入库过"挡住 —— 而它**其实根本没进库**。
`PENDING` / `PROCESSING` **照挡**：那是真的在处理中，再排一遍等于白烧一次 embedding。

### 上传为什么要管理员

知识库是**租户共有**的，不是某个人的私有数据。普通成员能上传，等于任何人都能往
所有人的模型上下文里塞东西 —— 这是"提示注入"的一个现实入口，不只是权限问题。
（对应地：写进库的文本在问答时会原样进入 prompt。）

### 报告页：**数字上线，逐题明细不上线**

`evals/results/*.json` 一个文件里同时躺着两样东西：

- **聚合结论**（命中率、通过数）—— 报告页要的是这个；
- **逐题明细**（题干、标准答案、`must_hit` 文件名、禁语清单）—— 那是**评分材料**。

所以边界不在"文件进不进镜像"，而在**接口这一层切开**：`app/api/reports.py` 只返回
聚合数字。镜像里带着原始文件没问题（它不是文件服务器），HTTP 上吐出去就成了公开题集。

> 📌 三者边界（最容易搞混的地方，曾经把语料也算成"评测材料"）：
> `evals/corpus/` ＝ **业务内容** ⟹ **必须上线**（否则站点只会拒答）；
> `evals/questions/` ＋ `run.py` ＝ **评分材料** ⟹ **不上线**（服务器不跑评测，这理由要单独成立，
> 不能用"本地和服务器结果差不多"充数）；
> `evals/results/*.json` ＝ **报告数据** ⟹ **上线**，但只以聚合形式出 HTTP。

### 报告页为什么"不许裸数字"

检索层的 `hit@5` 在同一个库上可以是 **0.840** 也可以是 **0.920** —— 取决于
`fulltext_min_similarity` 取 0.05 还是 0.20（§9.23）。单独摆一个 `0.92`，
读者会理解成"这个系统的检索准确率"，而这正是**最想避免的那种误解**。

所以这个页面有三条硬规则：

1. 每张卡片必须带**生成时间 ＋ 那次运行的配置**（时间戳和 config 是响应模型的**必填字段**）；
2. 每个比率必须带**分母**（`0.920（23/25）`）—— 只给 `0.92` 的话，读者不知道是 25 题里的 23 题；
3. 缺值显示 `—`，**不显示 `0`**：分母为零的比率是"不存在"，写成 `0.000` 会被读成"全错"。

同一层有多份快照是**正常的**（判分口径改过三次，§9.24）。页面因此只把每层最新一份做成卡片，
其余列在下面的表里 —— 不鼓励横向比，也不假装只有一次运行。

### 两个只在容器里才出现的坑

1. **命名卷的属主来自镜像。** Docker 创建**空**命名卷时，会用镜像里挂载点目录的属主
   初始化它。漏了 `mkdir /app/uploads && chown appuser` 这步，卷归 root，
   非 root 的进程写不进去 —— 表现是"上传直接 500"，而**本地不挂卷时完全正常**。
2. **nginx 的 `client_max_body_size` 会先把请求体落盘**（不是流式转发）。
   原来写的 32m 意味着任何人都能用垃圾请求往这块 40 GB 的盘里灌 32 MB。
   真正的水位应该在应用里（`UPLOAD_MAX_BYTES`，默认 2 MB），nginx 那道降到 4m 只作兜底。

### 验证到什么程度（诚实版）

- **HTTP 层**：集成测试覆盖（`tests/test_documents_api.py`，14 条）—— 真库、真落盘、
  真调 `handle_job`，只把 embedding 换成假实现（约定 9 不许真调模型）。
- **真 Redis ＋ 真卷 ＋ 真 embedding**：本机 compose 里跑过一次端到端探针
  （api 容器建行＋落盘＋`LPUSH` → worker `BLPOP` → 真的调了 `qwen3.7-text-embedding-flash`
  → 2 块 / 1024 维 / 状态 `READY` / 卷上文件已消失），耗时约 0.5 s，探针租户随后删除。

> 📌 已知不完美见 §10.3（单消费者、无重试退避、无死信队列）。

## 9.27 限流与配额：**两把尺子，两门不同口径的账**

### 先把两种"限制"分开

| | 管什么 | 谁来做 | 超了怎样 |
|---|---|---|---|
| **鉴权** | 谁能调用 | `app/core/security.py`（JWT） | 401 / 403 |
| **成本** | 一天能烧多少 | **本节**（`app/core/limits.py`） | 429 |

把这两件事混成一件，是这类功能最常见的错：于是"防刷"被塞进权限表，
或者"配额用完"被写成 403 —— 前者管不住成本，后者会让用户以为**自己做错了什么**。

### 两道限流，量的是不同粒度

    nginx（按 IP，120 次/分钟，burst 30）  →  挡扫描器、挡单机刷
    app  （按用户，30 次/分钟）            →  挡"一个人刷"，换 IP 也绕不过去

**为什么两道都要**：nginx 不知道谁是谁（它只看得见 IP）；
而按 IP 算会误伤 —— 同一个办公室十个人走一个出口，会互相拖累。

⚠️ **数值关系是设计的一部分**：nginx 那道必须**明显宽于**应用那道。
写反了的后果很具体 —— 用户先撞上 nginx 的 **HTML 错误页**，
前端只能显示"请求失败（HTTP 429）"，说不出"还有 12 秒"。

📌 顺带修掉一颗**已经埋着的雷**：nginx 原来是 `30r/m burst 10`，
而知识库页在入库期间**每 1.5 秒轮询一次状态**（≈ 40 次/分钟）——
它自己就能把这道限额撞穿。上传一个大一点的文件时大概率踩到，
表现是"列表突然报错、但其实东西已经进库了"。现在改成 120r/m，burst 30。

### 速率：固定窗口，**键里带对齐后的时间戳**

```python
key = f"gq:rl:{user}:{aligned_to_minute:%Y%m%d%H%M}"
used = await redis.incr(key);  if used == 1: await redis.expire(key, 120)
allowed = used <= limit
```

两个细节都是踩过才知道的：

1. **键里带时间戳，不是"靠 TTL 当窗口"**。靠 TTL 的话窗口从**第一次请求**开始算，
   于是"每次隔 61 秒发一次"永远不会触发限流 —— 它总能落进一个"刚开启"的新窗口。
2. **先加后判**。先判后加的话，被拒的请求不计入，于是每 `N+1` 个请求都会被判成
   "N 以内" —— **实际放行量是上限的两倍**。

代价是**固定窗口的边界突发**：`:00:59` 和 `:01:00` 各来 N 次，一分钟内就看到 2N 次。
为它上滑动窗口（zset）不值 —— 这里治的是"脚本刷"，不是"精确公平"。

### 配额：**软熔断**，因为流式没法中途掐断

HTTP 状态码在第一个 `sources` 事件时就发出去了，所以"答到一半被发现超额"**做不到**。
做法只能反过来：

    这次跑完 → 记账（模型回报的 usage） → **下一次**进来时发现已超 → 429

代价说清楚：**实际用量可能略超配额**（最多超一条回答的量）。这个偏差是**有意接受**的
—— 比"答到一半被切断"体验好得多，而且超的那一条是有账可查的。

⚠️ **按业务日切（北京时间的零点），不按 UTC**。按 UTC 切的话重置发生在北京**早上 8 点**，
用户会觉得"刚上班就没额度了"，而且根本猜不到规则。

### token 数是**真数**，不是估算

实测（2026-10-17 当场验的）：请求带 `stream_options: {"include_usage": true}` 之后，
**流的最后一帧**带 `usage: {prompt_tokens, completion_tokens, total_tokens}`。

```json
{"choices":[{"delta":{"content":""},"finish_reason":"length"}],
 "usage":{"prompt_tokens":35,"completion_tokens":16,"total_tokens":51}}
```

估算（字数 ÷ 2 之类）在中文上误差 30%~50% —— 用来做"一天的总账"会直接算错账，
不值得省那一个字段。两个坑：

- **带 usage 的那一帧 `choices` 是空数组**。任何"取不到 content 就 continue"的解析
  都会把它跳过，于是这份 usage 永远读不到。
- 要**覆盖**不要累加：那一帧是最终总计，出现两次时累加会把账算成两倍。

📌 **拒答时 `usage` 是空的** —— 因为拒答**根本没调模型**（约定 17）。
    所以拒答不占额度，账面上也看得出来。这是"先判拒答再调模型"顺带白捡的好处。

### fail-open：Redis 挂了就**放行**

这两把尺子治的是**成本**，不是安全。Redis 抖一下就把整站 429 掉，
等于把"缓存故障"升级成"服务不可用" —— 这个交换不划算。

所以 Redis 异常一律**放行 ＋ 打警告 ＋ 记 `gq_limit_failopen_total`**。
**静默放行才是真问题**，放行本身不是：那个指标不为 0，就说明"这段时间的计量不可信"。

⚠️ 这里踩了一个只在故障时才暴露的坑：函数 `_failopen` 和指标变量 `_failopen`
**重名**，函数把变量遮住了 —— 一进异常分支就
`AttributeError: 'function' object has no attribute 'labels'`，
也就是**兜底逻辑自己先炸**。平时跑一百次都不会出现，因为正常路径不会进那个分支。
现在的写法是函数 `_fail_open` ／ 变量 `_failopen`，故意错开一个下划线。

### 429 必须**能照着退避**，不能只说"太频繁"

响应体（不是 `HTTPException` 的 `{"detail": "..."}`，那样前端拿不到字段）：

```json
{"detail":"请求太频繁（上限 30 次/分钟），请 12 秒后再试",
 "code":"rate_limited","scope":"rate","used":31,"limit":30,"retry_after_s":12}
```

外加标准的 `Retry-After` 头 —— 这样**不是我们前端**的调用方（脚本、监控）
也能照着退避，不用解析我们的 JSON。

📌 前端还有一条**必须**做的事：轮询里遇到 429 **不要弹红错，安静退避**。
    入库还在正常进行，弹一个"请求太频繁"会让人以为坏了、去重传 —— 反而更糟。
    `DocumentsView` 里因此有一个会在 429 时倍增的间隔（1.5 s → 最多 15 s）。

### 测试：固定窗口 ＋ 墙钟 ＝ **flaky**

一开始的写法是"连发两次、断言第二次 429"。它**随机失败**过两次，原因很具体：

    第一次请求落在 :59.9、第二次落在 :00.1 → 两次各自进了一个新窗口 → 都是 200

这也是固定窗口的真实性质，所以不能靠"发得快"来断言。现在的做法是**预先铺满计数**，
而且**把本分钟和下一分钟的窗口都铺满**（只铺当前分钟的话，跨分钟还是可能失败）。
测试从此与墙钟无关。

📌 这条值得记：**"测试自己有隐藏的时间依赖"是最容易误判成业务 bug 的一类失败** ——
    单跑过、连跑挂，而且报错指向业务代码。

### 已知不完美

- **固定窗口的边界突发**最多 2 倍（接受：这里治脚本刷，不追求精确公平）。
- **配额是软的**：可能超一条回答的量（见上）。
- **Redis 宕机期间不限流也不记账** —— 靠 `gq_limit_failopen_total` 发现，
  不靠它拦（那个时间段本来就是"降级运行"）。
- **计数只按天/分钟保留**：跨天历史不落库，所以"上周某人用了多少"查不到。
  真要做成本报表，得把 `usage` 也落进消息表（`messages` 现在只存 `latency_ms` /
  `confidence`，没有 token 数）。

## 9.28 embedding 元数据锁：两套向量空间**不能被悄悄混用**

### 故障长什么样

换一个 embedding 模型（或者供应商在别名后面悄悄换了模型），库里 231 个块的向量
是**旧模型**算的，而查询向量是**新模型**算的。余弦相似度照算不误 ——
但这时它**不是"相似度"，是噪音**。

而这个故障的三个特征让它特别难发现：

    · 不报错（SQL 正常执行）
    · 不崩溃（检索照样返回 k 条）
    · 接口 200 —— 只是**答案慢慢变差**

和 §10 里那条「`pg_trgm` 在 `ctype=C` 下对中文恒为 0」是**同一种病**：
功能坏了，但什么都不报。所以处理方式也一样：**主动测、主动喊**。

### 三个防线，各管一段

| 防线 | 在哪 | 不一致时 |
|---|---|---|
| **写**：向量与元数据一起落库 | `app/kb/ingest.py` | ——（早就有，`embedding_model` / `embedding_dim` 两半） |
| **读**：向量检索**只查当前模型**的块 | `app/rag/retrieval.py` | 旧向量**自动被忽略** ⟹ 不会污染排序 |
| **启动**：扫一遍库，对不上就喊 | `app/db/checks.py` | 显眼告警 ＋ `gq_embedding_metadata_drift_chunks` 指标 |

### ⚠️ 为什么**不在入库时拒绝**（这条推翻了 `knowledge.py` 原来的注释）

`app/db/models/knowledge.py` 的模块注释原本写着"入库时两者与配置不一致 → 直接拒绝"。
真写下去会发现**它把自己的恢复路径堵死了**：

    换模型的正确做法是「逐文件 `ingest.py --replace` 重嵌入」。
    第一个文件重嵌入时，库里**仍然躺着**其余文件的旧向量 ——
    按"入库时拒绝"的逻辑，这一步会被拒 ⟹ **永远换不了模型**。

所以改成"**读侧硬过滤 ＋ 启动响亮告警 ＋ 写入如实记账**"：
旧向量不会被用到（安全），但也不会拦住你重嵌入（可恢复）。

> 📌 这条也说明一个通用判断：**"检测到不一致就拒绝写入"听着严谨，
> 但要看它会不会挡住"把不一致修好"的那条路。** 会挡住的，就不能这么写。

### 为什么**读侧过滤**是最有效的那一道

它把"不可比"变成"不存在"：旧向量根本不参与排序、不参与 RRF 融合、不参与精排候选。
代价是**那部分知识检索不到了** —— 但这是一种**准确的坏**，
比"虚假的好"（看起来检索到了，其实分数是噪音）强得多。

至于"检索不到"这件事本身，靠**启动告警 ＋ 指标**让人看见。
三条防线里，只有这一道是"每次都生效"的：自检只在启动时跑一次。

### 为什么 `unknown`（有向量但没记模型）要单独统计

两种"用不到"的**修法不一样**：

| 情况 | 含义 | 怎么修 |
|---|---|---|
| `mismatched` | 知道是哪个旧模型 | 换回该模型，或全量重嵌入 |
| `unknown` | 连模型名都没记 | **先搞清楚它是谁嵌的**，否则不知道往哪修 |

理论上 `unknown` 不该出现（两半总是同时写）。真出现就是历史遗留数据 ——
不把它算进"一致"里，是唯一安全的做法。

### 实测：这次改动**不改变现网行为**（有证据）

上线前查了两边库：

```
本地：total=471  with_vec=471  vec_but_null_model=0   model=qwen3.7-text-embedding-flash dim=1024
生产：total=231  with_vec=231  vec_but_null_model=0   同上
```

全部块早就是同一个模型、同一维度、没有空值 ⟹ 读侧过滤**一条都不会筛掉**。
所以这是一次"加安全网"而不是"改行为"的改动 —— 这一点是**查出来的，不是猜的**。

### 自检测试里的一个坑：它是**全库**扫的

`warn_if_embedding_lock_mismatch()` 默认遍历**所有有块的租户**（生产就该这样）。
但测试里如果不限定范围，它会把开发库里的真实数据也算进去 ——
于是"该安静"的用例会因为别人的数据而报警，测试变成依赖全局状态。

所以给它加了一个 `tenant_ids` 参数：**生产不传（全扫），测试传自己造的租户**。
📌 这是"给测试留一个入口"而不是"为测试改语义" —— 默认行为没变。

## 9.29 自研看板：**服务端代查**、指标口径，以及"看板挂了不影响业务"

v1.1 第 2 步。四组卡片：可用性与延迟 / 资源 / 问答与用量 / 限额与数据健康。
不做 Grafana 的理由在 §10.1（2C2G 上多一个 ~100 MB 的进程，而它给的东西我们用不上）。

### ① 为什么由**服务端**代查，而不是浏览器直连 Prometheus

Prometheus 的 9090 上**没有鉴权**，也没有限流。挂到公网等于送人一个 PromQL 执行入口
（`/api/v1/query?query=` 什么都能算，还能把 `rate()` 套在超大区间上当放大器）。
所以：**9090 不发布到宿主机**，`compose` 里只有 `expose`；浏览器永远够不到它。

代查的接口 `GET /api/v1/monitoring/snapshot` 只允许查 `app/api/monitoring.py::PANELS`
里写好的表达式 —— **客户端传不了 query**。这一条同时解决三件事：
没有 SSRF、没有任意查询、也没有人能拿它扫一遍整个时序空间（那会把 2C2G 打满）。

**代价**：加一个面板要改后端（写 PromQL ＋ 口径文案），不能在前端临时加。这是**故意的**：
面板里的每一条都得有人负责说清"这个数怎么来的"。

### ② Prometheus 挂了返回 **200 + `available=false`**，不是 5xx

看板取不到数据，最常见的原因是**监控还没启起来**或**容器刚重启** —— 那属于
"页面要显示的现状"，不是"接口故障"。返回 502 会让前端只能整页报错，
而正确的界面是：**橙色说明 ＋ 一句"业务本身不受影响"**（看板是旁路）。

判据：如果一个接口的失败**不影响主链路**，那它的失败就是一种**数据**，不是错误码。

### ③ 指标基数的两条纪律（`app/core/metrics.py`）

| 纪律 | 不这么做的后果 |
|---|---|
| `path` 标签用**路由模板**（`/api/v1/conversations/{conversation_id}`），不用真实 URL | 用户每建一个会话就多一条时间序列 —— Prometheus 内存会**慢慢**涨死，而不是立刻报错 |
| **不挂 `user_id` / `tenant_id` 标签** | 等于把基数交给用户数据决定。按人 / 按租户的用量在 **Redis** 里（配额页读那儿） |

404 归到 `__unmatched__` 一格：扫描器最喜欢打随机路径，那是现成的基数炸弹。

### ④ SSE 的"耗时"不是系统慢 —— 所以 P95 要分两块

`/api/v1/chat` 的请求在**整条流结束**时才落指标，所以它的耗时是
「用户从提问到看完回答」，量级 5~30 秒；而普通请求是几十毫秒。
混在一个 P95 里，看板会常年显示"P95 = 8 秒，系统很慢"——
**其实是流没关**，不是慢。所以面板分成「普通请求 P95」和「问答流 P95」两块。

### ⑤ 问答结果分三个**互斥**的桶：answered / refused / error

**拒答单独一桶**，因为拒答率突然升高通常意味**检索坏了**（阈值没变、库里却搜不到东西）。
混进"正常回答"里，这个信号就被稀释成"答得少了一点"。
`error` 也不能和拒答混：拒答是**产品行为**，出错是**故障**。

### ⑥ 中间件必须是**纯 ASGI**，不能用 `@app.middleware("http")`

那个装饰器背后是 `BaseHTTPMiddleware`，会给响应 body 包一层再转发。
而 `/api/v1/chat` 是 SSE 长流 ⟹ 症状是"流式变成一次性吐"，
且**本地直连看不出来、过 nginx 才明显**（和 §9.12 那类坑一模一样）。

所以 `MetricsMiddleware` 只观察 `http.response.start` 那一帧来拿状态码，
body 一个字节都不碰。并且记在 `finally` 里 —— 异常路径也要记 500，
否则"挂了"这件事在指标里**根本不存在**。

### ⑦ ⚠️ CD 里所有 compose 命令都必须带 `--profile monitoring`

`prometheus` / `node_exporter` 挂在 `monitoring` profile 下。**不带这个 flag 时，
它们不在本次操作的启用集合里**，而 `up -d --remove-orphans` 会把"不在集合里的容器"
当孤儿处理。后果很隐蔽：**每次部署都顺手把监控干掉**，日志里只有一行 orphans，
站点一切正常，只是看板空了。

所以 `deploy.yml` 里 **pull / up / logs / 回滚** 四处全部带上了它。
📌 这也是为什么两个镜像必须先补进 ACR（§9.21 的同一条道理）：profile 一启用，
`compose pull` 就真的会去拉它们。

### ⑧ 「不许裸数字」在看板上的四条落法

1. 每块卡片都印后端给的 `hint`（窗口多长、是分桶估算还是精确值、分母是什么）；
2. 整屏印**生成时间** ＋ **问的是哪台 Prometheus**；
3. 样本比 `stale_after_s`（3 个抓取周期）旧就**标黄** —— 十分钟前的数和十秒前的数
   长得一模一样，可信度却完全不同；
4. 缺数据显示 `—`，**不显示 0**（0 和"没有采到"是两件事）。

### ⑨ 页面**不自动刷新**

这是运维面，不是仪表盘墙。自动刷新会让人盯着一个 30 秒才更新一次的数，
误以为是实时；而且每刷一次就是 15 个 PromQL 打在生产上。刷新是显式动作。

### 代价 / 已知的不完美

| 不完美 | 为什么现在这样 |
|---|---|
| 没有历史回看 | Prometheus 只留 3 天（`--storage.tsdb.retention.time=3d`），2C2G 上不留长期数据；要看"上周三发生了什么"得另做落盘 |
| 没有告警静默 / 分组 | 我们自己只推**一条**告警（v1.1 第 3 步），不去引 Alertmanager；需要静默时按"临时关掉轮询脚本"处理 |
| 最细颗粒 30 秒 | 抓取周期就是 30 秒。它**不是实时监控**，页面自己也这么写 |
| 新面板要改代码 | 见 ① 的代价：每块面板都得有人写口径文案 |

## 9.30 告警：Prometheus 只负责**算**，推给人交给一个 60 秒的搬运工

v1.1 第 3 项。规则两条：`ApiScrapeDown`（抓不到 `/metrics` 持续 1 分钟）、
`LimitMeteringBroken`（限额因 Redis 不可用而**放行**的次数在涨）。

### ① 为什么不引 Alertmanager

它要**再加一个容器**（≈40 MB）＋ 一整套 route / receiver / inhibit / silencer 配置，
而我们要的只有两件事：**新出现的 firing 推一次、恢复了再推一次**。
2C2G 上这是"用一整套路由系统换两个 if"。

**代价（要认）**：没有分组、没有静默、没有抑制、没有重试队列。
真正需要这些时再引 —— 判据是"告警开始互相淹没"，不是"想用 Grafana 生态"。

### ② 分工：Prometheus 算状态，自研代码推消息

`/api/v1/alerts` 是 Prometheus 的**只读 HTTP 接口**，返回当前所有**活跃**告警
（含 `pending`）及 `state` / `labels` / `value`。所以我们不需要 Alertmanager 那套
webhook 机制：让 Prometheus 把规则算出来，再由 `app/core/alerts.py` 每 60 秒拉一次、
自己判断"哪些是新的、哪些消失了"。

**为什么放在 api 进程的 lifespan 里**（而不是新开一个容器）：api 本来就连着 Redis、
也已经知道 Prometheus 地址；多一个容器要多一份内存和多一处健康检查，而这件事
**每 60 秒只干一丁点活**。

⚠️ **代价说清楚**：搬运工跟着 api 一起重启（api 挂了告警也停）—— 但那时
`ApiScrapeDown` 正好会响，而这个响**没人推**。这是这套设计**真实存在的盲区**，
写在这里而不是装作没有。补法（挪进 worker）是"用一个容器换一个盲区"，暂不做。

### ③ ⚠️ **先推成功，再记账**

去重靠 Redis 的一个 set `gq:alert:active`（已知在 firing 的指纹）。
每轮算两个差集：`firing - active` 推"告警"、`active - firing` 推"已恢复"。

顺序**必须是**"先 POST 成功 → 再 `SADD`"。反过来的话，**推送失败的那一次会被记成
"已经通知过"**，于是这条告警**永远不会再推**。
判据：**静默丢失比重复推送严重得多** —— 重复只是吵，静默是"你根本不知道有这回事"。

⚠️ 同理，set 放 Redis 不放进程内存：api 每次滚动更新都会重启，
放内存就会把还在 firing 的告警**重推一遍**（部署越频繁，群里越吵）。

### ④ `pending` 不算告警

`/api/v1/alerts` 也返回 `pending`（还没走完规则里的 `for:` 时长）。
把 pending 当告警推 = **每抖一下就报一次**，很快没人看群了。
规则里的 `for: 1m~2m` 就是为了先滤掉抖动。

### ⑤ 报文按 URL 域名判断，且**用 text 不用卡片**

- 含 `open.feishu.cn` → `{"msg_type":"text","content":{"text":...}}`
- 含 `qyapi.weixin.qq.com` → `{"msgtype":"text","text":{"content":...}}`
- **认不出的域名按企微兜底**（text 最通用），不报错、不要求用户选。

卡片好看，但字段结构会随他们改版而漂；text 只依赖最稳定的那个字段。

⚠️ **留空 = 关闭**：`ALERT_WEBHOOK_URL` 为空时只打一行「告警未配置」就返回，
**不轮询、不报错** —— 可选功能缺失不能把"能用"变成"起不来"。

### ⑥ 内容只有四样：服务名 / 指标名 / 当前值 / 时间

⚠️ **不复用 `annotations`**。那里可以写任意自由文案，而它正是最容易把
用户提问、知识库片段、token 顺手带进群聊的地方。消息里的一切都从 `labels` 的
**白名单字段**取：`alertname` / `job` / `metric`（`metric` 是我们自己在规则里加的标签 ——
没有它，消息只能说"有条规则响了"）。测试里专门有一条：往 `annotations` 塞手机号，
断言它不出现在消息里。

### ⑦ ⚠️ 改了规则文件**必须显式重启** Prometheus（`/-/reload` 靠不住）

`prometheus.yml` / `alerts.yml` 是 **bind mount 进容器**的。改文件**不会**让 compose
认为服务定义变了（挂载源路径没变）⟹ `up -d` 不重建 prometheus，进程里还是**旧配置**。

第一版做法是打 `/-/reload`（compose 已开 `--web.enable-lifecycle`）——
**2026-10-19 端到端验收时发现它在 CI 里静默没生效**：Prometheus 日志里一条 load 记录都没有，
而这一步末尾还挂着 `|| echo 跳过`，于是"规则没更新"**完全没有痕迹**：
正式规则迟迟不生效，告警继续按临时阈值在跑，直到人工 reload 才恢复。

📌 **结论：`|| 兜底成功` + 看不见的通道 = 静默失效。** 这和本项目其它坑是同一个病。
⟹ 改成**确定性动作**：`docker restart gq-prometheus`（容器不存在会直接非零），
再轮询 `/-/healthy` 确认它回来了 —— 规则文件写错的话它根本起不来，这一关会红。
代价：**每次部署 Prometheus 重启约 5 秒**（监控短暂中断，`promdata` 卷不受影响）。

⚠️ 9090 **没有发布到宿主机**，所以"看它有没有起来"也只能在容器里探测（同 §9.29 ①）。
⚠️ **`alerts.yml` 必须和 `prometheus.yml` 同一次 scp**：`rule_files:` 指向它，
只传后者的话 Prometheus 会因为找不到规则文件而**起不来**。

### 已知的不完美

| 不完美 | 为什么现在这样 |
|---|---|
| 没有重试队列 | 推送失败在下一轮（60 秒）自然重试；真正的重试要持久化 + 退避，为一个 webhook 不值 |
| 没有静默 / 抑制 | 要临时闭嘴就清 `gq:alert:active` 或把阈值调高；抑制需要"谁压住谁"的模型，现在只有两条规则 |
| resolved 不带当前值 | 那时 Prometheus 已经不返回这条了；它要回答"好了没"，不是"多少" |
| api 挂了就不推 | 见 ② 的盲区 |

## 9.31 配额页：**只读一份账，不新开计量**

v1.1 第 2 项。`GET /usage/me`（所有人看自己的）＋ `GET /usage/tenant`（仅管理员看本租户）。

### ① 不新开一套计量：token 只有**一个写入口**

token 是 `app/core/limits.py::add_tokens` 在**回答结束时**写进 Redis 的
（`gq:quota:{user_id}:{YYYYMMDD}`，TTL 2 天）。配额页只**读**它。

"页面上再算一遍"是最容易让两处数字对不上的做法：配额页算 5,000、限流器算 5,200，
用户就会在"明明还有额度"的时候被 429。**同一件事只能有一个写入口**。

### ② 为什么另写了 `peek_quota`，不复用 `read_quota`

`read_quota` 是**准入判断**用的，它有一个副作用：超额时给 `gq_limit_denied_total` 加一。
拿它来渲染页面 ⟹ **看一眼配额页就等于"被拒一次"**，那个指标立刻失去意义。

所以加了 `peek_quota` / `peek_rate`：**只看账，什么都不改**。
📌 判据：一个函数如果"读一次"会改变别的东西，它就不是查询函数 ——
别因为"反正逻辑一样"就复用。

### ③ ⚠️ 取不到就是 `None`，不是 0

Redis 不可用时 `peek_quota` 返回 `None` ⟹ 页面显示 `—` 并附一句"**这不是 0**"。

这条和全项目的「不许裸数字」是同一条：**"不知道花了多少"和"没花"是两件事**。
显示 0 会让人以为额度还很足，然后下一次提问就被 429 打脸 —— 那是最难解释的一种体验。

### ④ 只算**问答**的 token（这是口径，必须印在页面上）

embedding / rerank 是**按次计费**，和"用户发了多少字"完全不成比例：
一次上传会打几十次 embedding，而它们没有 `usage` 字段可累加。
把两者混进"用户配额"里，那个数字**既不能解释、也不能和账单对上**。

所以口径写死一句：*只统计问答消耗的 token（模型回报的真实 usage；拒答不调模型 ⟹ 0）；
embedding / rerank 不在这个数里*，并**原样显示在页面上**。

### ⑤ 成本要**单价**，而且必须把单价印出来

`LLM_PRICE_PER_MILLION_TOKENS` 默认 **0 = 不折算**。理由：各家价格会变，
写死一个数字比不给更糟（三个月后它就是个错误答案）。
配了之后页面显示"估算 ¥x.xxxx（按 ¥N / 百万 token 估算）" —— **一个不带单价的金额是不可解释的**。

⚠️ 它只影响**展示**，不参与任何限流 / 熔断。

### ⑥ 租户视图的边界

管理员看的是 `admin.tenant_id` 下的用户 —— **租户内的**管理员，不是跨租户超管。
测试里专门有两条：别人租户的成员**不许**出现（哪怕他用量更高）；普通成员访问 `/usage/tenant` 得 **403**
（403 不是 404：这里"有没有这个接口"不是秘密，`/usage/tenant` 本来就存在，只是角色不够）。

### ⑦ 逐个用户读 Redis，不打 MGET

用户数是"一屋子客服"的量级，多几次往返无所谓；换来的是**键的构造只有一处**
（`limits._quota_key`）—— 用 MGET 就得在别处再拼一遍键，那是一份必然漂移的副本。

### 已知的不完美

| 不完美 | 为什么现在这样 |
|---|---|
| 只有今天，没有趋势 | 记账 TTL 2 天（`add_tokens` 里定的）。要做趋势得先落盘成表 —— 而那正是 ③ 备份恢复演练之后更值得做的事 |
| 不按文档 / 会话拆分 | 那要给每次调用加维度（多写几个键 + 基数上涨），现在只有"按人"这一个问题需要回答 |
| 成本是估算，不是账单 | 单价是配置项、模型可能有阶梯价 / 缓存价；真实账单只能以云厂商为准 |

## 9.32 备份与恢复演练：**备份的价值只有恢复过才算数**

v1.1 第 3 项。`deploy/ops/backup.sh`（pg_dump ＋ 轮转）＋ `deploy/ops/restore-drill.sh`
（恢复到临时库、逐表比行数）＋ 服务器上的 **systemd timer**（每天 03:00）。

### ① 为什么是 `pg_dump -Fc` 而不是 `pg_dumpall` / 直接拷数据目录

| 方案 | 为什么不选 |
|---|---|
| `pg_dumpall` | 连角色 / 表空间一起导，恢复时**要动全局对象**；我们只需要"这一个库" |
| 直接 `cp -r` 数据目录 | **必须停库**才能拿到一致快照；而且版本 / 平台一变就打不开 |
| **`pg_dump -Fc`** | 逻辑一致快照、**不停库**、自带压缩、能选择性恢复（`pg_restore -l/-t`） |

⚠️ 恢复需要 `CREATE EXTENSION vector` 权限 —— 容器里的 `POSTGRES_USER` 是超管，够用。

### ② 校验的是「读得动」，不是「文件在」

`backup.sh` 做两件事而不是一件：
1. `SIZE >= 10000`（0 字节的 dump 也能 `ls` 到）；
2. `pg_restore -l < dump` 能列出目录 —— 这一步才证明**这个文件是一个能用的 dump**。

⚠️ 还有一条容易漏的：**先写 `.part`，校验通过再改名**。
否则一次中断会留下"看起来像备份"的半截文件，而还原脚本按时间取的就是最新那份。

### ③ 轮转按**份数**，不按天数

"保留 7 天"在"连续 7 天备份都失败"的情况下等于**一份都没有**。
按份数保留，至少保证「最近 N 次**成功的**备份都还在」。`KEEP=7`（1.1 MB/份，共 ≈ 8 MB）。

### ④ 调度用 **systemd timer**，不是 cron

这台机器上 `cron` 服务**根本没在运行**（`systemctl is-active cron` → inactive）。
与其为了一个定时任务去启用一个平时不用的服务，不如用**已经在跑**的 systemd：

```ini
# /etc/systemd/system/grounded-backup.timer
[Timer]
OnCalendar=*-*-* 03:00:00
Persistent=true        # 关机错过 03:00，开机后补跑 —— 否则"那天没备份"没有任何痕迹
RandomizedDelaySec=5m
```

📌 `Persistent=true` 是这条的**关键**：这台机器会重启（我们今天就重启过一次），
没有它，"错过的那次"会被**静默跳过**。

### ⑤ 恢复演练：**只碰自己建的临时库**

`restore-drill.sh` 恢复到一个 `gq_drill_<UTC时间戳>` 的**临时库**（带时间戳：连跑两次不撞车、
也不会误删别人的库），比完行数就用 `trap` 删掉。

比对的不只是行数，还有**结构**：
- 扩展 `vector` / `pg_trgm` 在不在；
- `chunks.embedding` 列在不在、**带向量的块数**是否一致。

⚠️ 只看行数会漏掉最要命的一种坏法：**数据都在，但向量没了** ——
那样的库"看起来完整"，检索却一条都命中不了（正是 §9.28 那个静默失效）。

**2026-10-19 首次实测结果**：documents 35 / chunks 231 / users 1 / conversations 1 / messages 4
**全部一致**；扩展 3 个齐全；`chunks.embedding` 存在且 **231 块全带向量** ⟹ `PASS`。

### 已知的不完美

| 不完美 | 为什么现在这样 |
|---|---|
| **备份和库在同一块盘上** | 防的是"误删 / 迁移出错 / 库被写坏"，**不防磁盘故障**。异地/对象存储要引 OSS SDK ＋ 凭据管理，v1.1 不做 |
| 没有 WAL 归档 / 时间点恢复（PITR） | 那是"恢复到某一条 SQL 之前"，要开 `archive_mode` ＋ 持续上传；每天一次全量对本项目的量级够用 |
| 没在恢复后跑一遍业务自检 | 现在比的是行数与结构，没有再发一次提问验端到端（那要调模型、要钱）。要验就跑一次人工提问 |
| 演练**不自动**跑 | 定时跑的是备份；演练是**手工**的（`deploy/ops/restore-drill.sh`）。自动化它要先决定"恢复了往哪放"，暂不做 |

## 9.33 压测：**先证明测量可信，再谈优化**

v1.1 第 4 项。脚本 `scripts/ops/loadtest.py`（固定并发打一个接口，出吞吐与分位数），
证据在 `docs/evidence/loadtest-*.json`。

### ① 量什么、不量什么

**不压 `/api/v1/chat`**：它要调模型、要花钱，而且耗时由上游决定 —— 量到的是 DeepSeek 的延迟，
不是我们的。压测要压**我们能改的那部分**。

打的是 `GET /api/v1/conversations`：JWT 校验 ＋ **一次真 DB 查询** ＋ 序列化，
能代表"业务请求里我们自己那部分开销"；而且它**没有限流**（问答 30/分钟/用户那条会先把自己撞成 429，
测出来的是限流而不是性能）。`/healthz` 作为对照组，量"纯框架开销"。

### ② 两组数（本机 12 核；20 并发 × 12 秒；**交替测量**）

| 配置 | 吞吐 | p50 | p95 |
|---|---|---|---|
| `pre_ping=on` 第 1 次 | **358.5 req/s** | 31.1 ms | 90.6 ms |
| `pre_ping=off` 第 1 次 | 346.8 req/s | 31.2 ms | 98.5 ms |
| `pre_ping=on` 第 2 次 | 338.1 req/s | 48.6 ms | 137.1 ms |
| `pre_ping=off` 第 2 次 | 329.5 req/s | 31.9 ms | 184.8 ms |
| 对照：`/healthz`（无鉴权无 DB） | 508.5 req/s | 20.4 ms | 125.3 ms |
| **生产**：`/healthz`，5 并发 × 10 秒 | **289.9 req/s** | **16.5 ms** | **21.8 ms** |

📌 生产那组的 **p99 只有 25 ms、错误 0** —— 低并发下 2C2G 这台机器很轻松。

### ③ ⚠️ 我第一次量出来的「+22%」**是假的**

第一轮顺序是 "on → off"，结果 `off` 比 `on` 快 25%（274 → 347），
看起来是个漂亮的优化。**但那是冷启动污染**：
第一次跑的时候，uvicorn 刚起、PG 的连接还没建立、查询计划还没缓存 ——
它比的是「**冷** vs **热**」，不是「A 配置 vs B 配置」。

改成**交替测量**（on → off → on → off）之后，差异**完全消失**（358/338 vs 347/330，
差异小于同一配置两次之间的波动）。

📌 **教训：任何"优化前后"的数字，只要两次测量的环境状态可能不同，就必须交替取，
并且至少各测两次。** 单次对比几乎一定会把"环境漂移"读成"优化效果" ——
而这正是最容易被写进简历、然后在面试里被追问到崩的那种数字。

### ④ 为什么这次**测不出** uvicorn worker 的扩展性

| workers | 吞吐（各测两次/一次） |
|---|---|
| 1 | 298 / 344 req/s |
| 2 | 400 / 287 req/s |
| 4 | 285 req/s |

数字在 285~400 之间乱跳，**差异被波动盖住**。原因不是服务器没扩展，而是
**测压机和服务端在同一台机器上**：Python 单进程的 httpx 客户端自己就顶在 ~350 req/s 左右，
两台"抢同一批 CPU"。要测真容量必须**换一台机器当测压机**（或用 `wrk` / `k6` 这类低开销工具）。

⟹ **所以这次没有任何"优化"上线。** 见下一条。

### ⑤ 结论：把旋钮做成配置，但**默认值不动**

`POSTGRES_POOL_SIZE` / `POSTGRES_MAX_OVERFLOW` / `POSTGRES_PRE_PING` / `POSTGRES_POOL_RECYCLE`
四个都进了配置（**为了能测**，也为了线上能临时调），但默认值保持原样：
`5 / 5 / true / 1800`。

理由是数据：池大小与 `pre_ping` 在交替测量下**都没有可分辨影响**，
而 `pre_ping=True` 是"池里的死连接不会变成一次用户可见的 500"的保险 ——
**没有证据支持的改动，不做**。

📌 真实容量参考：业务接口 ≈ **300~350 req/s**（本机单进程），生产 `/healthz` 在 5 并发下
290 req/s、p99 25 ms。而实际流量是"几个人在问问题"—— 余量在**两个数量级**以上。
这个项目现在**没有性能问题**，需要的是"知道瓶颈在哪、以及怎么量"，而不是提前优化。

### 已知的不完美

| 不完美 | 为什么现在这样 |
|---|---|
| 测压机与服务端同机 | 只有一台开发机。换独立测压机才能测出"加 worker / 加机器"的真实扩展曲线（`CANDIDATES.md` 记了一条） |
| 没压 SSE 问答流 | 那要真的调模型（花钱且不可复现）。它的耗时口径已经在看板上单列（§9.29 ④） |
| 没做阶梯加压 / 拐点分析 | 固定并发只回答"这个并发下多少吞吐"；找拐点要阶梯 + 更长时长，价值低于它花掉的时间 |

## 9.34 闭卷/开卷对照：**"RAG 有用"这句话必须能被量出来**

v1.2 第 3 项。实现：`RagPipeline(closed_book=True)`（`app/rag/pipeline.py`）＋
`evals\run.py --mode {open,closed,both}`（同一批题、同一个模型、同一个判分器）。
证据：`evals\results\contrast-*.json` ＋ 两侧的 `generation-{open,closed}-*.json`。

### ① 要回答的问题

面试里最锋利的一句是：**"你把检索去掉，模型是不是也能答对？"**
这句话不是质疑工程质量，而是质疑**这个项目的存在意义** —— 而它只能靠一组对照实验回答，
不能靠"我们检索命中率 1.000"来回答（命中率高只证明**检索**对，不证明**检索对回答有用**）。

### ② 三个天真做法，以及为什么都不行

| 天真做法 | 会发生什么 | 那测到的是什么 |
|---|---|---|
| 只报开卷分数 | 无法证明检索有贡献 | 模型 + 提示词的综合能力 |
| 闭卷 = 把【参考资料】填成"（无）" | 开卷提示词第 1/3 条写着"只依据参考资料""不足就说不足" → 模型**照着提示词把每道题都拒掉** | **提示词服从性**，不是参数化记忆 |
| 闭卷另写一套调用代码 | 差值里混进"两套实现"的噪音（超时、重试、message 拼法都可能不同） | 两份代码的差异 |

所以闭卷必须：**换提示词（这是处理本身）＋ 同一段代码（这是控制变量）**。

### ③ 具体怎么做的

| 维度 | 开卷（线上） | 闭卷（对照组） |
|---|---|---|
| 检索 / 精排 | 混合检索 → RRF → rerank | **完全不调**（embedding / rerank 一次不碰） |
| 提示词 | `SYSTEM_PROMPT`（"只依据【参考资料】"+ 标 `[n]`） | `CLOSED_BOOK_SYSTEM_PROMPT`（允许用先验知识，允许说"不确定"） |
| 拒答 | 按置信度阈值判定（调模型之前） | **不判**：没有检索就没有分数，"一律拒答"是 0 分基线，不是基线 |
| 引用 | 发 `[n]` 并核对 `must_cite` | **没有引用**，`cite_ok=None`（判引用等于判它作弊） |
| 语言 / 简洁 / 不提内部词汇 | 三条要求**两边完全一样** | 同左 |

📌 闭卷的第二条规则（"不确定就说明不确定，但给出你认为最可能的回答"）**故意偏袒开卷**：
它把闭卷推向"更容易编"。这不是抹黑对手 —— 一个不用 RAG 的模型在真实客服场景里就是这样表现的，
它不会因为不知道就闭嘴。想量"不许猜"的极限，那组实验恒为"全部拒答"，没有信息量。

### ④ 2×2 实测（2026-10-20，两库各 20 题，单次运行）

| 知识库 | 闭卷要点全中 | 开卷要点全中 | **差值** | 要点命中率（闭→开） | 引用对 |
|---|---|---|---|---|---|
| **A · FastAPI 官方文档**（公开，15 篇 / 279 块） | 13/20 = **65%** | 18/20 = **90%** | **＋25 pt** | 79.5% → 94.9% | 20/20 |
| **B · 自造跨境家居语料**（私有，35 篇 / 231 块） | 1/20 = **5%** | 14/20 = **70%** | **＋65 pt** | 26.3% → 90.8% | 20/20 |

**两个知识库的差值差 40 个百分点** —— 这就是 `PLAN §7.2` 事先写下的预测（A 差值小、B 差值大），
而且是**先写下、后验证**的，不是事后凑的解释。

| 数字 | 说明 |
|---|---|
| A 库闭卷 65% | 模型**本来就背过** FastAPI → 不给文档也能答对大半。**这正是"拿公开文档当成绩"会自欺的原因**（`AGENTS §7.1` 约定 1 的实证） |
| B 库闭卷 5% | 虚构公司的条款不可能"背过" → 20 题里只有 1 题碰巧全中 |
| 引用 20/20 | 开卷在**两个库**上引用都指得对；闭卷没有引用可比 |

> ⚠️ **单次运行，±1 题的抖动是有的**：B 库开卷在 10-17 是 14/20、今天 14/20，中间有一次 13/20。
> 25 题级别的题集不足以谈小数点后的差异（同 §9.23 的结论）。

### ⑤ 闭卷不是"说不出"，而是**自信地编** —— 这是幻觉的直证

判分器里 `must_not_say`（禁语）**一条都没命中**（闭卷 0/20、开卷 0/20），
但这**不代表闭卷没有幻觉**，只代表"整句子串匹配"抓不住改写后的编造。
所以另加了一个弱指标：**回答里有没有出现数字**。

| | 闭卷 | 开卷 |
|---|---|---|
| B 库含数字的回答 | 18/20 | 20/20 |
| B 库要点命中率 | **26.3%** | 90.8% |

**它张嘴就给具体数字，只是数字是编的。** 原文照抄两条（`generation-closed-*.json`）：

- `gen-09 包邮门槛是多少？` → 闭卷答"**普通地区订单实付满 99 元包邮**"。
  实际是 **美国 $59 / 德国 €69 / 日本 ¥8000 / 新马 S$80**，没有任何一个地区是 99。
- `gen-10 各站点配送要多久？` → 闭卷答"同城 1–2 / 省内 2–3 / 跨省 3–5 / 偏远 5–7 个工作日"。
  **整段都是编的**，而且它还发明了一个这家公司不存在的维度（同城/跨省 —— 人家是跨境）。

📌 这解释了为什么**拒答必须由确定性代码在调模型之前判**（`AGENTS §7.1` 约定 17）：
让模型自己"拿不准就不说"，它会在**最该闭嘴的地方**给你一张排比工整的表。

### ⑥ A 库的闭卷分数也不是"检索能力差"，是**知识过时**

`fa-01 Which command starts the dev server?` → 闭卷答
`uvicorn main:app --reload`。文档里现在写的是 **`fastapi dev`**（0.105+ 的推荐写法）。
模型的参数化记忆停在旧版本上，**这类"版本敏感"问题恰好是企业做 RAG 的真实动因**
（`PLAN §7.2` 那句"增益集中在私有 / 长尾 / 版本敏感的知识上"，这里有了具体样本）。

### ⑦ A 库为什么单独一个数据库

检索层**没有"按知识库过滤"**的能力 —— `HybridRetriever` 只在租户范围内检索，
`kb` 只是 `documents.filename` 的前缀（评测脚本用它把 chunk 折算成文档路径）。
把 279 块 A 库语料塞进 B 库那个库，A 库的题会**召回 B 库的 chunk**：
候选被无关内容挤占，开卷分会变低 —— 那会把"公开知识增益小"这个结论**做成假的**。

所以 A 库跑在**独立数据库 `gq_kb_a`** 里（`CREATE DATABASE ... LC_COLLATE 'C.UTF-8'` ＋
`alembic upgrade head` ＋ `seed` ＋ `ingest --kb fastapi`），跑的时候用
`POSTGRES_DB=gq_kb_a` 覆盖（**环境变量优先于 `.env`**）。
⚠️ 这只是本地开发库；生产仍然只有 B 库。

### ⑧ 判分器的三条实用规矩（写新题集时照这个来）

要点判分走的是"**有数字/拉丁词就以它们为准**"（§9.24），于是：

1. **每条要点至少含一个数字或英文标识符** —— 否则会掉进"中文二元组覆盖率"那条路，
   而英文回答的中文二元组几乎是 0，**必然判错**。
2. **要点写成中文句子 + 嵌入准确的英文标识符/数字**，不要写成英文句子：
   `It uses Depends to inject` 会让 `uses / Depends / to / inject` **四个词都变成必含原子**，
   回答少一个就判错。写成 `用 Depends 注入依赖` 则只有 `Depends` 是原子。
3. **禁止用语（`must_not_say`）要写目标语言**：给英文回答配中文禁语，等于没配（子串永不命中）。

### 已知的不完美

| 不完美 | 为什么现在这样 |
|---|---|
| `must_not_say` 抓不住改写后的编造 | 整句子串匹配；换成"数字核对"或 LLM 判官都会引入新的不可复现性。当前的替代是**看样例 + 含数字率** |
| A 库只有 **279 块**（15 篇 tutorial），不是计划书写的"1 万 chunk" | 1 万块的用途是**证明工程规模**；对照实验只需要"这是公开知识"这个性质。⚠️ 面试若被问"1 万块呢"，要如实说这是**语料子集** |
| 单次 20 题 | ±1 题抖动。要更稳只能扩题集，成本主要在我写题的时间，不在 token |
| 闭卷不与"检索质量"解耦 | 闭卷分低可能来自"没证据"，也可能来自"提示词不同"。要分离得再加第三个对照（给**随机**证据），记在 `CANDIDATES.md` |

### 顺手修的坑：包装器签名漂移

`evals\run.py` 的 `SpyChat`（数模型调用次数的包装器）在 `ChatClient.stream()` 加了
`usage` 参数之后**没跟着改**，于是 `--layer generation` 一跑就
`TypeError: stream() got an unexpected keyword argument 'usage'` ——
而这行**不在** `ModelAPIError` 的捕获范围里，整批直接崩。
📌 教训：**包装器的签名要盯住被包装对象**；对方"加个可选参数"是向后兼容，但包装器会把它挡住。

### ⑨ 判分尺子本身也得被测（v1.4 B1）：数字按**集合**比，不按子串找

改之前：要点里的"数字/百分比/拉丁词"被抽成**字符串**，再在回答里找**子串**：

```
要点 "家具主体 2 年"  →  原子 ["2"]  →  回答里有没有 "2"？
```

这个尺子两头都错，而且**错得看不出来**：

| 方向 | 例子 | 后果 |
|---|---|---|
| **太松**（真阳性丢失） | 回答写"保 **20** 个月"或"**2024** 年起算" | 里面有 `2` → 判**通过**。答错的题被记成答对，分数只涨不跌 |
| **太严**（假阴性） | 回答写"**两年**"或"**24 个月**" | 没有 `2` → 判**失败**。答对的题被记成答错 |

改成 `(族, 换算后数值)` 的**集合比对**（`_numeric_atoms`）：

| 规则 | 为什么 |
|---|---|
| `1 年 = 12 个月`、`1 天 = 24 小时` **换算** | 两种说法是同一个政策；不换算的话"同义改写"照样判错 |
| **月 ↔ 天不换算** | `30 天 ≠ 1 个月`（2 月只有 28 天）。拿约等号判分，会把"120 天"和"4 个月"判成同一个 |
| **工作日**独立一族 | "3 个工作日"和"3 天"是两回事，话术里经常同时出现 |
| 区间 `3~5` 拆成**两个**原子 | 只答一端就是没答全 |
| **中文数字只有带单位才算数量** | `一层`、`一次`、`同一`、`统一` 里的"一"不是数据 —— 不挡的话，要点"多一层 `item` 键"会要求回答里有数字 1，**实测误杀 4 题** |
| **钟点（`09:00`）整段忽略** | 它是格式不是数值；`_norm` 会把冒号抹掉，回答里的 `0900` 和要点的 `09:00` 永远对不上 —— **实测误杀 1 题** |
| **拉丁词仍按子串**判（不改成词集合） | `_norm` 抹空格，`fastapi dev` 在回答里粘成 `fastapidev`；按词比**实测误杀 3 题** |

📌 **验收口径：先证明"零回归"，再谈"更准"** —— 拿已经存下来的回答用 `--rescore` 重判
（同一批回答、只换尺子）：

| 结果文件 | 旧口径 | 新口径 |
|---|---|---|
| `generation-open-20261019T164323Z`（A 库 20 题） | 18/20 | **18/20** |
| `generation-open-20261019T164100Z`（B 库 20 题） | 14/20 | **14/20** |

**一模一样** —— 这批回答本来就写得直白，尺子变严/变松都碰不到它。
所以 B1 的价值不在"分数变了"，而在**新题集（B2 的 65 题）不会被同义改写绕过**，
以及"答错的题不会因为里面恰好有个 `2` 被记成答对"。

⚠️ **顺手逮到一个静默 bug**：`--rescore` 原来把题集写死成 `generation.yaml`。
拿去重判 A 库（题号是 `fa-01…`）时**一题都对不上**，于是写出一份 **0/0 的空报告并显示成功**。
现在：题集/模式/知识库一律**从结果文件里读**，且"一条都没重判上"直接**失败退出**。

📌 这一节的教训可以推广成一句：**当你用一把尺子去改另一把尺子时，先让它复现旧结果。**
复现不了，你分不清"新尺子更准"和"新尺子坏了"。

### ⑩ 题集扩到 60 题：**靶纸本身必须可核对**（v1.4 B2）

检索题集从 25 道扩到 **60** 道（新增 35 道，覆盖物流税费 / 会员营销 / 服务 / 历史版本 /
未生效草案 / 内部稿 / 相邻概念）。扩题的过程暴露了一个比"题够不够多"更要紧的问题：

> **`must_hit` 是一句无法核对的主张。**

它说"这道题的答案写在这篇里"，但**没人验证过**。标错的后果特别坏 ——
标成一篇压根没写答案的文档，那题永远 0 分，看起来却像"检索能力差"；**不报错，只是分数悄悄失真**。

所以新题每条都带 `evidence:` —— **答案在文档里的那句原文**，并由
`tests/test_retrieval_questions.py` 逐条断言"这句话真的在 `must_hit` 的某个文档里"：

| 检查 | 失败意味着 |
|---|---|
| id 连续、问句不重复 | 题集被复制粘贴搞乱了 |
| `must_hit` 路径真实存在 | 文档改名 / 路径写错（检索评测会**静默**把它算成漏召回） |
| 新题都带 `evidence` | 又出现了"无法核对的主张" |
| `evidence` 逐字出现在文中 | **`must_hit` 标错或证据抄错** —— 这条一起红，靶纸就还算可信 |

📌 这一条把"请人逐题审"变成了**机器每次都审**。人只需要判断一次"这句原文是否回答了这道题"，
而"原文是否在文里"这种事不该靠人眼。

**60 题的实测**（B 库 · `scope=current` · 今天 · 一次运行）：

| 消融 | hit@5 | MRR@10 | 25 题时 |
|---|---|---|---|
| fulltext | 0.567（34/60） | 0.368 | 0.720 |
| vector | 0.933（56/60） | 0.783 | 0.960 |
| rrf | 0.917（55/60） | 0.713 | 0.920 |
| **rerank** | **0.983（59/60）** | **0.885** | 1.000 / 0.9600 |

⚠️ **数字比 25 题时低，这是对的** —— 样本大了 2.4 倍，且新题故意覆盖了以前没测的地方
（未生效草案 / 内部稿 / 相邻概念）。旧的 1.000 是"25 道题的 1.000"，不是"系统的检索准确率"。

⚠️ **已知漏召回 1 题**：`ret-51`（开箱视频能不能剪辑）在 rerank 组仍召不到 ——
出处只在内部判定标准里。**故意留着**：它是真短板，删掉只会让分数好看（要修就修检索，不许改题）。

## 9.35 提问带图：图只做「线索」，**不进向量空间**

v1.2 第②项。代码：`app/rag/vision.py`（读图）＋ `app/images.py`（文件）＋
`app/orders.py`（订单通道）＋ `app/api/chat.py::_prepare_image`。
评测：`evals\run.py --layer image`，真值 `evals\fixtures\images.meta.yaml`。

### ① 先划清三种模式，本期只做第一种

| 模式 | 图是什么 | 谁的主场 | 本期 |
|---|---|---|---|
| **A · 线索型** | 图是**指代**（"这个能退吗"里的"这个"） | VL（要读懂"是什么东西、什么状态"） | ✅ **做了** |
| **B · 提取型** | 图是**待处理对象**（合同/发票/单据/扫描件，要逐字保真） | **OCR**（VL 会顺手改写，不能当原文） | ⏸️ 等 OCR 供应商 |
| **C · 证据型** | 图里**就是答案**（产品照片当知识库） | 多模态向量 + 图检索引擎 | ❌ 不做 |

📌 分清这三者比"支持图片"这个说法重要得多：它们的数据面、失败模式、评测口径**完全不同**。
把 B 当 A 做，会得到一个"读得挺像但抄错数字"的功能；把 C 当 A 做，会得到一个**没人用的图库**。

### ② 为什么不建多模态向量（qwen-vl 那一格）

图向量能插的位置只有三个：**替换**文本 embedding（等于把整个 RAG 换成多模态库）、
在检索里**加一路**（RRF 只吃名次，技术上能放）、或**另起一个库**（"两个 RAG"）。
三个都不划算，原因是价值判断而不是技术判断：

> **图检索的价值 = 只有当知识**只**存在于图里时才成立。**

而我们的知识库 **0 张图**（35 篇全是 markdown）。为 7 张**测试图**建一套跨模态检索，
是在解决一个不存在的问题 —— 而且会立刻付三笔账：rerank 失效（它只吃文本对）、
引用溯源失效（用户点开看到的是图，没法定位到"哪句话支持了这个结论"）、
拒答阈值失效（新空间的分数分布完全没标定过）。

📌 真要做的判定条件（写进 `CANDIDATES.md`）：**≥100 张知识库图片 ＋ 真实"以图找图"需求**。
那时也要**加一路、不换空间**，并且图块必须配 caption（让文本那一路也能召回它）。

### ③ 读图是**一次调用、两段输出**

天真做法是"先分类再路由"：文字图走 OCR、情景图走 VL。那要**两次模型调用**（图 token 翻倍），
分类错了还要回退。这里一次调用同时产出两类信息 —— 实拍照片看 `scene`，
文书截图看 `transcription`：

```json
{"image_type": "...", "scene": "纸箱一角压瘪并撕裂",
 "transcription": "订单号：SF10001", "has_exact_fields": true}
```

⚠️ **同一套提示词必须同时覆盖两类图**：只按"破损照片"写，订单截图会被硬套成"描述一张图"；
只按"单据"写，照片会被要求"转写文字"（然后给空字符串）。

### ④ 三条数据面，隔离级别**各不相同**

| 数据 | 归属 | 过滤 |
|---|---|---|
| 知识库（`documents`/`chunks`） | **租户共有** | `tenant_id` |
| 订单（`orders`） | **用户私有** | `tenant_id` ＋ **`user_id`** |
| 图（`images`） | **用户私有，且跟着一条消息** | `tenant_id` ＋ **`user_id`** |

⚠️ **图绝不进 `chunks`**：知识库是租户共有的，图是某个人的附件。混进去的后果不是"检索变差"，
而是**A 用户上传的图出现在 B 用户的检索结果里** —— 那是越权。
📌 判据也很简单：上传前后 `chunks` 行数必须不变（验收第 6 条）。

⚠️ 订单是本项目**第一条"租户内按用户"**的读取路径（`AGENTS §7.1` 约定 13 早有这个概念，
但从没有代码）。查不到 / 不是本人的 → **一律 404**，和查别人的图同一条纪律。

### ⑤ 检索 query 只用 `scene` 和原话，**不用转写、不用单号**

```
检索 query = scene + 用户原话        （PLAN §8.3 D6）
转写与单号  →  只进"生成上下文"，不进检索
```

三个理由：
1. **转写里是精确串**（单号、金额、错误码），对 `pg_trgm` 和向量都**没有语义**，
   塞进 query 只会稀释原话的召回；
2. 单号有**专门的通道**（精确查 `orders`），不需要在检索里碰运气；
3. 用户只写"这个能退吗"（4 个字）时，`scene` 补上的正是它缺的语境 ——
   **这是带图提问真正值钱的地方**，也是评测里"带图 2/3 vs 不带图 0/3"的来源。

### ⑥ 三种降级，**都必须显式**

| 情况 | 行为 | 为什么不能"悄悄算了" |
|---|---|---|
| 读图 API 挂 | 明说"图片没读成功，我只按文字回答"，`sources.image.error` 带给前端 | 用户会以为我们看过图了 —— 那是**假装**读了 |
| 模型没按 JSON 回 | 整段当 `scene`，记 `fallback=true`，**不抛** | 一次格式问题不该毁掉整条问答；但降级必须可统计 |
| 文件丢了（库里有行、卷上没有） | 500 ＋ 日志 | 数据不一致是服务端问题，不能装成"图里没内容" |

### ⑦ 多轮：图只对它那条消息生效，但**读数会变成文字记忆**

模型**看不到图**（历史里只有文字）。所以如果什么都不做，用户追问"那多久到账"时，
模型完全不知道刚才有张图 —— 会答"我没有看到图片"。

做法（`PLAN §8.3` 新增 1）：图/订单的读数压成一句话存进**用户消息的 `meta`**：

```json
{"image_id": "...", "image_note": "用户发来一张图：纸箱压瘪撕裂；图中文字：订单号 SF10001",
 "orders": [{"order_no": "SF10001", "status": "delivered", ...}]}
```

追问时靠它恢复上下文，**不重调读图模型**（省钱、且输出稳定）；检索 query 仍然只用**当前原话**。
📌 `meta` 与 `content` 分开是刻意的：`content` 永远是**用户原话**，混进机器生成的文字
会让排障、评测、前端渲染三处都失真。

### ⑧ 送模型的那份副本：**缩，但要保住字**

| 原图 | 处理 | 理由 |
|---|---|---|
| 长边 ≤1600 且 ≤1 MB 且没 EXIF 旋转 | **原样发送** | 一次重编码都不做，评测才可复现 |
| PNG（截图/文书） | 只缩尺寸，**仍存 PNG** | JPEG 会在细笔画字边缘产生振铃，"1/7""8/B" 容易糊 |
| JPEG/WEBP（照片） | 长边 1600 ＋ q88，仍超 1 MB 再退一档 | 照片对这点损失不敏感 |

⚠️ **先做 EXIF 转正**：手机照片常常是"横着存 + 一个标记说请旋转 90°"。不转正，
模型看到的是**躺倒的图**，而且它**不会报错** —— 只会给你一段看起来像胡说八道的转写。

### ⑨ 实测（2026-10-22，7 张 fixture）

| 指标 | 结果 |
|---|---|
| **读图硬断言** | **7/7**（必须字符串全中 ＋ 场景命中），骨架归一化后比较 |
| **答案层：带图** | **2/3** |
| **答案层：不带图** | **0/3** |

📌 三个问题都是**上下文无关**的（"这个还能退吗 / 这个还能保修吗 / 我这单退款多久到账"），
图是唯一的指代来源 —— 这就是"带图 vs 不带图"该有的差。

⚠️ **那条失败是真 badcase，没有为了分数去改题**：断腿木椅问"还能保修吗"，带图回答写
「全线统一保修 **1 年**」—— 它引用了语料里 **2023 版已废止**的保修条款（现行是家具主体 2 年）。
**版本敏感**正是企业做 RAG 的真实动因，这条留着当样本。

### ⑩ 两个"看起来该用、其实只能记录"的字段

`has_exact_fields`（图里有没有值得精确匹配的串）在两次运行里对同一张图给了**不同值**。
所以它**只当诊断信息**，不控制任何分支 —— 抽单号是无条件的（抽不到就不查库）。
把它当开关的后果是"有时查库有时不查"，而用户完全感知不到差别，只会觉得"这个系统时灵时不灵"。

`image_type` 同理：同一张拍屏图两次分别被判成 `photo` 和 `screenshot`。**类型不该驱动逻辑**，
它只用来让人看懂"模型把这张图当成什么了"。

### ⑪ 前端：**两步**上传，以及 `<img>` 为什么拿不到图

```
选图 / 粘贴 → POST /images（201，拿 image_id）→ 提问 {question, image_id}
                                                      ↓
   消息里的缩略图：GET /images/{id}（带 Bearer）→ blob() → <img src="blob:…">
```

**为什么不在提问时把图一起塞过去**：聊天是 SSE（POST + JSON）。塞图要么 base64 进 JSON
（请求体涨 1.33 倍，还会进访问日志），要么把请求改成 multipart —— 于是
"multipart 请求 + SSE 响应"凑在一起，任何一端出错都极难定位。
两步还有个附带好处：图要**长期留着**（刷新页面还得看得见），它天然属于"先存好、再引用"。

**为什么缩略图不能直接写 `<img src="/api/v1/images/xxx">`**：
`<img>` 发的是浏览器自己管理的 GET，**带不了 `Authorization` 头**，而我们的接口要 Bearer。
直接写 src 只会拿到 401 和一张碎图标。所以只能 `fetch`（走 `apiFetch` 加头）→
`blob()` → `URL.createObjectURL`。⚠️ 这是"图片也走鉴权"的必付代价，不是绕路：
去掉鉴权确实能让 src 直接可用，但那等于把所有人的图变成"知道 id 就能看"。

**界面上必须显式说出来的两件事**（`PLAN §8.3` D10）：
读图**失败**（"图片没读成功，只按文字回答"）**任何档位都显示**；
读图**结果**（"用户发来一张图：……"）只在**详细**档、且折叠着显示 —— 它最长 300 多字，
铺开会把回答挤出屏幕。⚠️ 刷新后这两条要**长得一样**：后端把读数写在**用户消息**的
`meta` 里，前端把那条用户消息的 `image_note` / `image_error` 搬到**紧随其后的那条回答**上，
否则"📷 读图结果"会出现在我们的问题底下，看着像用户自己说的话。

### 已知的不完美

| 不完美 | 为什么现在这样 |
|---|---|
| **一条消息只带一张图** | 多图会让读图调用次数、token 结算、以及"哪句话对应哪张图"三样一起翻倍，而客服场景里一张图通常够了（一张运单 / 一处破损）。多图等 ① 渠道做完再谈 |
| **图只进不出** | 存进 `uploads/images/` 就永久留着：**没有清理任务、没有配额、也没有按 sha256 去重**。单张 ≤3 MB，这个量级几年也撑不满盘 —— 但这是"没做"，不是"做得很省" |
| 没有 OCR，B 提取型没做 | OCR 供应商未定；且 OCR 的主场是**逐字保真**，与 VL 的"读懂"是两条链路 |
| fixture 是文生图产物，不是真实照片 | 真实单据涉及隐私（单号/地址/电话），合成图是唯一可进 git 的选项。代价：画面比真实场景干净 |
| 图与订单的**日期对不上**（图里写死 2026-10-17，`orders.delivered_at` 是"相对今天"） | 写死日期会让"签收 30 天窗口"那条演示在某天之后失效。**宁可差一天，也不要故事过期** ⟹ 评测不断言日期 |
| 一张图只读一次、不做 sha256 复用 | 单图只会被读一次（图不继承到后续轮次），做复用是为 0 收益加一层"提示词改版后缓存静默过期"的风险 |

## 9.36 相关度 ≠ 有效性：时间只做**筛选**，绝不进**分数**

> 🔄 **状态（2026-10-22）**：**阶段 A ＋ B ＋ B2 已落地** ——
> A（加列 ＋ 回填 ＋ 灌库映射 ＋ 14 条单测，**零行为变化**）；
> B（`RETRIEVAL_SCOPE` ＋ 把资格条件写进**两条召回 SQL 的 `WHERE`**，**在 `LIMIT` 之前**）；
> **B2（`ref_time` ＋ 生效区间）**。两支尺子并存：`all` 复现基线（0.560 / 0.920 / 0.840 / 1.000），
> `current` 是产品态（**0.720 / 0.960 / 0.920 / 1.000**，精排 MRR **0.8433 → 0.9600**）。
> **阶段 C（冲突告警）未开工**。

> 📌 **B2 把过滤语义从"是不是 active"改成"在参照时刻是否有效"**（详见本节 ⑧）：
> `content_status IN ('active','superseded')` ＋ **生效区间含 `ref_time`**。
> 理由：**历史版本在它当时那个时间点是有效的** —— 客户问"我 2024 年那单保修几年"，
> 2023 版才是正确答案；`draft` / `internal` / `sibling_brand` 则**任何时候都不该**答给客户。
> ⚠️ `ref_time` **只进 `WHERE`**（筛行），**绝不进分数** —— 这条不因为"多了一维"而松动。

### ① 问题：**内容对，依据错**

2026-10-22 用户在生产问「这个椅子角坏了能不能退款？」（带一张椅子破损照片）。
回答**内容是对的**，但"超 30 天按保修顺序处理"那段引的是
**`90-干扰-历史版本/02-2023版保修条款（已废止）`**；而**现行版** `40-服务/40-保修与维修.md`
里有一模一样的三步顺序，**根本没进前 5**。

分数说明了根因：

| # | 来源 | 精排分 |
|---|---|---|
| [1] | 退换货总则（**现行**） | 0.980 |
| [2] | 2023 版退货政策（**已废止**） | 0.979 |

**差 0.001。** 两份政策文字几乎相同，版本差异只有一两个数字 ⟹ 向量是语义压缩，这点差异被抹平。
**推论（重要）**：版本问题**不可能**靠"换更强的 embedding / 更强的精排"解决 —— 信息量上就不成立，
只能靠**元数据 + 过滤**。

⚠️ 这类错**从回答本身看不出来**：有理有据、带引用、置信度 0.98。比"答不出来"危险得多。

### ② 原则：两个判据、两条管道、**只有一个交汇点**

```
【相关性管道】打分
   query 文本 ──► embedding ──► cosine / rerank ──► score
        ↑ 这条路上没有 status、没有日期、没有 ref_time

【有效性管道】布尔
   documents 元数据 ＋ ref_time ──► WHERE ──► TRUE/FALSE ──► 哪些行存在
```

```
score = cosine(embed(query), chunk.embedding)                        ← 输入里没有任何时间量
候选  = { chunk | content_status='active' AND 生效区间含 ref_time }   ← 只有这里碰时间
```

> **有效性不是"参与计算"，而是"改变有哪些行存在"。行不存在，就没有分数可言。**

这不是靠纪律守住，是**结构性保证**：时间根本不在打分那条路径上。

### ③ 落在哪：`retrieval.py` 的**两条**召回 SQL（t2）

```
t1  chat.py：正则抽单号 → 有则查 orders 取 placed_at ─┐
    问句里有显式日期（"2024 年 3 月买的"）──────────┼─► ref_time
    都没有 ────────────────────────────────────────┘   （三级优先，见 ⑧）
t2  retrieval.py：两条召回 SQL 的 WHERE 里加三行（★ 唯一要改的地方）
t3  RRF 融合（只对 t2 出来的行算名次）
t4  API 精排（只吃文本对，不知道世上存在废止版）
t5  拒答判定（只看分数阈值，与时间无关）
t6  生成（提示词里加【时间基准】，见 ⑧）
```

```sql
-- 全文路 与 向量路 **都要加**（只加一路 = 没加）
AND d.content_status IN ('active', 'superseded')
AND (d.effective_from IS NULL OR d.effective_from <= :ref_time)
AND (d.effective_to   IS NULL OR d.effective_to   >= :ref_time)
```

> ⚠️ **区间是闭的**（两端都含）：政策原文写的是"执行至 2025 年 12 月 31 日"，
> 那一天本身仍属有效。代价是**相邻版本不许共用边界日**（旧的 `to` 与新版的 `from`
> 不能是同一天，否则那天两版都算有效）—— 这是**语料编写规则**，落在灌库映射里。
> 现有语料是对的：2023 版 `to=2025-12-31`，现行版 `from=2026-01-01`。

**为什么必须是 t2，不能往后挪：**

| 挪到 | 后果 |
|---|---|
| t4 之后（精排完再删） | 候选集在 SQL 里就已定死 top-k，删两条只剩更少；**第 21 名（可能正是现行条款）永远补不上** |
| t5 之后 | 废止文档已进提示词，模型**已经可能引用它** |
| t6（提示词里写"别用废止版"） | **这就是改造前的做法** —— 靠模型自觉，2026-10-22 已经失败过一次 |

📌 **不是"召回后再筛"，是"带条件召回"**：`WHERE` 先于 `LIMIT`，在同一条 SQL 的一次扫描里完成。

### ④ 字段分工：`content_status` 管"今天"，`effective_*` 管"某个历史时刻"

| 字段 | 回答什么问题 | 需要它的场景 |
|---|---|---|
| `content_status` | 这篇**今天**能不能给客户引用 | 「这个椅子角坏了能不能退款」→ 用现行版 |
| `effective_from/to` | 在**某个历史时刻**哪版有效 | 「**我 2023 年买的床，当时保修几年**」→ 只按今天过滤会漏掉当年那版 |

`ref_time` **不是字段**，是查询参数：有订单 = 那单的 `orders.placed_at`（**事件时间**，不是今天）；没订单 = 今天。
> 📌 三列是**文档属性（常量）**，`ref_time` 是**查询参数（变量）** —— 别混。

### ⑤ 怎么证明"时间没混进分数"（可写成测试的不变式）

> 同一 query、两次不同的 `ref_time` → 候选集 A 与 B；
> **取交集 A∩B 的 chunk，两次算出的分数必须逐位相同**。
> 谁要在打分里偷偷加时间权重，这条立刻红。

### ⑥ 防自欺：**两支尺子必须并存**

| 评测模式 | 衡量什么 | 分数应该 |
|---|---|---|
| `--scope all`（35 篇全参与） | **版本鉴别能力**（看到冲突能否选对 / 会不会指出"已废止"） | **允许低**，这是诚实数字 |
| `--scope current`（产品态） | 产品实际表现 | 高 |
| 两者之差 | **"知识库治理值多少分"** | 新维度，而不是推翻旧结论 |

⚠️ **判定"作弊"的标准不是"有没有过滤"，而是"过滤之后还能不能测那项能力"**。
干扰项（26 篇）是**评测资产**：产品态不召回它们，但全库态永远可复现旧数字。
**哪天为了分数好看把 `--scope all` 删掉，那才是作弊。**

### ⑦ 已知代价 / 边界

| 项 | 说明 |
|---|---|
| **"杜绝"的强度取决于标签** | 只有被正确标成 `superseded` 的才被挡住；标签错了那篇会**永久召回不到、且不报错** ⟹ 必须有评测断言兜底 |
| **挡不住"同版本内自相矛盾"** | 德国站那条（现行文档里 30 天 vs 7 天，两份都 `active`）靠**冲突告警 + 修语料**，不是靠过滤器 |
| **会被分数反噬** | `--scope current` 会掉分（靠存档版答对的题会掉下来）—— 这是诚实代价，先记录、再决定 |
| **引入一条隐性契约** | 语料目录 → `content_status` 的映射固化在 `ingest.py`，挪目录必须同步改（显式 dict ＋ 单测断言兜住） |

> 📎 一句话硬约束（给 AI） → `AGENTS.md` §7.1 **约定 20**

### ⑧ B2 落地：`ref_time` **三级优先**，以及一个"检索对了、生成会自己推翻"的坑

代码：`app/rag/reftime.py`。

| 顺序 | 来源 | 可信度 | 什么时候有 |
|---|---|---|---|
| ① | 订单 `orders.placed_at` | 库里的**事实** | 这句话（或图里的转写）能捞出**本人的**单号 |
| ② | 问句里的显式日期 | 尽力而为，可能读错 | "我 2024 年 3 月买的" |
| ③ | 今天 | **无信号** | 其余全部情况 |

**为什么不做"反问用户要订单号"**：绝大多数是泛问（"保修多久"），反查会把一句话变成两轮，
而用户真在意的时候自己会说日期。所以第 ③ 级**必然**存在，且它等于阶段 B 的行为 ——
`ref_time` 这套机制**不会让任何现有问答变差**。

**多张订单时取最早那张**：只能挑一个时点，宁可让答案落在**更老**的政策边界上
（把 2 年报成 1 年，用户会去核对；把 1 年报成 2 年，用户会被误导）。

#### ⚠️ 坑：检索对了，模型会拿"已废止"四个字把唯一正确的资料否掉

按 2024 年作答时，检索到的**正是** `90-.../02-2023版保修条款`，而它正文第一行写着
"**（已废止）** / 本版已于 2025-12-31 废止"。不给任何解释，模型最自然的反应是：
"该条款已废止，请按现行政策"—— **用检索结果否定检索结果**，正确答案被自己的语料作废。

所以 `prompt.build_messages` 在**真有时间信号**时追加一块：

```
【时间基准】
这笔问题按 **2024-03-15** 这个时点适用的条款来回答（依据：用户订单的下单时间）。
参考资料里若写着「某日废止」，只要废止日在这个时点**之后**，
它对这笔订单就是**当时有效**的条款，请照常据此作答，
并在回答里说明「这是你下单时适用的版本」……
```

三条设计约束：

1. **没有信号时不许加这块**（`RefTime.informed == False`）—— 凭空说一句"按今天"，
   模型会以为用户在问时间，反而多一层猜测。
2. **"依据"必须说人话**（"用户订单的下单时间"），因为它会顺着出现在回答里。
   写成 `source=order` 那种内部词就白费了。
3. **不改 `SYSTEM_PROMPT` 的五条规矩** —— 那块是行为规范，可有可无的上下文另起一段，
   混进去会让人以为"只依据参考资料"这条松了。

#### 可复现：`--ref-time YYYY-MM-DD`

`evals/run.py --ref-time` 把时间钉死（`RefTimeSource.FROZEN`，优先于订单与问句），
并写进结果 JSON 的 `config.ref_time` —— 不记的话，同一批题换个日子跑会得到**另一组数字**，
而两组结果文件长得一样。

> 📌 这已经是本项目**第三次**踩"加了开关但没接上"（前两次：`--scope` 没 `cache_clear()`、
> `--scope` 没传给直接 new 出来的 retriever）。这次的形态是**测试桩签名**：
> `tests/test_closed_book.py::_fake_retrieve` 少一个 `ref_time=` 关键字，
> 于是开卷对照组整个 `TypeError`。**判据：加参数 = 把所有"假实现"也当调用点过一遍。**

### ⑨ B2 的已知代价 / 边界

| 项 | 说明 |
|---|---|
| **多单只能取一个时点** | 两单跨版本（2023 ＋ 2026）时答案只会覆盖更老那版；真要做对得让"候选集"支持时间**区间**（闭区间求交），当前没做 |
| **跨零点可能差一天** | `orders.placed_at` 是 `timestamptz`，`.date()` 按带的时区取。政策区间以**年**计，不影响归属；引入时区换算等于多一个能配错的地方 |
| **不认相对时间** | "去年""前年""买了一个月" 一律落到"今天" —— 读不出来就老实退，不猜 |
| **问句日期可能被误读** | 只认 `2024年3月` / `2024-03-15` 这类确定写法；"2023版条款"这种**版本号**刻意不读成日期（有单测钉死） |
| **相邻版本不能用同一天做边界** | 闭区间的直接后果，属语料编写规则（见 ③） |

## 9.37 飞书渠道：**长连接** ＋ 一个"渠道账号"

v1.2 第①项。代码：`app/channels/feishu.py`（纯逻辑）＋ `feishu_runner.py`（长连接进程）。

### ① 先把两个"飞书"分开

| | 群机器人 **webhook** | 自建应用 ＋ **长连接** |
|---|---|---|
| 凭据 | 一个 URL | `App ID` ＋ `App Secret` |
| 能力 | **只能发**（单向） | **收发都行** |
| 用在哪 | v1.1 **告警**（`ALERT_WEBHOOK_URL`） | **本项**：用户在飞书里提问 |

⚠️ 这两者**极容易混**（用户 2026-10-22 就问过"我不是填过 webhook 了吗"）。
webhook 收不到用户消息 —— 它不是渠道，是喇叭。

### ② 为什么长连接，不是事件回调

回调要**公网可达 ＋ 验签 ＋ HTTPS**，而本项目**明确不做 HTTPS**（`AGENTS §7.1` 约定 4）。
长连接是**出站**的：服务器主动连飞书，**不需要任何入站端口**，也不需要证书。
代价：必须有一个**常驻进程**（内存 **≈ 200 MB**：**实测 anon 197 MiB**，`mem_limit` **320m**，`PLAN §2.3`）。

⚠️ **这个数字第一版是错的**（当时按 96 MB 估）：生产容器一开，`import lark_oapi` 就被内核
**SIGKILL（exit 137）**，而且**死在打任何日志之前** —— `docker logs` 一行都没有；
healthcheck 只 `pgrep` 进程，所以容器**照样 `Up (healthy)`**，现象看着像"连不上飞书"。
判据：`docker stats` 显示 **≈ 99.98% / 上限**；`docker run --memory=96m … python -c "import lark_oapi"`
直接 137、换 256m 立刻通过。教训：**`mem_limit` 不是"省一点没关系"的旋钮** ——
它杀进程时**不留日志**（进程还没活到写第一行），所以只能靠**占用率**认出来，别靠报错。

### ③ 结构：两个文件，`lark` 只出现在一个里

```
feishu.py          解析事件 → 落库 → 跑 pipeline → 发回复     ← 无 lark import
feishu_runner.py   lark 事件 → 交给 feishu.py；发送走 API     ← lark 延迟 import
```

**为什么把 `lark` 关在一个文件里**：解析/去重/切分/渲染都是纯逻辑，测试不需要装 SDK、
更不需要连飞书（14 条测试 0.4 秒跑完）。将来换渠道（企微/钉钉）只重写 runner 那一层。

### ④ 渠道账号：`open_id → 用户` 的映射**先不做**

飞书发消息的人（`open_id`）不属于任何租户用户。真做映射要有成对的表 ＋ 管理界面 ＋
越权设计 —— 那是另一件事。v1.2 先让**所有飞书消息都记在 `FEISHU_CHANNEL_EMAIL` 那个账号**下
（留空回落管理员）。

⚠️ **隔离仍然成立**：消息只落它名下那个租户/用户，Web 端看不到别人的飞书会话。
⚠️ 代价说清：**飞书里人人平等** —— 同一个群里谁问，看到的都是同一个账号的数据视图。
真要多人多身份，就得做映射表（进 `CANDIDATES.md`）。

### ⑤ 三种"不该答"的消息，都要**显式丢掉**

| 情况 | 为什么 |
|---|---|
| `message_type != text` | v1.2 不做飞书侧多模态 —— **如实忽略**，不假装看过 |
| `sender_type != user` | 别的机器人（含我们自己的回复）也会触发事件，不挡会**无限对话** |
| 重复的 `message_id` | 飞书会重投：不挡就答两遍、库里两条一样的消息 |

📌 第二条是**测试抓出来的**：注释先写了、实现漏了，`test_parse_ignores[bot]` 立刻红。

### ⑥ 进程的两种退出必须分开（运维最常问）

```
FEISHU_ENABLED=false        → 打一行日志、**退出码 0**（预期，不是故障）
FEISHU_ENABLED=true 缺凭据  → **退出码 2**，并说清缺哪个（配置错，重启没用）
```

所以 compose 里是 **`restart: on-failure`**，不是 `unless-stopped`：
后者会把"正常退出"也无限拉起 → 重启风暴 ＋ 日志刷屏，真原因被埋掉。
📌 容器停在 `Exited (0)` 是**正常状态**：`docker ps` 看不到，`docker ps -a` 看得到。

### ⑦ 容器与 CD

服务挂在 **`feishu` profile** 下（默认不启用），于是和 `monitoring` 踩同一个坑：
**CD 的 pull / up / 回滚 / logs 四处都必须带 `--profile feishu`**，否则
`--remove-orphans` 会把它当孤儿删掉（`AGENTS §10`）。

镜像**只有一套**（api / worker / feishu 同一个，只是 `command` 不同），
所以 `lark-oapi` 放**主依赖**、不做 optional extra —— extra 装不进镜像，
飞书容器会在运行时 ImportError。代价：其余容器白带几 MB。

### ⑧ 回复发的是**卡片**，不是文本 —— 以及那个降级函数

飞书的 **`msg_type=text` 不渲染 markdown**。第一版就是按纯文本发的，真机联调时用户在群里
看到的是 `**保修期按部件类别分别计算**` 和一整行 `|------|------|` 的**源码**（2026-10-22 实测）。

现在发 **`msg_type=interactive`（卡片）**：正文塞进一个 `lark_md` 元素，**由飞书自己渲染**。

**为什么是卡片，不是 `post` 富文本**：两者都能渲染粗体 / 列表 / 链接，但卡片只要把 markdown
丢进去就完事；`post` 要求我们**自己把 markdown 解析成「行 → 元素 ＋ 样式」的 AST**。
卡片还有第二层好处：将来要做真流式（"更新同一张卡片"）和按钮，都只有卡片这条路。

**为什么必须有一个降级函数 `to_feishu_markdown()`**：`lark_md` 只是 markdown 的**子集**，
下面三样**它不认**，不降级就原样露出源码：

| 语法 | 卡片支持吗 | 降级成 |
|---|---|---|
| **表格**（管道符分隔） | ❌ | `- a：b` 列表行（两列最常见）；多列带上表头 `- 头1：v1｜头2：v2` |
| `#` **标题** | ❌ | 整行加粗 `**标题**` |
| `---` **分割线** | ❌ | 空行（群里一句 `---` 没有信息量） |

⚠️ **降级的第一原则是"信息一条都不许丢"**：宁可难看，也不能把某一列静默删掉 ——
所以**认不出表头时（没有分隔行）就把所有行都当数据**，不许拿第一行冒险。
📌 表格才是这题的真痛点：保修条款天然是"部件 → 期限"的表，而**飞书卡片压根没有表格元素**。

顺带一个小修：模型常把引用标记 `[3]` **单独甩一行**，这里并回上一行
（`…该版本已废止。 [3]`），否则群里孤零零一个数字。

⚠️ **只看正文是不够的**：下面"参考来源"的摘要**直接取自 chunk 原文**，标题和表格行会一起
被带出来（`部件类别 | 期限 | 起算点 | |------|------| | 家具主体…`）—— 第一版就漏了这里，
正文干净了、来源区还在露源码（2026-10-22 真机第二次看到）。所以 `render_reply()` 对摘要
**同样洗一遍**：分隔行整段丢掉、管道符换全角 `｜`、连续 `｜` 合并成一个。

### ⑨ 已知不完美

| 不完美 | 为什么现在这样 |
|---|---|
| **去重是单进程内存**（有界 512 条） | 单副本够用；多副本要换 Redis（同一 `message_id` 会在两个进程各答一遍） |
| **不分块流式**：生成完一次发出 | 飞书机器人没有 SSE 那套；真流式要改成"**更新同一张卡片**"，是另一件事（卡片已经把这条路铺好了，见 ⑧） |
| **长回答按段落切、分多条发** | 飞书单条有上限，而**截断不可接受**（会把结论砍掉）；切点优先空行 |
| **飞书侧的表格只能降级成列表** | `lark_md` 没有表格。真要表格得用卡片的 `table` 元素（列宽、分页、手机端折行全要自己算），v1.2 不做 |
| 没做 `open_id → 用户` 映射 | 见 ④ |

## 9.38 引用可核对性：**能抓出来，先不改写**

v1.3 收尾。代码：`app/rag/citations.py`（纯函数）＋ `pipeline` 里一次调用。

### ① 起因：一个**只有逐条核对才能发现**的错

B2 真机验收（2026-10-23，生产 · 飞书）时，模型把「布艺与填充件 **6 个月**」标成了 `[2]`。
但那两行写在 `[3]`（`2023 版保修条款` 的表格）里，`[2]` 是「保修与退换货的区别」对照表 ——
**那张表里没有任何期限数字**。界面上有引用、点进去是另一段话。

这类错比"答不出来"危险得多：回答**听起来有依据、还真带了编号**。而 `prompt.build_context`
的文档字符串里早就写着"编号错位是引用溯源最隐蔽的失败方式"—— 现在是它第一次现形。

### ② 判据：只核**数字 + 单位**

```
一句话 → 去掉 [n] → 抽出 "数字+单位" 原子 → 这些原子出现在被引段落里吗？
```

| 选择 | 为什么 |
|---|---|
| 只核**数字 + 单位** | 它们"最不可替换"：`7 天`和`30 天`不是同义词，而`退货`和`退换`在语义上等价。拿名词去判，会把**对的**引用判成错的 |
| **日历分量不核**（`2024年` / `3月` / `15日`） | ⚠️ 见下面 ③，**真机首跑就误报的那一条** |
| 一句标多个编号时，**任一**段落命中即通过 | "一句话用两段资料各支撑一半"是合法写法，硬要求"全在一段里"必误杀 |
| 没有数字的引用句**不计入分母** | "这条请咨询人工 [2]" 本来就全是名词。惩罚它等于逼模型不要引用 |
| 归一化只抹空白与千分位逗号 | 每多一条同义词规则，就多一种"我改了你却没改"的走样；而**证据侧**的走样会让错引用"看起来通过" |

### ③ ⚠️ 首跑就误报：**日期不是条款数值**

上线后第一次真机（2026-10-23 02:06，飞书），日志立刻出现：

```
WARNING 引用串号：2/3 句对不上（首个：markers=(3,) atoms=('2024年','3月','2025年','3月')）
```

而那是一条**完全正确**的回答：「按签收日起算，**2024 年 3 月**签收的订单，其 1 年保修期已于
**2025 年 3 月**前后到期 [3]」——
`2024 年 3 月` 来自**用户提问**、`2025 年 3 月` 是模型**算出来**的，只有 `1 年` 才需要在原文里。

⟹ **规则修正：日历分量（`2024年` / `3月` / `15日`）不参与核对。**
不修的话，**任何做了日期推算的回答都会被判串号** —— 而那恰恰是"有用来"的回答。

⚠️ 修的时候差点走反：第一版写成"数值 ≥ 12 就算日历"，于是 `3月` 反而被当条款数值留下。
**年看下限（≥1900）、月日看上限（≤12 / ≤31）** —— 两个方向相反。
⚠️ `个月` 与 `月` **必须区分**：`6 个月` 是条款数值（要核），`3 月` 是日历（不核）。

📌 这也印证了 ④ "只抓不改"：如果当时直接按检查结果去删引用，
这条**正确的** `[3]` 就会被删掉 —— 用户失去核对入口，而库里一条记录都没有。

### ④ ⚠️ **只抓，不改** —— 这是本节的要点

三个理由，缺一条都还能勉强；三条一起，结论就很硬：

1. **改不动**：回答是流式发出去的，事后改写等于让用户看到前后两个版本；
2. **检查器自己会错**：误报时删掉一个**正确**的引用，比串号更糟 ——
   用户失去核对入口，而我们一条记录都没留；
3. **先得能度量**：串号率是 0 还是 12%，决定的修法完全不同。

所以产物是 **`Answer.extra["citation_audit"]`（checked / unsupported / rate / 前三条明细）
＋ 一行 warning ＋ 一个计数器 `gq_citation_support_total{result}`**。
⚠️ 计数器**必须同时记 `ok`** —— 只有分子没有分母，"串号 3 次"是 3/10 还是 3/1000 说不清。

> 📌 真要改输出（删编号 / 降级成"来源可能不准"），等这个比例攒起来再说。
> 候选池里记了三种修法与成本，其中"程序化校验 → 降级标注"正是本节这条检查往后走一步。

## 9.39 冲突告警：**同主题 ＋ 同适用范围**，才算矛盾

v1.3 阶段 C。代码：`app/kb/conflicts.py`（纯函数 ＋ CLI ＋ `GET /reports/conflicts`）。

### ① 要治的病

客服手册写"德国站 30 天"、官网政策写"德国站 14 天法定撤回"。**两份都在知识库里，谁都没发现** ——
等客户撞上才有人知道。这类不一致**不可能**靠检索解决（两份都是"active"、都相关），
只能靠一件**离线体检**把它们并排摆出来。

### ② 判据：三个条件同时成立

```
同一主题（退货期限 / 质量退换期限 / 保修期限 / 报障时限）
＋ 同一适用范围（美国站 / 德国站 / … / 全局）
＋ 同一单位族（天 / 月 / 年 / 小时）
＋ 值不同
```

**为什么"同适用范围"是必需条件**：语料里"总则 7 天 vs 美国站 30 天"**不是冲突**，
那是分地区规则，文档自己写了"本页规则优先于《退换货总则》"。
不筛 scope 的话，检测器第一次跑就会喷一堆这种"看起来矛盾"的东西 —— **然后没人再看告警**。
告警的价值在于"每一条都值得点开"，不在于"发现得多"。

**为什么只比同单位族**：`48 小时`（报障）和 `7 天`（寄回）换算成同一个数就"冲突"，
但它们根本不是同一个动作。**宁可漏，不可误**。

### ③ 首跑数据：199 → 1，每一次收缩都有名字

| 版本 | 冲突数 | 新增的约束 | 治的是哪个假象 |
|---|---|---|---|
| v0 | **199** | — | 完全不能用 |
| v1 | 32 | 只比 `active` ＋ `internal`；跳过讲解稿 | `superseded` 的 2023 版 15 天（那是版本变更，B2 已解决）、`sibling_brand` 的 Lab 30 天（另一门生意） |
| v2 | 6 | 规则句必须有**锚点**（签收/期限/起算/以地区开头） | "客服在 48 小时内审核"、"顾客在 7 天内把商品交给承运方" —— **流程句冒充规则句** |
| v3 | **1** | 年份不算期限（`2023 年版` ≠ 2023 年保修期）；伞形词 `退换货` 不算主题；辟谣稿不参与配对 | "2023 vs 2（year）"；"质量 30 天"被归成"无理由 7 天"；辟谣文自己变成冲突源 |
| **v4** | **3** | 同一行**重复同一个值**不再算"多条规则"；`天 ↔ 小时` 换算后比较；`报障时限` 拆成 `破损` / `丢件少件`；合并键去掉文档名 | "7 天内…7 天内的破损单"被整行跳过（漏）；"48 小时 vs 7 天"因跨单位配不上（漏）；丢件 7 天被拿去和破损 48 小时配对（假）；同一个错值写在三篇文档里被刷成三行 |

**剩下的那 1 条就是真阳性**：`93-干扰-内部FAQ/01-新客服入职手册`（internal）写"德国站 30 个自然日"，
`10-退换货总则`（active）写"德国站 14 天法定撤回权"。
📌 语料里另外两处故意写错的（保修统一 1 年 / 破损 7 天内报）**这一版没抓到** ——
前者因为"保修"主题的锚点太宽（漏），后者因为 `7 天` 与 `48 小时` 跨单位（按设计不换）。
**召回率是已知短板**，见 ④。

### ③′ v1.4 A4 把另外两处也抓到了（3/3）

`README-语料设计说明` 里写明语料有 **3 处故意写错**。v3 只抓到 1 处，A4 之后 **3 处全中，
且没有新增假阳性**（同一份语料：199 → 32 → 6 → 1 → **3**）。四处改动，每处都对应一个具体的漏法：

| 改了什么 | 原来漏在哪 |
|---|---|
| **一行里重复同一个值**算一条事实（只有**不同**值才跳过） | "签收后 **7 天**内…看到 **7 天**内的破损单" —— 这句里 `7 天` 出现两次，被"一行多个期限拆不准"整行跳过。⚠️ **两处故意写错全是这个写法**，所以这一条一改，两处同时浮出来 |
| **`天 ↔ 小时` 换算后比较**（`_CANONICAL_HOURS`） | `48 小时` 和 `7 天` 单位族不同，永远配不到一起。⚠️ **只收这一对**：`1 天 = 24 小时` 是定义；`1 个月 = 30 天` 是**约等于**，拿它去比"4 个月 vs 120 天"会把两条都对的政策报成冲突 |
| **`报障时限` 拆成 `破损` 与 `丢件/少件`** | 合在一起时，"丢件 7 天" 会被拿去和 "破损 48 小时" 配对 —— 三条**假**冲突，反而把真正的那个错（内部稿把**破损**写成 7 天）盖住了 |
| **合并键去掉文档名**（两侧都记 `docs`） | 同一个错值写在"物流政策"和"竞品对比"两篇里时，同一个问题被刷成两行 |

合并之后还有两个"选谁"的问题，都是被**生产报告**打出来的（不是想出来的）：

| 选谁 | 规则 | 不选会怎样 |
|---|---|---|
| **代表文档** | 按状态排序（`active` 最前），代表文档取第一篇，**原句跟着换** | 破损那一侧的第一篇是"竞品对比培训材料"—— 报告把**竞品材料**当政策摆出来，读者会以为那是我们的说法 |
| **代表原句** | 先剔掉"自己写着另一个主题"的句子，再挑带得上范围的，同等条件下取**最短**那句 | 内部质检稿里"丢件 7 天"和"破损 7 天"值相同 → 报告标题写"破损报障时限"、引的却是**丢件**的原句 |

📌 结果（本机语料，离线跑）：`17 篇参与配对 / 24 条事实 / 3 处冲突` ——
德国站 14 vs 30、破损 48 小时 vs 7 天、保修 2 年 vs 1 年。


### ④ 已知边界（都不打算在这一版修）

| 项 | 说明 |
|---|---|
| **召回率低** | ✅ **2026-10-23 改善了（v1.4 A4）**：语料里 3 处故意写错**全抓到**，假阳性仍为 0。⚠️ 但**仍是规则驱动**：只认 4 个主题、只认单期限句；换个说法（"两周"、"一个月出头"）照样漏。见 ③′ |
| **配对范围是"规则型文档"** | 讲解稿 / 辟谣稿 / 存档版 / 兄弟品牌靠**文件名**排除（`_NOT_A_POLICY` / `_COMPARABLE`）—— 又一条隐性契约，靠单测盯着 |
| **只报不一致，不判谁对** | 输出带**原句**和两份文档，30 秒内能人工判断；`kind` 把"内部 vs 政策"和"现行 vs 现行"分开，因为运维动作不同（前者改内部稿，后者要产品决策） |
| **页面没接** | ✅ **2026-10-23 已接**（v1.4 A2）：`/reports` 页顶部一块只读卡片，见 ⑤ |
| **没挂定时任务** | ✅ **2026-10-23 已挂**（v1.4 A3）：服务器 systemd timer 每天 09:30，见 ⑥ |

### ⑤ 页面接入（v1.4 A2）：**现算的体检**和**只读的快照**放在同一页，但不许混在一起

`/reports` 页原来只有"评测快照"（读 `evals/results/*.json`，是**历史**）。
冲突体检加到同一页时，刻意做了三件事：

| 做法 | 为什么 |
|---|---|
| 放在**顶部**、单独一块卡片 | 冲突是"现在要不要动手"；快照是"上个月跑出来多少分"。混在一个列表里，人会把体检结果当成又一个历史数字 |
| **两块的加载 / 出错 / 权限各自独立** | 体检要当场扫库（慢、且**只有管理员能看**），快照只读文件。绑在一起的话，体检 403 会让整页变红，而评测快照本来是好的 |
| 403 显示成**一句灰色说明**，不是错误 | 普通成员看不到这一块是**设计**，不是故障。⚠️ 更不能把它显示成"0 处冲突" —— **"没找到"和"你没有权限"在界面上必须分开** |

数据这块只展示后端算好的三样：**分母**（扫了几篇 / 参与配对几篇 / 跳过几篇）、
**每条的原句**、**两份文档的文件名**。⚠️ 页面**不做任何判断**（不排序谁的优先级高、不标"谁错"）——
判断依据是原句，人 30 秒就能看出来；让程序去猜哪份该改，等于把 §9.39 ③ 那些误报搬进界面。

### ⑥ 定时告警（v1.4 A3）：**每天一次、有冲突才发、跑不成也要发**

代码：`deploy/systemd/grounded-conflicts.{service,timer}` ＋ `deploy/ops/conflicts-check.sh`
＋ `app/kb/conflicts.py::notify_report`。

| 决定 | 为什么 |
|---|---|
| **每天 09:30** ＋ `Persistent=true` ＋ 抖动 5 分钟 | 备份在 03:00，错开；**上午看到才处理得了**，半夜推等于没推。关机错过要**补跑** —— 否则"那天没体检"没有任何痕迹 |
| **只在真有冲突时推** | 每天一条"一切正常"，等于训练所有人忽略这个群；等真有冲突时没人看（和 ③ 收口的动机是同一个） |
| **`push_text` 返回 `False` 就当失败（exit 1）** | 它在 `ALERT_WEBHOOK_URL` 没配时是**静默返回 `False`** 的。不翻成失败，systemd 那边永远是绿的、群里一条没有 —— `AGENTS §10`「某一步静默没生效」的同一个病 |
| **体检自己跑不起来时，另推一条失败告警** | 容器没起 / 连不上库，只留一行 journalctl ≙ 没有告警。脚本先推再 `exit 1`，两条路都有声音 |
| unit 里调 **`docker exec gq-api …`**，不是 `docker compose exec` | systemd 给的是**干净环境**，compose 要先做变量插值 → 实测直接 `required variable ACR_REGISTRY is missing`。`docker exec` 只认容器名 |
| unit 文件**进仓库**（`deploy/systemd/`），但**不随 CD 同步** | 部署不该悄悄改定时任务（改 `/etc/systemd/system` 还要 `daemon-reload`）；但 unit 内容必须可复盘，**不能只活在服务器上** |

📌 为什么"先让人看几轮再自动化"没有更晚做：A2 上线后这个报告已经能被人看见，
定时任务只是**把"人记得去看"换成"它自己说"**；而且它只发**有冲突**的那一次，
噪音上限就是真的冲突数（当前 1）。

## 9.40 引用降级标注：**把"我没把握"说出口**，而不是替用户删引用

v1.4 · 治理闭环 A 组第 1 项。代码：`app/rag/citations.py`（判据不变）＋
`app/api/chat.py`（`done` 事件带 `citation_audit`）＋ `app/channels/feishu.py::citation_hint`（末尾一行）。

### ① 从"能抓"到"说出口"，中间隔着一个决策

§9.38 已经把串号抓出来了 —— 但**只有日志和 Prometheus 知道**。
用户看到的仍然是一个"带编号、看起来可核对、点过去却是另一段话"的回答。
对他而言 §9.38 **等于不存在**。

三种走法：

| 方案 | 会发生什么 | 结论 |
|---|---|---|
| 删掉对不上的 `[n]` | 检查器**自己会误报**（§9.38 ③ 就是活例），误删的是**正确**的引用 | ❌ 用户失去核对入口，我们一条记录都没留 |
| 换成 `[?]` / `[未核实]` | 看着像系统坏了；而且 `[?]` 到底什么意思没人教过用户 | ❌ 比起"没把握"，更像是"坏了" |
| **末尾追加一行提示** | 正文**一个字不动**，末尾多一句"本次有 N 处引用未能核对上，请以原文为准" | ✅ |

选它的三个理由：

1. **改不动正文**：回答是流式发出去的，事后改写 = 用户看到前后两个版本（§9.38 ④ 理由一）；
2. **判断权交回用户**：我们只报告"核不上"，不宣布"这是错的" —— 替他核对，不替他下结论；
3. **它自己也是度量**：提示出现的比例 ≈ 串号率，和"人看得见的抱怨"是同一个东西。

### ② 措辞：「没核对上」≠「答案是错的」

⚠️ 这是本节最容易写错的地方。核不上的原因至少有三种：

| 原因 | 例子 | 我们的判定 |
|---|---|---|
| 真串号 | 数值写在 `[3]`，标了 `[2]` | 该提示 ✅ |
| **表述换了** | 原文 `24 个月`，回答写 `2 年` | 也提示（我们只做字符串核对） |
| 模型自己算的 | 日期推算（`2025 年 3 月`） | 已豁免（§9.38 ③ 日历分量） |

中间那一类**并不是错误**。所以提示只陈述"**我们的核对结果**"：
写成"第 2 处引用有误"，就是在把一堆**正确**的回答钉成错误 —— 比不给提示更糟。

### ③ 只在**真的核过**时才提示（也才带字段）

| 情形 | `checked` | 提示 | `done.citation_audit` |
|---|---|---|---|
| 拒答 / 闭卷 | 0 | 无 | **不带** |
| 有引用但整句全是名词 | 0 | 无 | **不带** |
| 核过、全对上 | >0 | 无 | 带（`unsupported: 0`） |
| 核过、有对不上 | >0 | **有** | 带（含前 3 条明细） |

⚠️ **常态下每次回答都挂一句警告，用户很快就会当水印不再读**（狼来了）。
两端必须同一口径：后端 `checked > 0` 才带这个字段，前端 `asCitationAudit()` 里
`checked <= 0` 一律当没有 ⟹ 调用方只需要判 `undefined` 一个条件。

### ④ 谁显示、谁暂时不显示

| 渠道 | 现状 |
|---|---|
| **飞书** | 追加在**最后一行**（来源区之后）。⚠️ `FEISHU_SHOW_SOURCES=false` 时来源不显示，**提示照样显示** —— 没有来源可点时，这行提示恰恰更重要 |
| **Web** | `done` 事件已带 `citation_audit`（TS 类型 `DoneEvent.citation_audit`），**界面暂不展示** |

Web 不展示的理由：那边的引用是**可点的**，用户能自己点开核对；而飞书里 `[1]` 点不了，
来源只是一行文字摘要 —— 飞书才是"看起来能核、其实核不了"的那一端。
⚠️ 这是**已知的不完整**，记在 §10.3；数据先有、展示后补，比反过来便宜。

### ⑤ 代价与没做到的

- **提示是"整条回答级"的**：用户知道"有 1 处不对"，但**不知道是哪一处**。
  逐句标注（`[2]?`）必须改正文，与 ① 直接冲突 —— 这是刻意不做的。
- **顺带覆盖了一种情况**：引用了**不存在的编号**（只有 3 段却写了 `[9]`）时，
  取不出被引段落 ⟹ 该句所有原子都"找不到" ⟹ 会被判成串号。方向是对的。
- **不改善回答质量**：它只是把"看起来可核对"变回"明确告诉你哪里没对上"。

## 9.41 第三组对照：**随机证据**，把"提示词的功劳"和"检索的功劳"拆开

v1.4 B3（#8）。代码：`evals/run.py` 的 `RandomEvidencePipeline` ＋ `--mode random|all`。

### ① 为什么两组不够

§9.34 的闭卷 vs 开卷能证明"**给了证据**比没给强"，但那份证据里混着两样东西：

| 混在一起的两样 | 举例 |
|---|---|
| **检索找对了** | 召回的是《退换货总则》里那 7 天 |
| **提示词要求引用资料** | "只依据【参考资料】""每条结论标 `[n]`" —— 格式本身就在逼模型收敛 |

要去掉后者的干扰，就需要第三组：**开卷的提示词 ＋ 无关的证据**。

```
闭卷（无证据） → 随机证据（开卷提示词 ＋ 无关段落） → 真证据（开卷）
        └──── 提示词 ＋ 格式的功劳 ────┘└──── 检索的功劳 ────┘
```

### ② 三条保证（缺一条这个实验就白做）

| 保证 | 为什么 |
|---|---|
| **固定随机种子**（`--seed`，每题派生子种子） | 否则"某次运气好"无法复现；同一批题重跑必须抽到同一批段落 |
| **同样 5 段、长度相近**（中位数 ±40%） | 否则"证据更少 / 更短"会混进结论 |
| **排除同文件**（题干 `must_hit` 指向的文档不参与抽取） | 不然随机抽到正解所在文档，这组就不是"无关证据"了 |

### ③ 实现：只覆盖一个方法

```python
class RandomEvidencePipeline(RagPipeline):
    async def _retrieve(self, question, *, ref_time=None):
        return list(self._evidence), None, "none"
```

⚠️ **只换检索结果**，提示词 / 拒答 / 引用 / 落库全走原路径 —— 和 §9.34 ② 那条纪律一样：
对照组和被试组的差异里**不许混进"两套实现"的噪音**。
⚠️ 置信度给 `None`：没有可信的相关性分数就不该拿它判拒答；`_should_refuse` 对
"没分数但有命中"的结论是**照答**，所以随机组和开卷组**一样尽力回答**。
⚠️ 随机组的**引用不判**（`cite_ok=None`）：它的"引用"是随机的，判它对错等于判它作弊。

### ④ 实测（2026-10-23，B 库 20 题，单次运行）

| 模式 | 要点全中 | 要点命中率 | 含数字的回答 | 出现禁语 | 引用对 |
|---|---|---|---|---|---|
| 闭卷 | 0/20 | 27.6% | 18/20 | 0/20 | 不判 |
| **随机证据** | **0/20** | **10.5%** | 10/20 | **1/20** | 不判 |
| 开卷 | 15/20 | 93.4% | 20/20 | 0/20 | 20/20 |

**归因**（按要点命中率）：

| 这一段 | 数值 | 读法 |
|---|---|---|
| 提示词 ＋ 格式 | **−17.1%**（随机组 − 闭卷） | ⚠️ **负贡献** |
| 检索 | **+82.9%**（开卷 − 随机组） | 几乎全部功劳 |

### ⑤ 那个负号才是这一节最值钱的东西

**无关证据比没有证据更糟。** 闭卷时模型至少会按自己的知识给出大致方向（27.6%）；
一旦给它 5 段"看起来像政策"的无关段落，它会**把它们当成依据**，还更敢写具体数字 ——
命中率掉到 10.5%，并且**唯一一次踩到禁语**就出在这一组。

📌 这直接回答了面试里那句"RAG 的价值是不是就是提示词工程"：
**不是**。提示词单独拿出来是**负的**，把分数拉起来的是"检索到了对的那几段"。
📌 它也印证了线上那条取舍：**宁可不答，也不要拿低分候选硬答**（`_should_refuse`）——
按这一组的数据，"给一段不太相关的资料让它作答"比"直接说没有"更危险。

### ⑥ 边界

| 边界 | 说明 |
|---|---|
| 单次 20 题 | ±1 题抖动；随机组是 0/20，这个量级的差别不是抖动 |
| "无关"是概率意义上的 | 从全库 477 段里随机抽，偶尔可能抽到与题目弱相关的段落 —— 这会**抬高**随机组，让"检索的功劳"偏**保守** |
| 只跑 B 库那 20 题 | 生成层题集才有 `required_points`，才判得出"要点命中率" |
| 随机池含已废止 / 兄弟品牌段落 | 对"随机"来说无所谓（本来就不该被引用），但这也意味着它顺带测了"抗干扰" |

## 9.42 短追问的检索改写：**只拼规则，不调模型**

v1.4 C1'（F2）。代码：`app/rag/followup.py`（纯函数）＋ `pipeline` 里一行。

### ① 要治的病

用户先问「退货运费谁出」，接着说「**德国呢**」。第二句里**没有任何政策词** ——
全文（trgm）和向量都检索不到《地区差异》那一段，可它显然是同一话题的追问。

⚠️ 这类问题在**两种界面**上都会出现（Web 输入框、飞书群里），而且**看起来完全正常**：
用户收到一条答非所问的回答，我们这边没有任何报错。

### ② 为什么用规则拼接，不让模型改写（`PLAN §8.7` D2）

| 方案 | 问题 |
|---|---|
| 让模型把追问改写成完整问句 | 多一次模型调用 ＝ 多一处不确定性；而且**改错无法解释** —— 同一个问题两次运行召回不同，badcase 归因就断了 |
| **规则拼接**（选它） | 每一步都能复述给用户听："你上一句问了 X，这一句只有「德国呢」，所以检索时两句一起用" |

⚠️ **只改检索 query，不改提示词**。提示词里永远是用户这一问的原话 ——
把「德国呢」改写成别的句子塞给模型，等于**替用户重述问题**。

### ③ 什么时候才拼（三条缺一不拼）

| 条件 | 为什么 |
|---|---|
| 本问 **≤ 15 字** | 长问句自己带足了语境；拼上一轮只会**稀释**召回 |
| 且含**指代词**（`它` / `这单` / `那单` / `这个` / `那个` / `呢`） | 这类词自己不能独立成意。⚠️ 刻意**不认**单字 `这` / `那`（"这个怎么处理"不是追问） |
| 且历史里找得到**上一条用户问句** | 没有上一轮就没什么可拼 |

⚠️ **宁可不改，也不要改错**：拼错了会把召回导到上一轮的话题上，而用户看到的仍是
一条"看起来正常"的回答 —— 最难查的那类坏。
⚠️ 上一轮问句放**前面**、本问放**后面**：检索按"整串像不像某段话"打分，
能对上文档的是前面那半句。

### ④ 实现上的两个坑

| 坑 | 说明 |
|---|---|
| **历史里包含本问自己** | `app/api/chat.py` 是**先落库本问、再读历史**的 → 不跳过"与本问相同"的那条，会拼成「德国呢 德国呢」 |
| **上一轮问句可能很长** | 截到 60 字：太长的历史会把这一问整个淹掉 |

### ⑤ 实测（2026-10-23，真实检索：全文＋向量 → RRF → rerank）

6 组「上一轮 ＋ 追问 ＋ 期望文档」：

| 追问 | 改前 | 改后 |
|---|---|---|
| 「德国呢」 | ✗ 没进 top-5 | **✓ 第 2 位** |
| 「德国站呢」（会员升级） | ✗ 没进 top-5 | **✓ 第 1 位** |
| 「日本呢」（包邮门槛） | ✓ 第 4 位 | ✓ **第 1 位** |
| 「那电子件呢」/「日本便利店付的呢」/「六楼没电梯那个呢」 | ✓ 第 1 位 | ✓ 第 1 位（**没被动过**） |

**改前召不到、改后召到了：2/6**，另有一例位次从第 4 升到第 1，**没有一例变差**。

### ⑥ 零回归的证据（不是"我觉得不会影响"）

| 尺子 | 结果 |
|---|---|
| 检索层（60 题 × rerank） | **0.983 / MRR 0.885** —— 与 C1' 之前**完全一致** |
| 生成层（20 题开卷）重跑 | 引用来源 **20/20 完全一致**；分数 14/20 vs 15/20 的差别来自**模型措辞抖动**（`gen-12` 从错变对、`gen-14`/`gen-20` 从对变错，三题的 `cite_ok` 都是 True） |

📌 关键：`evals/run.py` **从来不传历史** ⟹ 改写**不可能**触发（单测
`test_first_question_of_a_conversation_is_never_rewritten` 盯着这条）。
所以"重跑两支尺子"能证明的其实是不回归；**有没有用**要靠 ⑤ 那 6 组实测。

### ⑦ 边界

| 边界 | 说明 |
|---|---|
| **只拼最近的那"一句"** | 连着追问（「退货运费谁出」→「德国呢」→「那法国呢」）时会**一直往前找到最近一句有实质内容的问句**（2026-10-24 补），但**只取一条**：三句连拼会把 query 撑长，反而稀释召回 |
| **不做指代消解** | 不判断「它」指什么，只是把上一句整体带上。指错了也只会"多带点上下文" |
| **不识别话题切换** | 用户说「换个话题，那退款呢」时仍会拼上一轮 —— 目前靠"上一轮也是退款相关"侥幸不坏 |
| **15 字 / 6 个指代词是拍出来的** | 没有标定集可调。它们的作用是**把改写限制在明显是追问的场合**，不是"最优阈值" |
| **评测测不到这块**（⚠️ 说实话） | `evals/run.py` **从来不传历史**（每题都是会话里的第一句）⟹「连续短句累积」「`history_messages` 6→12」在评测数字上**必然一模一样**。重跑评测只能当**回归网**（确认没动坏别的），**不能**当"多轮变好了"的证据。要量化它得先补一组多轮题集 |

### ⑧ 2026-10-24 走查补的两处（P1-⑧）

| 改动 | 为什么 |
|---|---|
| **连续短句累积**（`_is_thin()`：跳过"本身就是追问"的历史问句） | 连追三句时只拼紧邻那句，query 会变成「德国呢 那法国呢」—— 里面**一个政策词都没有**，等于没拼。⚠️ 判据是"短 **且** 带指代词"，**不能只看长度**：`能退款吗`（5 字）自己能独立成意，跳过它会把检索引到更早、已经跑偏的话题上 |
| **chip「已合并上一轮检索」**（详细档，挂在**用户消息**上） | 改写在后台发生，用户看不出有没有生效 —— 答对了以为是模型聪明，答偏了也无从判断是不是改写惹的祸。⚠️ 落两处：SSE `sources`（刚问完就看到）＋ **用户消息的 `meta`**（刷新后还在，而"想看出有没有生效"往往正是事后看的）。chip 与改写共用 `previous_question()` 一个判断 ⟹ **chip 亮 ⟺ 检索真的被改写**（`tests/test_followup.py` 钉住这条） |

## 9.43 上传前先压一遍：**前端压一次，省三次**

走查 P1-⑦。代码：`web/src/api/images.ts::squeezeForUpload()`。

### ① 要治的病

一张 6 MB 的手机截图，在**没压**的形态下要付三次钱：**上传 6 MB**（弱网好几秒）＋
**服务端存 6 MB**（命名卷是有限的）＋ **每次刷新页面再下 6 MB**（消息里的缩略图走的是原图）。

⚠️ 后端**已经**会把图缩一份 —— 但那份**只喂给读图模型**，不落盘（§9.35：原图保持上传时的字节，
`sha256` 就是它的哈希）。所以"后端会压"这件事，对上面三笔开销**一点作用都没有**。
这是很容易自我安慰的一句话，写在这里防复发。

### ② 为什么不在后端压完再存

| 做法 | 代价 |
|---|---|
| 后端收 6 MB → 压 → 只存压完的 | 上传那一趟省不掉；而且**改了"用户上传的事实"** —— 原图 sha256 对不上，出问题没法回溯 |
| **前端先压 → 只传压完的** | 三笔全省；代价是**客户端会重编码**，见 ⑤ |

顺带一个好处：压完的图通常 **< 1 MB**，正好落进 `to_model_copy()` 的透传条件，
于是**送模型的那份＝前端压完的那份**，全链路只编了一次。

### ③ 四条边界（每条都对应一个真实会出的错）

| 边界 | 不做会怎样 |
|---|---|
| **已经够小就一个字节都不动**（长边 ≤1600 **且** ≤1 MB） | 截图上的细笔画文字在 JPEG 里起振铃（"1/7""8/B" 容易糊）。1 MB 这个门槛不是拍脑袋 —— 它**正好是后端透传的条件**，于是"前端没压"⟹"模型拿到的就是原图"，不会压两遍 |
| **压完反而更大就退回原图** | 描边 / 纯色截图重编码成 JPEG 完全可能变大，那压它只有损失 |
| **透明区先铺白底** | JPEG 没有 alpha，canvas 初始是**透明黑** → 带透明的截图变成一块黑框 |
| **EXIF 方向烤进像素**（`createImageBitmap(..., { imageOrientation: 'from-image' })`） | 手机照片是"横着存 ＋ 一个标记说请转 90°"。不转正，界面上是一张躺倒的图，**而且不报错** |

解不开（HEIC、超大拼接图、canvas 不给）→ **照原图传**，让后端说它的话
（"不支持的图片格式：HEIF"比前端编的"压缩失败"准得多）。

### ④ 为什么"抬上限"和"加压缩"必须一起做

两个动作单独做都是白做：

- **只抬上限（3 → 8 MB）**：用户手里那张 6 MB 的图照样要传 6 MB、存 6 MB、下 6 MB。
- **只加压缩**：压不动的图（HEIC、超大拼接图）照样被 3 MB 挡在门外。

⚠️ 还有第三处必须同步：**nginx 的 `client_max_body_size`（4m → 12m）**。
不同步的话，8 MB 的图会被 nginx 用**它自己的 HTML 错误页**挡回来，前端解析不了 ——
症状是"本地传得上去、部署后传不上"。（这个文件是**打进 nginx 镜像**的，
镜像 tag 又是 commit SHA，所以 push 之后下一次 CD 自己就会带上新配置，不用手动 reload。）

### ⑤ 代价

**JPEG q0.85 对大截图是有损的。** 之所以接受：这条路径**只作用于大图**
（日常 Ctrl+V 的截图基本都在 1 MB 以内，走透传不动），而"大图"本来就会被后端缩到长边 1600
再交给模型 —— 不给前端压，模型看到的也只是另一份重编码的结果。

实测（真浏览器，`__squeeze.html` 临时校验页，测完删）：

| 输入 | 输出 |
|---|---|
| 3200×2400 噪声 JPEG（当成"手机照片"，**6.1 MB**） | **940 KB**，长边 1600 |
| 2400×1800 纯色 PNG（88 KB） | 12 KB，1600×1200，文件名跟着改成 `.jpg` |
| 2000×1500 带透明 PNG | 透明区变 **rgb(255,255,255)**（不是黑） |
| 3000×2000 ＋ `Orientation=6` 的 JPEG | **1067×1600 竖图** —— EXIF 已烤进像素 |
| 300×200 的小 PNG | **原样返回 `null`**（一个字节都没动） |

## 9.44 飞书群聊：**按人分桶**，不是按群

走查 P1-⑥。代码：`app/channels/feishu.py::_conversation()` ＋ `app/channels/feishu_names.py`。

### ① 要治的病

以前的实现是"**一个 `chat_id` = 一个会话**"（标题里编了 chat_id 来找回）。
私聊没问题（`chat_id` 天生一人一个），**群聊会出人命**：
群里 A 问「我的单 SF10001 到哪了」，B 接着问「那我的呢」——
两个人共享一条上下文，模型会把 **A 的单号**当成 B 的接着答。
这类错**不报错、看起来还很连贯**，是最难被发现的那类坏。

### ② 怎么分

| | 分桶键 | 为什么 |
|---|---|---|
| 私聊 `feishu_p2p` | `(tenant, chat_id, open_id)` | `chat_id` 已经唯一，加上 `open_id` 只是统一代码路径 |
| **群聊 `feishu_group`** | `(tenant, chat_id, **open_id**)` | 同一个群里有好几个人 ⟹ **必须按人分**，否则上下文串台 |

⚠️ 代价：**群聊的会话条数会明显变多**（群里 10 个人问过 = 10 条）。
这就是为什么列表必须**三级分组**（内部 / 私聊 / 群聊·群名（N 人））——
不分组的话，列表很快被"飞书用户 · 3a9c1f"淹没。

⚠️ 去重靠**列**（`uq_conversations_external` 唯一索引），不再靠标题：
标题会变（群改名），列不会。`web` 那三列是 NULL，而 PG 认为 NULL 互不相等
⟹ 网页端会话不受这条唯一约束影响。

### ③ 真名：**拿不到就降级，绝不挡回答**

`title` = **这个人**（群里的某位顾客 / 私聊的那个人）；`external_title` = **群名**。
两者都要调飞书开放平台（`im:chat:readonly` / `contact:user.base:readonly`）。

| 情况 | 表现 |
|---|---|
| 有权限、在通讯录可见范围 | 显示真名 / 真群名 |
| **没权限 / 不在可见范围 / 接口抖了** | 「飞书用户 · `open_id` 后 6 位」「飞书群 · `chat_id` 后 6 位」，**回答照常** |
| 解析过的会话 | **7 天内不再问**（`external_title_at`）；过了 7 天再刷一次，群改名能跟上 |

⚠️ **无论成功失败都写 `external_title_at`**：不写的话，解析一直失败时**每条消息**都要重试一次
注定失败的 HTTP —— 这是"降级"和"拖慢"的分界线。

| **上传只吃文本类（`.md` / `.markdown` / `.txt`）** | 加 PDF / docx 就要引解析库，还会多一类"解析出来是垃圾但没人发现"的**静默失败**（扫描件、加密、乱码字体）。当前语料本来就是 markdown | 真要接 PDF 时：先做**解析结果的可见性**（把抽出的文本显示给上传者确认），再接解析库 |
| **入库队列只有单个消费者，且没有重试退避 / 死信队列** | 单 worker 是**有意的**（embedding 密集、内存可预测，2C2G 上不开并发）。失败就**如实落 `FAILED`**，靠用户重传 —— 而启动时的「补队列 / 改判」逻辑**假设自己是唯一消费者** | 要开第二个 worker 时**先改 `_recover`**（否则两个进程会把对方的任务互相重排队）；要做自动重试时要区分**可重试**（限流 / 超时）和**不可重试**（超限 / 编码坏） |
| **限流是固定窗口，窗口边界上最多突发 2 倍** | 这里治的是「脚本刷」，不是「精确公平」；滑动窗口要多一次 zset 操作，而收益只是消掉边界那一小段突发 | 真要「精确公平」时（那时也该先有真实流量数据了） |
| **配额的账只在 Redis 里按天记，不落库** | 每回答一次就多一条写库不值得；而且「上周某人用了多少」现在没人问 | 要做**成本报表**时 —— 得把 `usage` 也写进 `messages`（现在只存 `latency_ms` / `confidence`） |
| **元数据锁只「不用」老向量，不「修」它们** | 读侧过滤是**安全**的那一半；重嵌入是**要花时间和钱**的另一半，没法自动做 | 真要自动化，得先能**估算重嵌入成本**并让用户确认（`ingest.py --replace` 现在是一次性的手工动作） |
| **报告页没有"对比两次运行"的能力** | 只按快照平铺展示，配置写在卡片上让人自己看。做 diff UI 要先解决"哪两次可比"（配置一致吗？题集改过吗？），那是另一个话题 | 判分口径稳定下来、且能说清"配置相同才算可比"之后 |
| **`--no-embed` 会留下没有向量的 chunk** | 补向量只能 `--replace` 重跑；忘了加就**静默跳过**（文档被判"已入库过"），**向量永远补不上且不报错**。现在的防线只是"脚本结束时打印一句提醒" | 拿到 key 后立刻 `--replace`；或加一个比 `--replace` 安全的 **`--embed-only`** 补齐模式 |
| **`citations` 字段混装两种含义** | 成功回答时它是"**引用**"；拒答时（§9.19 决定落库后）它是"**检索候选，但没有被引用**"。**字段名会撒谎** | 要做干净就得拆开（加 `retrieved` 字段，或给每条标 `used: bool`）。**当前不值得**，但要知道它是个将就 |
| ~~**只有一套拒答阈值，却要跟两种分数比**~~ | ✅ **2026-10-17 已修**：`answer_min_score`（rerank，0.60）与 `answer_min_cosine`（余弦，**0.45**）分成两个配置，`_should_refuse` 按 `score_kind` 选。⚠️ 修完仍要承认：**余弦几乎没有分离度**（可答 0.409~0.688 ／ 不可答 0.352~0.578，重叠区比可答区间还宽）⟹ rerank 关掉时**拒答能力显著下降**，这是降级不是等价配置 | 若哪天要把"rerank 关闭"当成可用形态，得换更强的**召回**或加一个**轻量交叉编码**；但那就超出"模型全走 API"的预算了。数据与取舍见 **§9.25** |
